# ประวัติและรายละเอียด Android ทุกเวอร์ชัน (1.0 → 17)

เอกสารนี้อธิบายวิวัฒนาการของระบบปฏิบัติการ Android ตั้งแต่เวอร์ชันแรกจนถึง
Android 17 โดยแต่ละเวอร์ชันจะครอบคลุม: **ฟีเจอร์/จุดเด่น**, **ข้อดี**, **ข้อเสีย/จุดด้อย**,
**ประเด็นด้านความปลอดภัย/ช่องโหว่** และ **ความแตกต่างจากเวอร์ชันก่อนหน้า**

> หมายเหตุ
> - "API level" คือหมายเลขที่นักพัฒนาใช้ระบุความสามารถของแพลตฟอร์ม (ใช้ใน
>   `compileSdk`/`targetSdk`/`minSdk`)
> - ส่วนช่องโหว่เป็นการสรุปเชิงข้อเท็จจริง/การศึกษา (ชื่อช่องโหว่และผลกระทบ) ไม่ได้
>   ให้รายละเอียดวิธีโจมตี ช่องโหว่ที่ระบุถูกแก้ไปแล้วผ่าน security patch
> - ข้อมูล Android 16–17 อ้างอิงแหล่งข่าว/เอกสารทางการปี 2025–2026 (ดูท้ายเอกสาร)
>   บางรายละเอียดของเวอร์ชันใหม่อาจมีการเปลี่ยนแปลงเพิ่มเติมภายหลัง

## ยุคเริ่มต้น (2008–2010)

### Android 1.0 / 1.1 (API 1–2, 2008–2009)
- **ฟีเจอร์:** Android Market, เว็บเบราว์เซอร์, Gmail, Google Maps, ซิงก์ Google, ระบบแจ้งเตือนแบบ pull-down
- **ข้อดี:** เปิดกว้าง (open source), รองรับผู้ผลิตหลายราย, มัลติทาสก์ตั้งแต่ต้น
- **ข้อเสีย:** ยังไม่มีคีย์บอร์ดบนจอ (พึ่งฮาร์ดแวร์), แอปน้อย, UI หยาบ
- **ความปลอดภัย:** วาง **app sandbox** บนพื้นฐาน Linux user ID ต่อแอป (รากฐานที่ใช้จนถึงปัจจุบัน) แต่ยังไม่มีการเข้ารหัสข้อมูลเครื่อง
- **ต่างจากก่อนหน้า:** เป็นรุ่นแรก

> **เวอร์ชันแรกที่ถึงมือผู้ใช้ทั่วไป = Android 1.0 (กันยายน 2008)**
> - เครื่องแรกที่วางขายจริงคือ **HTC Dream** (ในสหรัฐฯ ใช้ชื่อ **T-Mobile G1**)
>   วางจำหน่ายเดือนตุลาคม 2008 — ถือเป็นสมาร์ตโฟน Android เครื่องแรกสำหรับผู้บริโภค
> - ตัวเครื่อง G1 มีจอสัมผัสแบบสไลด์เปิด **คีย์บอร์ด QWERTY จริง** (ยังไม่มีคีย์บอร์ด
>   บนจอในเวอร์ชันนี้), แทร็กบอล, รองรับ 3G/Wi-Fi
> - **แยกให้ชัด:** ปลายปี 2007 Google ปล่อยเพียง **SDK รุ่นพรีวิวสำหรับนักพัฒนา**
>   (early look) ซึ่ง **ยังไม่ใช่** ผลิตภัณฑ์สำหรับผู้ใช้ทั่วไป — เวอร์ชันสู่ผู้บริโภค
>   จริงเริ่มที่ 1.0 บน HTC Dream/G1
> - **Android 1.5 Cupcake** เป็นเวอร์ชันแรกที่ใช้ **ชื่อรหัสขนม** และเพิ่มคีย์บอร์ด
>   บนจอ แต่ **ไม่ใช่** เวอร์ชันแรกที่ถึงมือผู้ใช้

### Android 1.5 Cupcake (API 3, 2009)
- **ฟีเจอร์:** คีย์บอร์ดซอฟต์แวร์บนจอ + third-party keyboard, widget บนหน้าโฮม, อัดวิดีโอ, อัปโหลด YouTube
- **ข้อดี:** ทำให้โทรศัพท์แบบจอสัมผัสล้วนใช้งานได้จริง
- **ข้อเสีย:** พิมพ์บนจอยุคแรกยังแม่นยำน้อย
- **ต่างจากก่อนหน้า:** เริ่มระบบ **codename ขนม** และเปิดแนวทาง widget/soft keyboard

### Android 1.6 Donut (API 4, 2009)
- **ฟีเจอร์:** รองรับความละเอียด/ขนาดจอหลายแบบ, Quick Search Box, รองรับ CDMA
- **ข้อดี:** เปิดทางให้ผู้ผลิตทำเครื่องหลากหลาย → ขยายตลาด
- **ข้อเสีย/จุดด้อย:** เป็นจุดเริ่มต้นของ **fragmentation** (ความหลากหลายของอุปกรณ์ที่ทำให้พัฒนา/อัปเดตยาก)

### Android 2.0–2.1 Eclair (API 5–7, 2009–2010)
- **ฟีเจอร์:** Google Maps Navigation (นำทางฟรี), รองรับหลายบัญชี, HTML5, live wallpaper, กล้องมีแฟลช/ซูมดิจิทัล
- **ข้อดี:** ฟีเจอร์นำทางฟรีเป็นจุดขายใหญ่
- **ความปลอดภัย:** เพิ่มนโยบายรหัสผ่าน (Exchange) สำหรับองค์กร

**ขยายความ: "HTML5" ใน Eclair คืออะไร**

HTML5 คือมาตรฐานเว็บรุ่นที่ 5 ที่เพิ่มความสามารถให้หน้าเว็บทำสิ่งที่เมื่อก่อนต้องพึ่งปลั๊กอิน
(เช่น Flash) ได้ในตัว เบราว์เซอร์ของ Eclair (เอนจิน **WebKit**) เริ่มรองรับความสามารถ
เหล่านี้ ซึ่งสำคัญมากในยุคนั้นเพราะมือถือไม่เหมาะกับ Flash:

- **`<video>` / `<audio>`** — เล่นวิดีโอ/เสียงในหน้าเว็บได้โดยไม่ต้องมี Flash player
- **`<canvas>`** — วาดกราฟิก/แอนิเมชัน 2D ด้วย JavaScript (ทำเกม/ชาร์ตในเบราว์เซอร์)
- **Geolocation API** — เว็บขอตำแหน่ง GPS ของเครื่องได้ (แผนที่/ค้นหาใกล้ฉัน)
- **Application Cache (AppCache)** — แคชหน้าเว็บไว้ใช้ **ออฟไลน์** ได้บางส่วน
- **Local Storage / Web Storage** — เก็บข้อมูลฝั่งเบราว์เซอร์ (แทนคุกกี้ที่จำกัด)
- **CSS3 / ฟอนต์เว็บ** — หน้าตาเว็บสวย/ยืดหยุ่นขึ้นบนจอมือถือ

**ทำไมถึงสำคัญกับ Eclair โดยเฉพาะ**
- เป็นช่วงที่ Apple ผลักดัน "เว็บไม่ต้องพึ่ง Flash" การที่ Android รองรับ HTML5 ทำให้
  เว็บบนมือถือเล่นสื่อ/แอปเว็บได้โดยไม่ต้องรอ Flash
- ปูทางสู่ **web app / mobile web** และแนวคิด **hybrid app** (แอปที่ห่อหน้าเว็บด้วย
  `WebView`) ที่นิยมในยุคถัดมา

**ข้อจำกัดในตอนนั้น**
- การรองรับยัง **ไม่ครบทุกสเปก** และประสิทธิภาพ JavaScript ยังช้า (เพิ่งมาเร็วขึ้นชัดใน
  Froyo 2.2 ที่ใส่เอนจิน V8 + JIT)
- ความสามารถอย่าง `<video>`/codec ขึ้นกับฮาร์ดแวร์และ codec ที่เครื่องมี ทำให้เว็บ
  บางหน้าเล่นได้ไม่เหมือนกันทุกเครื่อง

> **ชัดเจนเรื่องเวอร์ชัน: 1.6 ลงไป "ไม่รองรับ HTML5" หรือไม่?**
> - **ไม่ใช่ว่าไม่รองรับเลย** — เบราว์เซอร์ Android ใช้เอนจิน **WebKit** มาตั้งแต่ 1.x
>   จึงรองรับความสามารถยุค HTML5 **บางส่วน** อยู่แล้ว (เช่น `<canvas>`, local storage
>   บางส่วน) แต่ยัง **จำกัดและไม่ครบ** + JavaScript ช้า
> - **Eclair (2.0/2.1)** คือการ **ยกระดับ/รองรับได้ดีและครบขึ้นอย่างมีนัยสำคัญ**
>   (เช่น `<video>`/`<audio>`, Geolocation, AppCache) จึงมักถูกจดจำว่าเป็นจุดที่
>   HTML5 บน Android "ใช้ได้จริง" — **ไม่ใช่จุดที่เพิ่งมีเป็นครั้งแรก**
> - HTML5 เพิ่งเป็น **มาตรฐานทางการปี 2014** ดังนั้นทุกเบราว์เซอร์ (รวมถึง Android)
>   รองรับแบบ **ค่อย ๆ เพิ่มทีละเวอร์ชัน** ไม่ใช่มี/ไม่มีแบบขาว-ดำ
> - สรุป: **1.6 ลงไป = รองรับบางส่วน/จำกัด**, **2.0–2.1 = ดีขึ้นชัดเจน**,
>   **2.2 Froyo = JavaScript เร็วขึ้นมาก**

### Android 2.2 Froyo (API 8, 2010)
- **ฟีเจอร์:** คอมไพเลอร์ **JIT** (เร็วขึ้นชัดเจน), เอนจิน JS V8, USB/Wi-Fi tethering, รองรับ Adobe Flash, ติดตั้งแอปบน SD
- **ข้อดี:** ประสิทธิภาพกระโดด, ฟีเจอร์เชื่อมต่อครบ
- **ข้อเสีย:** Flash กินทรัพยากร/แบตและเป็นแหล่งช่องโหว่ (ภายหลังเลิกไป)

**ขยายความ: "JIT" ใน Froyo คืออะไร**

**JIT = Just-In-Time compilation (การคอมไพล์แบบทันเวลา)** — กลไกที่แปลงโค้ดแอปเป็น
**ภาษาเครื่อง (native code) ระหว่างที่แอปกำลังรัน** เฉพาะส่วนที่ถูกเรียกบ่อย

**บริบท Android:**
- แอป Android คอมไพล์เป็น **bytecode** (`.dex`) แล้วรันบน **Dalvik VM**
- **ก่อน Froyo:** Dalvik ทำงานแบบ **ตีความ (interpret)** คือแปล bytecode เป็นคำสั่ง
  เครื่องทีละคำสั่ง **ทุกครั้ง** ที่รัน → ช้า
- **Froyo (2.2):** เพิ่ม **JIT** — เมื่อเจอโค้ดที่ถูกเรียกซ้ำบ่อย ("hot path") จะคอมไพล์
  เป็น native แล้ว **เก็บไว้ใช้ซ้ำ** ไม่ต้องแปลใหม่ทุกครั้ง → เร็วขึ้นชัดเจน (โดยเฉพาะงาน
  คำนวณหนัก)

**เทียบ 3 แนวทางให้เห็นภาพ:**

| แนวทาง | คอมไพล์เมื่อไร | ข้อดี | ข้อเสีย | ใช้ในยุค |
|--------|----------------|-------|---------|----------|
| Interpret | แปลทีละคำสั่งตอนรัน | เริ่มเร็ว, กินพื้นที่น้อย | รันช้า | ก่อน Froyo |
| **JIT** | แปลโค้ดที่ร้อนระหว่างรัน | รันเร็วขึ้น | ต้อง "อุ่นเครื่อง" + ใช้ RAM/CPU ช่วงแรก | Froyo (Dalvik) |
| AOT | แปลตั้งแต่ **ตอนติดตั้ง** | รันเร็วตั้งแต่แรก | ติดตั้งนาน, กินพื้นที่ | ART (KitKat preview → Lollipop) |

> ภายหลัง **ART** (ตั้งแต่ Lollipop) ใช้ **JIT + AOT ผสมกัน** และเพิ่ม
> **profile-guided compilation** (คอมไพล์เฉพาะส่วนที่ผู้ใช้ใช้จริง ตอนเครื่องว่าง/ชาร์จ)
> เพื่อให้ได้ทั้งความเร็วและเวลาติดตั้งที่สมเหตุผล

**ขยายความ: "เอนจิน JS V8" ใน Froyo คืออะไร**

**V8** คือ **JavaScript engine ของ Google** (เขียนด้วย C++) — ตัวเดียวกับที่ใช้ใน
เบราว์เซอร์ Chrome และภายหลังเป็นหัวใจของ Node.js หน้าที่ของมันคือ **ประมวลผลโค้ด
JavaScript ในหน้าเว็บ**

**บริบท Froyo:**
- เบราว์เซอร์ Android ก่อนหน้านี้รัน JavaScript ได้ช้า
- Froyo (2.2) เปลี่ยนมาใช้เอนจิน **V8** ทำให้เว็บที่มี JS หนัก ๆ (เช่น Gmail แบบเว็บ,
  เว็บแอป) **เร็วขึ้นหลายเท่า** — เข้ากับกระแส HTML5/เว็บแอปในยุคนั้นพอดี

**ทำไม V8 ถึงเร็ว:**
- ใช้ **JIT** คอมไพล์ JavaScript เป็น **ภาษาเครื่อง (native)** โดยตรง แทนการตีความ
  ทีละบรรทัด
- **Garbage collection** ที่มีประสิทธิภาพ
- เทคนิค **hidden classes / inline caching** เพื่อเข้าถึง property ของ object ได้เร็ว

**แยกให้ชัด: V8 vs Dalvik JIT (ทั้งคู่มาใน Froyo)**

| หัวข้อ | Dalvik JIT | V8 |
|--------|------------|-----|
| เร่งความเร็วของ | **โค้ดแอป Android** (จาก `.dex`) | **JavaScript ในเบราว์เซอร์** (หน้าเว็บ/เว็บแอป) |
| ทำงานที่ | ระบบรันแอป (Dalvik VM) | เบราว์เซอร์ |
| แนวคิดร่วม | ใช้ JIT เหมือนกัน แต่คนละบริบท/คนละตัว |  |

> พูดง่าย ๆ: **Dalvik JIT** ทำให้ "แอป" เร็วขึ้น ส่วน **V8** ทำให้ "เว็บ/JavaScript"
> เร็วขึ้น — Froyo ได้ทั้งสองอย่างพร้อมกัน จึงเป็นเวอร์ชันที่ประสิทธิภาพกระโดดชัด

**ขยายความ: "Adobe Flash" ใน Froyo ช่วยเรื่องอะไร**

**Adobe Flash** เป็นเทคโนโลยี/ปลั๊กอินสำหรับเล่น **วิดีโอ แอนิเมชัน เกม และเนื้อหา
โต้ตอบ** บนหน้าเว็บ ซึ่งในยุคนั้นมีอยู่เต็มอินเทอร์เน็ต การที่ Froyo รองรับ Flash Player
ในเบราว์เซอร์ทำให้มือถือ **เปิดเนื้อหาเหล่านั้นได้**

**ช่วยเรื่องอะไร (ยุคนั้น):**
- **ดูวิดีโอบนเว็บ** — เว็บวิดีโอ/เว็บข่าวจำนวนมากฝังด้วย Flash player
- **เล่นเกม/แอนิเมชันบนเว็บ** — เกม Flash, แบนเนอร์แอนิเมชัน, สื่ออินเทอร์แอกทีฟ
- **เว็บแอป/สื่อโต้ตอบ** — หลายเว็บทำ UI/มีเดียด้วย Flash
- **จุดขายการตลาด:** Android เคลมว่าให้ประสบการณ์ **"เว็บเต็มรูปแบบ (full web)"**
  ต่างจาก iPhone ที่ Apple ปฏิเสธ Flash มาตลอด

**ข้อเสีย (เหตุที่ภายหลังเลิกไป):**
- **กินแบต/CPU/RAM หนัก** ทำให้เครื่องร้อนและอืด
- **เป็นแหล่งช่องโหว่ความปลอดภัย** บ่อย
- ออกแบบมาเพื่อเมาส์/คลิก **ไม่เหมาะกับจอสัมผัส**

**บทสรุปเชิงประวัติ:**
- Flash บนมือถือถูกแทนที่ด้วย **HTML5** ที่เล่นวิดีโอ/แอนิเมชันได้ **ในตัว** โดยไม่ต้อง
  พึ่งปลั๊กอิน
- Adobe ประกาศ **เลิกพัฒนา Flash สำหรับมือถือในปี 2011** และ Flash ถูก **ยุติการ
  สนับสนุนทั้งหมดปลายปี 2020**
- ดังนั้นการรองรับ Flash ใน Froyo จึงเป็น **"จุดขายของยุคหนึ่ง"** ที่ต่อมากลายเป็น
  สิ่งล้าสมัย

**ขยายความ: "ติดตั้งแอปบน SD (App2SD)" คืออะไร**

**App2SD (Apps to SD)** คือความสามารถที่ Froyo เพิ่มมา เพื่อให้ **ย้าย/ติดตั้งแอป
บางส่วนไปเก็บบนการ์ด microSD** แทนที่จะกิน **หน่วยความจำภายใน** ของเครื่องอย่างเดียว

**ทำไมสำคัญในยุคนั้น:**
- มือถือยุค Froyo มี **หน่วยความจำภายในเล็กมาก** (บางรุ่นเหลือให้แอปแค่หลักร้อย MB)
  ติดตั้งแอปไม่กี่ตัวก็เต็ม → ขึ้นเตือน "พื้นที่เหลือน้อย"
- App2SD ช่วย **ขยายพื้นที่ติดตั้งแอป** ด้วยการ์ด SD ที่ถูกและเพิ่มได้

**การทำงาน / ข้อจำกัด:**
- นักพัฒนาต้อง **เปิดอนุญาต** ในแอป (ผ่านค่า `android:installLocation`) แอปถึงย้ายได้
  — ไม่ใช่ทุกแอปย้ายได้
- ย้ายเฉพาะ **บางส่วน** (โค้ด/ทรัพยากรหลัก) ส่วน **ข้อมูลส่วนตัว/ฐานข้อมูล/widget**
  ยังอยู่ในเครื่อง
- **ข้อเสีย:** widget บนหน้าโฮมใช้ไม่ได้ขณะแอปอยู่บน SD (และตอนต่อ USB/ถอดการ์ด),
  SD ช้ากว่าหน่วยความจำภายใน, และเป็น **ความเสี่ยงด้านความปลอดภัย** เพราะ SD ยุคแรก
  เป็นพื้นที่ที่เข้าถึงได้ง่ายกว่า

**บทสรุปเชิงประวัติ:**
- เป็นทางแก้ของยุคที่สตอเรจภายในน้อย เมื่อเครื่องรุ่นหลังมีพื้นที่ภายในใหญ่ขึ้น ความจำเป็น
  ก็ลดลง
- ภายหลัง Android เปลี่ยนแนวทางเป็น **Adoptable Storage** (ตั้งแต่ Android 6.0
  Marshmallow) ที่ "รับ" การ์ด SD มา **เข้ารหัสและผูกเป็นส่วนหนึ่งของสตอเรจภายใน** แทน

## ยุคเติบโต (2010–2013)

### Android 2.3 Gingerbread (API 9–10, 2010)
- **ฟีเจอร์:** ปรับ UI ให้เรียบขึ้น, รองรับ **NFC**, SIP (VoIP), จัดการพลังงาน/แอปดีขึ้น, รองรับกล้องหน้า
- **ข้อดี:** เสถียรและอยู่ยาว เป็นเวอร์ชันยอดนิยมหลายปี
- **ข้อเสีย:** ยังออกแบบมาเพื่อจอเล็กเป็นหลัก
- **ความปลอดภัย/ช่องโหว่:** ยุคนี้มีช่องโหว่ระดับ root หลายตัว (เช่นตระกูล GingerBreak) ที่ผู้ใช้ใช้ root และมัลแวร์อาจใช้ยกสิทธิ์ — สะท้อนว่า kernel/แอปพลิเคชันยังแข็งแรงน้อย

**ขยายความ: NFC และ SIP (VoIP) ใน Gingerbread**

**NFC (Near Field Communication)**
- การสื่อสารไร้สาย **ระยะใกล้มาก (~ไม่กี่เซนติเมตร)** โดยแตะอุปกรณ์เข้าใกล้กัน
- Gingerbread เป็นเวอร์ชันแรกที่ **รองรับ NFC ระดับระบบ** (เครื่องแรกคือ Nexus S)
- ใช้ทำอะไร: **อ่าน NFC tag** (สติกเกอร์/โปสเตอร์ที่ฝังข้อมูล), แลกข้อมูลแบบแตะ
- เป็น **รากฐาน** ที่ต่อมาต่อยอดเป็น **การจ่ายเงินแบบแตะ** (Google Wallet/Google Pay)
  และ Android Beam
- ยุค 2.3 ยังทำได้แค่ "อ่าน" เป็นหลัก ความสามารถเต็ม (จ่ายเงิน/card emulation) มา
  สมบูรณ์ในเวอร์ชันหลัง

**SIP (Session Initiation Protocol) — VoIP**
- **VoIP = Voice over IP** คือการ **โทรด้วยเสียงผ่านอินเทอร์เน็ต** แทนสัญญาณโทรศัพท์
  ปกติ (เครือข่ายมือถือ/GSM)
- **SIP** คือโปรโตคอลมาตรฐานที่ใช้ "เริ่ม/จัดการสาย" ของ VoIP
- Gingerbread เพิ่ม **SIP API ในตัว** ทำให้แอปโทรผ่านเน็ตได้ และบางรุ่นโทร SIP ได้จาก
  แอปโทรศัพท์มาตรฐานเลย
- **ประโยชน์:** โทรผ่าน Wi-Fi/เน็ตได้ (ประหยัดค่าโทร โดยเฉพาะระหว่างประเทศ) ผ่านผู้ให้
  บริการ SIP
- **ข้อจำกัด:** ต้องมีบัญชี/ผู้ให้บริการ SIP, คุณภาพขึ้นกับเน็ต, และผู้ให้บริการเครือข่าย
  บางรายเคยจำกัดการใช้งาน

> สรุป: **NFC** = แตะเพื่อสื่อสาร/อ่านแท็ก (ปูทางสู่การจ่ายเงินแบบแตะ) •
> **SIP/VoIP** = โทรด้วยเสียงผ่านอินเทอร์เน็ตด้วย API มาตรฐานในระบบ

**ขยายความ (เชิงการศึกษา/ป้องกัน): ช่องโหว่ยุค Gingerbread**

> หมายเหตุ: ส่วนนี้อธิบาย **ประเภทและสาเหตุ** ของช่องโหว่เพื่อการเรียนรู้และการป้องกัน
> **ไม่ได้ให้ขั้นตอน/โค้ดสำหรับโจมตี** ช่องโหว่ที่กล่าวถึงเป็นของเก่าและถูกแก้ไปแล้ว

**ประเภทช่องโหว่: Local Privilege Escalation (การยกระดับสิทธิ์ในเครื่อง)**
- ตัวอย่างเชิงประวัติ: ตระกูล **GingerBreak**, **zergRush** (ปี 2011)
- แนวคิดโดยรวม (ระดับสูง): โค้ด/แอปที่รันด้วย **สิทธิ์ผู้ใช้ธรรมดา** อาศัยจุดบกพร่องใน
  ส่วนประกอบ **native** หรือสิทธิ์ที่ตั้งไว้หลวม เพื่อ "ยกระดับ" ตัวเองขึ้นเป็น **root**
- คนทั่วไปยุคนั้นใช้เพื่อ **root เครื่องตัวเอง** แต่ในทางร้าย **มัลแวร์** ก็ใช้กลไกเดียวกัน
  เพื่อยึดเครื่องได้

**สาเหตุเชิงระบบที่ทำให้ยุคนั้นเปราะ**
- โค้ด native (C/C++) ตรวจสอบ **ขอบเขตหน่วยความจำ/อินพุต** ไม่รัดกุม → เกิด memory
  corruption ได้
- การ **แยกสิทธิ์ (sandbox/permission)** และการเสริมความแข็งแรงของ kernel ยังไม่เข้มเท่าปัจจุบัน
- ยังไม่มีมาตรการป้องกันสมัยใหม่แบบครบถ้วน

**ผลกระทบ**
- หากมัลแวร์ได้สิทธิ์ root จะ **ข้าม app sandbox** เข้าถึงข้อมูลของทุกแอปและทั้งระบบได้

**แนวทางป้องกัน / มาตรการที่เพิ่มในภายหลัง**
- **SELinux enforcing** (เริ่มจริงจังยุค 5.x), **verified boot**, **ASLR**, **seccomp**
- การ **แยกสิทธิ์และลดพื้นผิวการโจมตี** (เช่นแยก media server หลัง Stagefright)
- **แพตช์ความปลอดภัยรายเดือน** และ **Project Mainline** (อัปเดตบางส่วนผ่าน Play)
- ฝั่งผู้ใช้: ติดตั้งแอปจากแหล่งที่เชื่อถือได้, อัปเดตระบบ, หลีกเลี่ยงการ sideload ที่ไม่จำเป็น
- ฝั่งนักพัฒนา: ตรวจสอบอินพุต, ใช้ API ที่ปลอดภัย, ปฏิบัติตาม least-privilege

### Android 3.0–3.2 Honeycomb (API 11–13, 2011)
- **ฟีเจอร์:** ออกแบบ **เฉพาะแท็บเล็ต**, UI แบบ "holographic", System Bar, **Action Bar**, ใช้ **Fragment** เป็นครั้งแรก
- **ข้อดี:** วางรากฐาน UI สมัยใหม่ (Fragment/Action Bar ใช้ต่อยาว)
- **ข้อเสีย/จุดด้อย:** ปิด source (ไม่เปิด AOSP ช่วงนั้น), แยกจากเวอร์ชันโฟน ทำให้สับสน และเป็นเวอร์ชันที่ถูกมองว่า "ไม่สมบูรณ์"
- **ต่างจากก่อนหน้า:** เป็นสายแท็บเล็ตโดยเฉพาะ ก่อนถูกรวมกลับใน ICS

**ขยายความ: UI แบบ "holographic" (ธีม Holo) คืออะไร**

**Holo (Holographic UI)** คือ **ภาษาออกแบบ (design language) แรกอย่างเป็นทางการ
ของ Android** เปิดตัวพร้อม Honeycomb — **ไม่เกี่ยวกับภาพ 3 มิติ/โฮโลแกรมจริง** แต่เป็น
ชื่อสไตล์

**หน้าตา/ลักษณะเด่น:**
- โทน **มืด (dark)** เป็นหลัก พื้นหลังดำ/เทาเข้ม
- สีเน้น **ฟ้า-ไซแอน (cyan) เรืองแสง** ให้ความรู้สึกไฮเทค/ล้ำ
- เส้นคม เรขาคณิต แบน ลดการเลียนแบบวัสดุจริง (เริ่มออกจากสไตล์ skeuomorphic)
- มีเอฟเฟกต์เรืองแสง/ไล่เฉดบาง ๆ คล้าย "แสงโฮโลแกรม" — เป็นที่มาของชื่อ

**ความสำคัญเชิงเทคนิค (ไม่ใช่แค่หน้าตา):**
- เป็น **ธีมมาตรฐานของระบบครั้งแรก** ที่การันตีให้นักพัฒนาว่าวิดเจ็ต (ปุ่ม, list, spinner)
  หน้าตาสม่ำเสมอทุกเครื่อง แม้ผู้ผลิตจะปรับแต่ง UI (skin) เอง
- ช่วยลดปัญหา **fragmentation ด้านหน้าตา** — แอปที่ใช้ Holo ดูเหมือนกันข้ามอุปกรณ์
- มาคู่กับองค์ประกอบยุคใหม่: **Action Bar** และ **Fragment** (เหมาะกับ layout จอใหญ่)

**บริบท/วิวัฒนาการ:**
- Honeycomb เป็นเวอร์ชันเฉพาะแท็บเล็ต Holo จึงออกแบบให้เหมาะจอใหญ่ก่อน แล้วนำมาใช้
  กับโฟนใน **Ice Cream Sandwich (4.0)**
- Holo อยู่ยาวถึงยุค Jelly Bean/KitKat ก่อนถูกแทนด้วย **Material Design** ใน
  **Lollipop (5.0, 2014)** ที่เน้นสีสว่าง เงา และการเคลื่อนไหวแบบกระดาษ

**ขยายความ: "ปิด source (ไม่เปิด AOSP ช่วงนั้น)" หมายความว่าอย่างไร**

**AOSP คืออะไร**
- **AOSP = Android Open Source Project** คือซอร์สโค้ดของ Android ที่ Google เปิด
  เผยต่อสาธารณะภายใต้ไลเซนส์โอเพนซอร์ส (ส่วนใหญ่ Apache 2.0)
- ปกติเมื่อ Android เวอร์ชันใหม่ปล่อยเสถียร Google จะ **เผยแพร่ซอร์สลง AOSP** ให้ผู้ผลิต
  /นักพัฒนา/ชุมชน (เช่นทีมทำ custom ROM) นำไปใช้และดัดแปลงได้

**กรณี Honeycomb**
- Google **เลือกไม่ปล่อยซอร์สของ Honeycomb ลง AOSP** ในช่วงนั้น (ต่างจากเวอร์ชันอื่น)
- เหตุผลที่ให้ไว้: Honeycomb ถูกทำ **เร่งด่วนเพื่อแท็บเล็ตโดยเฉพาะ** และมีการลัดขั้นตอน
  บางอย่างเพื่อให้ทันคู่แข่ง จึง **ยังไม่พร้อม/ไม่เหมาะ** ให้เอาไปใช้กับอุปกรณ์ทั่วไป
  (โดยเฉพาะโทรศัพท์) กลัวผู้ผลิตนำไปใส่ในเครื่องที่ไม่เหมาะแล้วประสบการณ์เสีย

**ผลกระทบ / ทำไมถือเป็นข้อด้อย**
- **ขัดกับจิตวิญญาณโอเพนซอร์ส** ของ Android → ถูกวิจารณ์เรื่องความโปร่งใส
- **ชุมชน/ผู้ทำ custom ROM และผู้ผลิตรายเล็ก** เข้าถึงโค้ดไม่ได้ช่วงนั้น
- ตอกย้ำภาพว่า Honeycomb เป็นเวอร์ชัน **"ชั่วคราว/ไม่สมบูรณ์"**

**คลี่คลายอย่างไร**
- ซอร์สกลับมาเปิดเมื่อรวมเข้ากับ **Ice Cream Sandwich (4.0)** ที่รวมสายโฟน+แท็บเล็ต
  เป็น codebase เดียว แล้วปล่อยลง AOSP ตามปกติ หลังจากนั้นเวอร์ชันหลัก ๆ ก็กลับมา
  ปล่อย AOSP ต่อเนื่อง

**ขยายความ: "แยกจากเวอร์ชันโฟน" หมายความว่าอย่างไร**

ช่วงปี 2011 Android มี **2 สายพัฒนาที่แยกกันคนละทางในเวลาเดียวกัน**:

| อุปกรณ์ | เวอร์ชันที่ใช้ |
|---------|----------------|
| โทรศัพท์ | **2.3 Gingerbread** |
| แท็บเล็ต | **3.x Honeycomb** (เช่น Motorola Xoom) |

- Honeycomb ทำขึ้น **สำหรับแท็บเล็ตโดยเฉพาะ** — **ไม่ได้ออกแบบให้ลงโทรศัพท์** จึงเกิด
  สภาพ "2 เวอร์ชันคู่ขนาน" ที่หน้าตา/ความสามารถต่างกันมาก

**ทำไมเป็นข้อเสีย**
- **สับสนสำหรับผู้ใช้และนักพัฒนา** — ต้องคิดเผื่อว่าแอปจะรันบน 2.x (โฟน) หรือ 3.x
  (แท็บเล็ต)
- **นักพัฒนาต้องดูแล 2 แนวทาง** (UI จอเล็ก vs จอใหญ่) เพิ่มภาระ
- ระบบนิเวศ **แตกเป็นเสี่ยง (fragmentation)** ชั่วคราว

**คลี่คลายอย่างไร**
- **Ice Cream Sandwich (4.0)** รวมสองสายกลับเป็น **codebase เดียว** ใช้ระบบเดียว
  ทั้งโฟนและแท็บเล็ต (พร้อมธีม Holo และ **Fragment** ที่ช่วยปรับ layout ตามขนาดจอ)
- ตั้งแต่ ICS เป็นต้นมา ไม่มีการแยกสายโฟน/แท็บเล็ตอีก

### Android 4.0 Ice Cream Sandwich (API 14–15, 2011)
- **ฟีเจอร์:** **รวมโฟนและแท็บเล็ตเป็น codebase เดียว**, ธีม **Holo**, Face Unlock, ปุ่ม virtual, ตัวจัดการ data usage
- **ข้อดี:** ประสบการณ์เป็นอันหนึ่งอันเดียว, ดีไซน์ทันสมัยขึ้นมาก
- **ข้อเสีย:** Face Unlock ยุคแรกหลอกด้วยรูปถ่ายได้ (ความปลอดภัยต่ำ)

### Android 4.1–4.3 Jelly Bean (API 16–18, 2012–2013)
- **ฟีเจอร์:** **Project Butter** (UI ลื่น 60fps), Google Now, การแจ้งเตือนแบบขยาย/มี action, รองรับหลายผู้ใช้ (แท็บเล็ต), Bluetooth LE (4.3)
- **ข้อดี:** ความลื่นไหลดีขึ้นชัดเจน, ผู้ช่วยอัจฉริยะยุคแรก
- **ความปลอดภัย/ช่องโหว่:** ยุคนี้มีช่องโหว่ระดับแพลตฟอร์มสำคัญที่ถูกเปิดเผยปี 2013 เช่น **"Master Key" (bug 8219321)** ที่ทำให้ดัดแปลง APK โดยลายเซ็นยังผ่านการตรวจ และ **Fake ID** — กระตุ้นให้ Google ยกเครื่องการตรวจสอบลายเซ็น/แพ็กเกจ

**ขยายความ: "การแจ้งเตือนแบบขยาย" (Expandable / Rich Notifications) คืออะไร**

**ก่อน Jelly Bean (2.x–3.x):** การแจ้งเตือนเป็นแค่บรรทัดเล็ก ๆ (ไอคอน + หัวข้อ +
ข้อความสั้น) กดแล้ว **เปิดแอปอย่างเดียว**

**Jelly Bean เพิ่ม:**
- **ขยายดูได้ (expandable):** สไลด์เพื่อ **กางการแจ้งเตือนให้ใหญ่ขึ้น** เห็นรายละเอียดเพิ่ม
  - **BigTextStyle** — อ่านข้อความยาวได้เต็ม (อีเมล/ข้อความ) โดยไม่ต้องเปิดแอป
  - **BigPictureStyle** — โชว์รูปภาพขนาดใหญ่ในแจ้งเตือน
  - **InboxStyle** — แสดงเป็นรายการหลายบรรทัด (เช่น สรุปอีเมลหลายฉบับ)
- **ปุ่มลงมือ (action buttons):** ใส่ปุ่มในตัวแจ้งเตือน เช่น **โทรกลับ / เลื่อนเตือน
  (snooze)** ทำงานได้เลยจากแถบแจ้งเตือน

**ประโยชน์**
- ผู้ใช้ **จัดการงานได้เร็วขึ้น** โดยไม่ต้องเข้าแอป และเห็นบริบทครบขึ้น

**บริบทเชิงวิวัฒนาการ**
- เป็นรากฐานที่ต่อมาต่อยอดเป็น **direct reply (ตอบกลับในแจ้งเตือน, Nougat 7.0)**,
  **notification channels (Oreo 8.0)**, **bundled notifications** และ
  **Conversations/Bubbles (Android 11)**

> สรุป: เปลี่ยนการแจ้งเตือนจาก "แค่บอก" เป็น **"กางดูรายละเอียดได้ + ทำงานได้เลย"**

**ขยายความ: "Google Now" คืออะไร**

**Google Now** คือ **ผู้ช่วยอัจฉริยะ (intelligent personal assistant)** ของ Google
ที่เปิดตัวพร้อม Jelly Bean (4.1, ปี 2012) — เป็น **ต้นแบบก่อนกลายเป็น Google Assistant**

**จุดเด่น:**
- แสดงข้อมูลเป็น **"การ์ด (Now Cards)"** ที่ **เด้งขึ้นมาเองแบบเชิงรุก (proactive)**
  โดยผู้ใช้ไม่ต้องถาม เช่น สภาพอากาศตอนเช้า, จราจร/เวลาเดินทางไปที่ทำงาน, เที่ยวบิน/
  การจองที่ดึงจาก Gmail, ผลกีฬา, นัดหมายในปฏิทิน, สถานะพัสดุ
- **เรียนรู้จากบริบท** (ตำแหน่ง เวลา ประวัติค้นหา ข้อมูลบัญชี Google) แล้วคาดเดาว่าผู้ใช้
  อยากรู้อะไรตอนนั้น
- รองรับ **ค้นหาด้วยเสียง** และตอบกลับด้วยเสียง

**ต่างจาก Siri ยุคนั้น:** Siri เน้น **ถาม-ตอบ** (ผู้ใช้สั่งก่อน) ส่วน Google Now เน้น
**เชิงรุก** เอาข้อมูลที่คิดว่าจำเป็นมาแสดงเองตามบริบท

**วิวัฒนาการต่อมา:**
- 2015: **Now on Tap** (แตะค้างปุ่มโฮมเพื่อดึงข้อมูลจากสิ่งที่อยู่บนหน้าจอ)
- 2016: เปิดตัว **Google Assistant** (ทั้งเชิงรุกและสนทนาโต้ตอบ) ค่อย ๆ มาแทน Google Now
- ต่อมา Now Cards ถูกแทนด้วยฟีด **Google Discover**

## ยุคปรับสมดุลและดีไซน์ (2013–2016)

### Android 4.4 KitKat (API 19–20, 2013)
- **ฟีเจอร์:** ปรับให้ทำงานบนเครื่อง RAM ต่ำ (**512MB**) ได้ (Project Svelte), Immersive mode, ตัวอย่าง **ART runtime**, ระบบพิมพ์, โปร่งใส status/nav bar
- **ข้อดี:** ขยายตลาดเครื่องราคาถูก, UI สะอาดขึ้น
- **ข้อเสีย/ช่องโหว่:** เป็นหนึ่งในเวอร์ชันที่ได้รับผลจาก **Stagefright** (ดูด้านล่าง) และการตัดสิทธิ์เขียน SD card ภายนอกทำให้บางแอปมีปัญหา

**ขยายความ: "Immersive mode" คืออะไร**

**Immersive mode (โหมดเต็มจอแบบดื่มด่ำ)** คือความสามารถที่ KitKat เพิ่มมา เพื่อให้แอป
**ซ่อนทั้ง status bar (แถบบน) และ navigation bar (แถบปุ่มล่าง) พร้อมกัน** ทำให้เนื้อหา
แสดง **เต็มจอจริง ๆ**

**ทำไมสำคัญ:**
- ก่อนหน้านี้ซ่อนได้แค่บางส่วน หรือแตะจอนิดเดียวแถบก็เด้งกลับ → ดูหนัง/อ่านหนังสือ/
  เล่นเกม/ดูรูปไม่เต็มจอ
- Immersive mode ให้ **พื้นที่จอทั้งหมดกับเนื้อหา** เหมาะกับวิดีโอ เกม อีบุ๊ก แกลเลอรี

**มี 2 แบบหลัก:**
- **Immersive (ปกติ):** ซ่อนแถบทั้งหมด ผู้ใช้ **สไลด์จากขอบจอ** เพื่อเรียกแถบกลับมา
  ชั่วคราวแล้วมันซ่อนอีกครั้ง — เหมาะกับเกม/แอปที่แตะจอบ่อย
- **Immersive Sticky:** คล้ายกัน แต่แถบที่เรียกกลับมา **โปร่งแสงและซ่อนอัตโนมัติ** โดย
  ไม่ขัดจังหวะการแตะของแอป

**ต่างจากของเดิม:** โหมดเดิม ("lean back" / "low profile") ซ่อนได้ไม่สมบูรณ์หรือแตะแล้ว
เด้งกลับง่าย ส่วน Immersive ซ่อนได้จริงจังและควบคุมการเรียกกลับด้วย gesture

> **สำหรับนักพัฒนา:** เดิมเปิดผ่าน system UI flags (`SYSTEM_UI_FLAG_IMMERSIVE` /
> `IMMERSIVE_STICKY`) — ภายหลังถูกแทนด้วย **WindowInsetsController** ในเวอร์ชันใหม่

**ขยายความ: "ART runtime" คืออะไร**

**ART = Android Runtime** คือ **runtime ตัวใหม่ที่ใช้รันแอป** (เครื่องยนต์รัน bytecode
`.dex`) สร้างมาแทน **Dalvik** ของเดิม — KitKat ให้ลองใช้เป็น **ตัวเลือก (developer
option)** ก่อน แล้วเป็น **ค่าเริ่มต้นใน Lollipop (5.0)**

**Dalvik vs ART:**

| หัวข้อ | Dalvik (เดิม) | ART (ใหม่) |
|--------|---------------|------------|
| คอมไพล์เมื่อไร | **JIT** — แปลโค้ดที่ร้อน**ระหว่างรัน** | **AOT** — แปลเป็น native **ตอนติดตั้ง** |
| ความเร็วรัน | เริ่มช้ากว่า (ต้องอุ่นเครื่อง) | **รันเร็ว/ลื่นตั้งแต่แรก** |
| แบต/CPU | คอมไพล์ซ้ำ ๆ ขณะรัน | ลดภาระ CPU ขณะรัน → ประหยัดแบตกว่า |
| เวลาติดตั้ง | เร็ว | **ช้าลง** (ต้องคอมไพล์ตอนติดตั้ง) |
| พื้นที่จัดเก็บ | เล็กกว่า | **กินพื้นที่มากขึ้น** |

**ข้อดี:** แอปเปิดเร็ว/ลื่นขึ้น, ประหยัดแบต, garbage collection ดีขึ้น (ลดกระตุก)
**ข้อแลกเปลี่ยน:** ติดตั้ง/อัปเดตช้าลง และกินพื้นที่มากขึ้น

**วิวัฒนาการต่อมา:**
- ตั้งแต่ **Nougat (7.0)** ART ใช้ **JIT + AOT + profile-guided compilation ผสม** —
  ตอนติดตั้งไม่คอมไพล์ทั้งหมด (ติดตั้งเร็ว) แล้วค่อยคอมไพล์เฉพาะส่วนที่ใช้จริงตอนเครื่อง
  ว่าง/ชาร์จ ได้ทั้งความเร็วและประหยัดพื้นที่
- ปัจจุบัน ART อัปเดตได้ผ่าน **Google Play system update (Project Mainline)**

> เกี่ยวโยงกับ Froyo: Dalvik ใช้ **JIT**, ส่วน ART เปลี่ยนมาเน้น **AOT** (ดูตารางเทียบ
> Interpret/JIT/AOT ในหัวข้อ Froyo)

### Android 5.0–5.1 Lollipop (API 21–22, 2014–2015)
- **ฟีเจอร์:** **Material Design** (ภาษาออกแบบใหม่), **ART เป็น runtime หลัก** (AOT), รองรับ **64-bit**, Project Volta (แบต), การแจ้งเตือนบนหน้าล็อก, multiple users บนโฟน
- **ข้อดี:** ดีไซน์ยกระดับทั้งระบบ, ประสิทธิภาพ/แบตดีขึ้น
- **ข้อเสีย:** รุ่นแรก ๆ มีปัญหาหน่วยความจำรั่ว/เสถียรภาพ
- **ความปลอดภัย/ช่องโหว่:** **Stagefright (2015)** — ช่องโหว่ในไลบรารีถอดรหัสสื่อ กระทบ Android ตั้งแต่ 2.2 ถึง 5.1 เปิดทางโจมตีจากไฟล์มีเดีย/MMS เป็นเหตุการณ์ใหญ่ที่ทำให้ Google เริ่ม **แพตช์ความปลอดภัยรายเดือน** และแยก/แข็งแรง media server; Lollipop ยังบังคับ **SELinux enforcing** เต็มรูปแบบ

### Android 6.0 Marshmallow (API 23, 2015)
- **ฟีเจอร์:** **Runtime permissions** (ขออนุญาตตอนใช้งานจริง), **Doze** ประหยัดแบตขณะพัก, App Standby, **Fingerprint API** มาตรฐาน, รองรับ USB-C, Auto Backup
- **ข้อดี:** ก้าวสำคัญด้าน **ความเป็นส่วนตัว** (ผู้ใช้คุมสิทธิ์ได้ต่อรายการ)
- **ข้อเสีย:** แอปเก่าที่ไม่รองรับ runtime permission อาจทำงานผิด
- **ความปลอดภัย:** ปรับปรุงรากฐานสิทธิ์ + fingerprint ที่ปลอดภัยขึ้น

## ยุคโมดูลาร์และเสถียรภาพ (2016–2019)

### Android 7.0–7.1 Nougat (API 24–25, 2016)
- **ฟีเจอร์:** **Multi-window / split-screen**, การแจ้งเตือนแบบ bundled + ตอบตรง, JIT+AOT (ART ไฮบริด), **Vulkan API**, **File-Based Encryption (FBE)**, Data Saver
- **ข้อดี:** มัลติทาสก์จริงจัง, กราฟิกประสิทธิภาพสูง
- **ความปลอดภัย:** FBE + verified boot เข้มขึ้น, ปรับ media stack ให้ทนต่อช่องโหว่แบบ Stagefright

### Android 8.0–8.1 Oreo (API 26–27, 2017)
- **ฟีเจอร์:** **Project Treble** (แยก vendor layer ออกจาก framework → อัปเดตง่ายขึ้น), **Notification channels**, จำกัด background service, **Picture-in-Picture**, Autofill framework, Adaptive icons
- **ข้อดี:** Treble ช่วยลดปัญหาอัปเดตช้า, จัดการแจ้งเตือน/แบ็กกราวด์ดีขึ้น
- **ข้อเสีย:** ข้อจำกัด background ทำให้บางแอปเดิมต้องปรับตัว
- **ความปลอดภัย/ช่องโหว่:** ยุคนี้เจอ **KRACK** (ช่องโหว่โปรโตคอล WPA2 ระดับ Wi-Fi ไม่เฉพาะ Android) ที่ต้องแพตช์วงกว้าง; Treble ช่วยให้กระจายแพตช์ได้เร็วขึ้น

### Android 9 Pie (API 28, 2018)
- **ฟีเจอร์:** **Gesture navigation** (ยุคแรก), **Adaptive Battery/Brightness** (ใช้ ML), Digital Wellbeing, รองรับจอ notch, App Actions/Slices
- **ข้อดี:** ประหยัดแบตอัจฉริยะ, ใส่ใจสุขภาพการใช้งาน
- **ความปลอดภัย:** จำกัดการเข้าถึง sensor/กล้อง/ไมค์ของแอป background, บังคับ HTTPS (network security config), DNS over TLS

## ยุคความเป็นส่วนตัวเป็นศูนย์กลาง (2019–2023)

### Android 10 (API 29, 2019)
- **ฟีเจอร์:** เลิกใช้ชื่อขนมอย่างเป็นทางการ, **Dark theme** ทั้งระบบ, **Scoped Storage** (จำกัดการเข้าถึงไฟล์), gesture navigation เต็มรูปแบบ, **Project Mainline** (อัปเดตส่วนประกอบระบบผ่าน Play), รองรับ foldable, live caption

- **ข้อดี:** ควบคุมความเป็นส่วนตัวละเอียดขึ้น
- **ข้อเสีย:** การบังคับ scoped storage กระทบแอปจัดการไฟล์/สำรองข้อมูล

### Android 12 (API 31–32, 2021)
- **ฟีเจอร์:** **Material You / Dynamic Color** (ธีมสีจากภาพพื้นหลัง), **Privacy Dashboard**, ไฟบอกเมื่อแอปใช้ **กล้อง/ไมค์**, ปุ่มปิดกล้อง/ไมค์ทั้งระบบ, **approximate location**, ปรับปรุงการเริ่มแอป
- **ข้อดี:** ดีไซน์ปรับแต่งตัวเอง + โปร่งใสด้านความเป็นส่วนตัวชัดเจน
- **ข้อเสีย:** ธีมไดนามิกทำงานได้ดีสุดบน Pixel ก่อน (OEM อื่นตามมาทีหลัง)

### Android 13 (API 33, 2022)
- **ฟีเจอร์:** **ตั้งภาษาแยกรายแอป**, ต้องขออนุญาต **การแจ้งเตือน** (runtime), **Photo Picker** (เลือกรูปให้แอปโดยไม่เปิดคลังทั้งหมด), themed app icons, ปรับ clipboard/ความปลอดภัยคลิปบอร์ด
- **ข้อดี:** ผู้ใช้คุมการแจ้งเตือน/การเข้าถึงรูปได้ดีขึ้นมาก
- **ความปลอดภัย:** ลดการเข้าถึงคลังภาพทั้งก้อน → ลดความเสี่ยงข้อมูลรั่ว

## ยุคปัจจุบัน (2023–2026)

### Android 14 (API 34, 2023)
- **ฟีเจอร์:** **Predictive back** (พรีวิวก่อนย้อนกลับ), Health Connect, การเข้าถึงรูป/สื่อ "บางส่วน" (partial media access), ปรับ regional preferences, รองรับ passkeys, ปรับ accessibility (ขยายฟอนต์ 200%)
- **ข้อดี:** ความเป็นส่วนตัวของสื่อละเอียดขึ้น, UX ย้อนกลับดีขึ้น
- **ความปลอดภัย:** จำกัด install แอปที่ target API เก่ามาก (ลด malware ที่เลี่ยงกลไกใหม่)

### Android 15 (API 35, 2024)
- **ฟีเจอร์:** **Private Space** (พื้นที่ซ่อนแอป/ล็อกแยก), **partial screen sharing** (แชร์เฉพาะบางแอป), บังคับ **edge-to-edge**, ปรับปรุงดาวเทียม (satellite), เตรียมรองรับ **16 KB page size**, ปรับ predictive back เป็นค่าเริ่มต้นมากขึ้น
- **ข้อดี:** เพิ่มความเป็นส่วนตัว (ซ่อนแอปที่ละเอียดอ่อน), แชร์จอปลอดภัยขึ้น
- **ข้อเสีย:** การบังคับ edge-to-edge ทำให้แอปเก่าต้องปรับ layout

### Android 16 (API 36, 2025)
- **ฟีเจอร์:** **Material 3 Expressive** (ดีไซน์เน้นแอนิเมชัน/สี/เบลอมากขึ้น), การแจ้งเตือนแบบ **progress-centric / Live Updates**, **Advanced Protection Mode** (โหมดความปลอดภัยสูงรวมศูนย์), รองรับ **LE Audio / เครื่องช่วยฟัง** ดีขึ้น, **HDR screenshots**, predictive back เป็นค่าเริ่มต้น, ปรับปรุงจอใหญ่, รองรับ **16 KB page size**, **Generic Bootloader (GBL)**
- **ข้อดี:** ดีไซน์สดใหม่, ความปลอดภัยรวมศูนย์ (Advanced Protection), การเข้าถึง (เครื่องช่วยฟัง)
- **ข้อเสีย/จุดด้อย:** 16 KB page size ต้องให้แอป/ไลบรารี native คอมไพล์รองรับ (บางแอปเก่าต้องแก้)
- **ความปลอดภัย:** **Advanced Protection** รวมมาตรการกันภัยขั้นสูงไว้จุดเดียว
- **ความแตกต่างเชิงกระบวนการ:** เริ่มโมเดล **Trunk Stable** — ปล่อยต่อปีเป็น 2 รอบใหญ่ (ประมาณไตรมาส 2 และ 4) เพื่อความเสถียรของ ecosystem
_(เนื้อหาส่วนนี้เรียบเรียงใหม่จากแหล่งข่าว/เอกสารทางการเพื่อให้สอดคล้องกับข้อกำหนดลิขสิทธิ์)_

### Android 17 (API 37 คาดการณ์, codename "Cinnamon Bun", 2026)
- **ไทม์ไลน์:** เบต้าสาธารณะแรก ~13 ก.พ. 2026, ปล่อยตัวเสถียร ~16 มิ.ย. 2026 (เริ่มที่ Pixel)
- **ฟีเจอร์เด่น:**
  - **Adaptive-first:** บังคับให้แอป **ปรับขนาดบนจอใหญ่ (large-screen resizability)** — เน้น foldable/แท็บเล็ต/เดสก์ท็อปโหมด
  - **Floating Bubbles** และเครื่องมือมัลติทาสก์ใหม่
  - ปรับปรุง **การบันทึกหน้าจอ** และ **โหมดเกม** สำหรับ foldable
  - ความเป็นส่วนตัว: **ตำแหน่งแบบชั่วคราว (temporary location access)**
  - ความปลอดภัย: **ล็อกเครื่องเมื่อถูกขโมย (stolen device lock)** ที่แข็งแรงขึ้น
  - ทิศทางใหญ่: เริ่มเปลี่ยนเป็น **"intelligence system"** ที่วางแอปเป็นศูนย์กลาง (ผสาน AI มากขึ้น)
- **ข้อดี:** ประสบการณ์จอใหญ่/พับได้ดีขึ้นมาก, ความเป็นส่วนตัว/กันขโมยแข็งแรงขึ้น
- **ข้อเสีย/จุดด้อย:** การ **บังคับ resizability** ทำให้แอปที่ล็อกแนวตั้ง/ไม่รองรับจอใหญ่ต้องปรับ (ภาระฝั่งนักพัฒนา)
- **ความแตกต่างจาก 16:** จาก "ดีไซน์ใหม่ + ความปลอดภัยรวมศูนย์" (16) ไปเน้น **adaptive-first + AI-centric + กันขโมย** (17)
_(ข้อมูล Android 17 อ้างอิงแหล่งปี 2026 ด้านล่าง และเรียบเรียงใหม่เพื่อความถูกต้องตามลิขสิทธิ์ — บางรายละเอียด/หมายเลข API อาจปรับเพิ่มภายหลัง)_

## ประเด็นเชิงระบบที่เป็น "จุดด้อย" ต่อเนื่อง

- **Fragmentation:** อุปกรณ์หลากหลาย + OEM/ผู้ให้บริการปรับแต่งเอง ทำให้ **อัปเดตช้า/ไม่ทั่วถึง** เป็นปัญหาคลาสสิกของ Android
  - Google บรรเทาด้วย **Treble** (8.0) และ **Mainline** (10) เพื่อกระจายแพตช์บางส่วนผ่าน Play
- **ช่วงเปลี่ยนผ่านนโยบายความเป็นส่วนตัว** (เช่น Scoped Storage) สร้างภาระ/ความสับสนให้นักพัฒนาแอปเดิม
- **การรองรับฮาร์ดแวร์ใหม่** (เช่น 16 KB page size, จอพับ, adaptive) ต้องอาศัยความร่วมมือจากแอป/ไลบรารี native
- **ความปลอดภัยขึ้นกับการอัปเดต:** ช่องโหว่ที่แก้แล้วยังเสี่ยงในเครื่องที่ไม่ได้รับแพตช์ (โดยเฉพาะเครื่องเก่า/ราคาถูก)

## คู่มือสำหรับนักพัฒนา: min/target/compile SDK

ค่าที่ใช้ในไฟล์ Gradle (`android { ... }`) มี 3 ตัวหลักที่มักสับสน:

| ค่า | ความหมาย | ผลถ้าตั้งผิด |
|-----|----------|--------------|
| `minSdk` | เวอร์ชันต่ำสุดที่แอป **ติดตั้งและรันได้** | ตั้งต่ำ = ครอบคลุมเครื่องมากขึ้น แต่ต้องเขียนโค้ดเผื่อ API เก่า |
| `targetSdk` | เวอร์ชันที่แอป **ทดสอบแล้วว่ารองรับพฤติกรรมใหม่** | ตั้งต่ำ = ระบบเปิด compatibility behavior เก่าให้; Play มีเส้นตายบังคับให้ target ใหม่ |
| `compileSdk` | SDK ที่ใช้ **คอมไพล์** (เข้าถึง API ใหม่ล่าสุดตอนเขียนโค้ด) | ควร = เวอร์ชันล่าสุด ไม่กระทบ runtime โดยตรง |

> หลักการ: `minSdk ≤ targetSdk ≤ compileSdk` เสมอ

### ตารางเทียบ เวอร์ชัน ↔ API level (ใช้กรอกค่า SDK)

| Android | API level | ใช้เป็น `minSdk` เมื่อ | ใช้เป็น `target`/`compileSdk` เมื่อ |
|---------|-----------|------------------------|------------------------------------|
| 5.0 | 21 | ต้องการครอบคลุมเครื่องเก่ามาก (เลิกนิยมแล้ว) | — |
| 6.0 | 23 | รองรับ runtime permission ขึ้นไป | — |
| 7.0 / 7.1 | 24 / 25 | ฐานที่พบบ่อยสำหรับแอปที่ต้องการเครื่องเก่า | — |
| 8.0 / 8.1 | 26 / 27 | มี notification channels ขึ้นไป | — |
| 9 | 28 | — | — |
| 10 | 29 | เริ่มบังคับ scoped storage (target 29+) | — |
| 11 | 30 | ฐานที่นิยมในปี 2023–2024 | — |
| 12 / 12L | 31 / 32 | Material You ขึ้นไป | — |
| 13 | 33 | notification runtime permission | — |
| 14 | 34 | — | เคยเป็น target ขั้นต่ำของ Play ปี 2024 |
| 15 | 35 | — | target ขั้นต่ำของ Play สำหรับแอปใหม่ (ช่วงปี 2025) |
| 16 | 36 | — | **แนะนำเป็น `compileSdk`/`targetSdk` ปัจจุบัน** |
| 17 | 37 (คาดการณ์) | — | `compileSdk` ล่าสุดเมื่ออัปเกรด |

> **หมายเหตุ Play Store:** Google Play กำหนด "target API ขั้นต่ำ" สำหรับแอปที่จะ
> อัปโหลด/อัปเดต และเลื่อนขึ้นทุกปี (โดยทั่วไป = เวอร์ชันหลักของปีก่อนหน้า) แอปที่มีอยู่
> เดิมมักมีระยะผ่อนผัน ตรวจเส้นตายล่าสุดในหน้า Play Console เสมอ

### ตัวอย่างค่าตามโจทย์แอป

| โจทย์ | minSdk | targetSdk | compileSdk | เหตุผล |
|-------|--------|-----------|-----------|--------|
| ครอบคลุมกว้าง (แอปทั่วไป) | 24 | ล่าสุด (36/37) | ล่าสุด | สมดุลระหว่าง reach กับพฤติกรรมใหม่ |
| เน้นความปลอดภัย/องค์กร | 30–33 | ล่าสุด | ล่าสุด | ตัดเครื่องเก่าที่ไม่ได้แพตช์ |
| เกม/กราฟิกหนัก | 26–28 | ล่าสุด | ล่าสุด | ต้องการ Vulkan/behavior ใหม่ แต่ยังครอบคลุมพอ |
| โปรเจกต์นี้ (FoodOrder) | **24** | **34** | **34** | ตั้งไว้ในปัจจุบัน (ดู `app/build.gradle.kts`) |

> โปรเจกต์ตัวอย่างนี้ตั้ง `minSdk 24`, `targetSdk 34`, `compileSdk 34`
> การอัปเกรดให้ทันสมัยควรขยับ `compileSdk`/`targetSdk` เป็น 36 (Android 16) เป็นอย่างน้อย

### เช็กลิสต์เมื่ออัปเกรด targetSdk

1. อ่านหน้า **Behavior changes** ของเวอร์ชันเป้าหมายในเอกสารทางการ
2. ทดสอบเรื่อง **สิทธิ์ (permissions)** ที่เข้มขึ้น (ตำแหน่ง, การแจ้งเตือน, สื่อ)
3. ทดสอบ **background/foreground service** และการจัดการแบต (Doze)
4. ตรวจ **storage** (scoped storage) และการเข้าถึงไฟล์
5. ตรวจ UI เรื่อง **edge-to-edge / จอใหญ่ (resizability)** โดยเฉพาะ target 15+ และ 17
6. รัน unit tests + instrumented tests + ทดสอบบนอุปกรณ์จริง/emulator หลาย API

## ศัพท์ทางเทคนิค (Glossary)

รวมคำศัพท์ที่ปรากฏในเอกสารนี้ เรียงตามกลุ่ม เพื่อใช้อ้างอิงเร็ว ๆ

### Runtime & ประสิทธิภาพ
- **Dalvik VM** — runtime เดิมของ Android ที่รัน bytecode `.dex` (ใช้จนถึงก่อน ART)
- **ART (Android Runtime)** — runtime ใหม่แทน Dalvik เน้น AOT (ดูหัวข้อ KitKat)
- **Interpret** — แปล bytecode เป็นคำสั่งเครื่องทีละคำสั่งตอนรัน (ช้า)
- **JIT (Just-In-Time)** — คอมไพล์โค้ดที่ถูกเรียกบ่อยเป็น native **ระหว่างรัน**
- **AOT (Ahead-Of-Time)** — คอมไพล์เป็น native ล่วงหน้าตอนติดตั้ง → รันเร็ว
  (ดู "ขยายความศัพท์ทางเทคนิค")
- **Profile-guided compilation** — คอมไพล์เฉพาะส่วนที่ใช้จริง ตอนเครื่องว่าง/ชาร์จ
- **V8** — JavaScript engine ของ Google (ในเบราว์เซอร์/Chrome, Node.js)
- **Garbage collection (GC)** — การคืนหน่วยความจำที่ไม่ใช้แล้วอัตโนมัติ

### UI & ดีไซน์
- **Holo (Holographic UI)** — ภาษาออกแบบแรกของ Android (โทนมืด + ฟ้าไซแอน)
- **Material Design** — ภาษาออกแบบตั้งแต่ Lollipop (เงา/การเคลื่อนไหวแบบกระดาษ)
- **Material You / Dynamic Color** — ธีมสีปรับตามภาพพื้นหลัง (Android 12)
- **Immersive mode** — โหมดเต็มจอที่ซ่อน status/navigation bar
- **Action Bar** — แถบหัวแอปมาตรฐาน (มากับ Honeycomb)
- **Fragment** — ส่วนย่อยของ UI ที่นำมาประกอบ/ปรับ layout ตามขนาดจอ
- **Edge-to-edge** — วาดเนื้อหาเต็มจอถึงขอบ (บังคับตั้งแต่ Android 15)
- **Skeuomorphic** — ดีไซน์ที่เลียนแบบวัสดุจริง (แนวเก่าก่อน Holo/Material)
- **Bundled notifications** — รวมการแจ้งเตือนจากแอปเดียวกันเป็นกลุ่มเดียว กางดูได้
  (Nougat 7.0) (ดู "ขยายความศัพท์ทางเทคนิค")
- **Direct Reply** — พิมพ์ตอบข้อความจากในแจ้งเตือนได้เลยไม่ต้องเปิดแอป (Nougat 7.0)
- **PiP (Picture-in-Picture)** — เล่นวิดีโอในหน้าต่างลอยเล็ก ๆ ขณะใช้แอปอื่น (Oreo 8.0)
  (ดู "ขยายความศัพท์ทางเทคนิค")
- **Autofill Framework** — ระบบเติมฟอร์มอัตโนมัติระดับ OS (รหัสผ่าน/ที่อยู่/บัตร) (Oreo 8.0)
  (ดู "ขยายความศัพท์ทางเทคนิค")
- **Adaptive icons** — ไอคอนแอปที่แยกชั้น foreground/background ให้ระบบครอบเป็นทรง
  ต่าง ๆ ได้ (Oreo 8.0) (ดู "ขยายความศัพท์ทางเทคนิค")
- **Gesture navigation** — นำทางด้วยท่าทาง (ปัด) แทนปุ่ม 3 ปุ่ม (Pie 9.0, เต็มรูป Android 10)
- **Digital Wellbeing** — เครื่องมือดู/จำกัดเวลาใช้แอป เพื่อสุขภาพการใช้งาน (Pie 9.0)
- **Display cutout / notch** — API รองรับจอที่มีรอยบาก/เจาะ (Pie 9.0)
- **App Actions / Slices** — เสนอ action/แสดงเนื้อหาบางส่วนของแอปในที่อื่น เช่นผลค้นหา
  (Pie 9.0) (ดู "ขยายความศัพท์ทางเทคนิค")

### การเชื่อมต่อ & สื่อ
- **NFC (Near Field Communication)** — สื่อสารไร้สายระยะใกล้ (แตะ)
- **SIP / VoIP** — โทรด้วยเสียงผ่านอินเทอร์เน็ต (SIP = โปรโตคอลจัดการสาย)
- **SMS / MMS** — ข้อความผ่านเครือข่ายมือถือ: **SMS** = ตัวอักษรล้วน (สั้น) •
  **MMS** = แนบรูป/วิดีโอ/เสียงได้ (ต่อมาถูกแทนด้วยแอปแชตและ **RCS**)
- **Tethering** — แชร์เน็ตของมือถือให้อุปกรณ์อื่น (ผ่าน USB/Wi-Fi/Bluetooth)
- **Data Saver** — โหมดประหยัดเน็ตมือถือ จำกัดการใช้ดาต้าเบื้องหลังของแอป (Nougat 7.0)
  (ดู "ขยายความศัพท์ทางเทคนิค")
- **HTML5** — มาตรฐานเว็บที่เล่นวิดีโอ/แอนิเมชันได้ในตัว (ไม่ต้องพึ่งปลั๊กอิน)
- **WebKit** — เอนจินเรนเดอร์เว็บที่เบราว์เซอร์ Android ยุคแรกใช้
- **Adobe Flash** — ปลั๊กอินเล่นสื่อ/เกมบนเว็บยุคเก่า (ยุติปลายปี 2020)
- **Bluetooth LE** — บลูทูธพลังงานต่ำ (อุปกรณ์สวมใส่/เซ็นเซอร์)
- **Vulkan** — API กราฟิกระดับล่าง overhead ต่ำ (มากับ Nougat)
  (ดู "ขยายความศัพท์ทางเทคนิค")
- **OpenGL ES** — API กราฟิกดั้งเดิมของ Android (เขียนง่ายกว่า Vulkan)

### สถาปัตยกรรมระบบ & การอัปเดต
- **AOSP (Android Open Source Project)** — ซอร์สโค้ด Android ที่เปิดสาธารณะ
- **Project Treble** — แยก vendor layer ออกจาก framework → อัปเดตง่ายขึ้น (Oreo)
  (ดู "ขยายความศัพท์ทางเทคนิค")
- **Project Mainline** — อัปเดตส่วนประกอบระบบผ่าน Google Play (Android 10)
  (ดู "ขยายความศัพท์ทางเทคนิค")
- **API level** — หมายเลขระบุความสามารถแพลตฟอร์ม (ใช้ตั้ง min/target/compileSdk)
- **Fragmentation** — ความหลากหลายของอุปกรณ์/เวอร์ชันที่ทำให้อัปเดตยาก
- **App2SD / Adoptable Storage** — ย้ายแอปไป SD (App2SD) / ผูก SD เป็นสตอเรจภายใน (6.0)

### สิทธิ์ & ความเป็นส่วนตัว
- **App sandbox** — การแยกสิทธิ์แต่ละแอปด้วย Linux UID
- **Runtime permission** — ขออนุญาตตอนใช้งานจริง (Marshmallow)
- **Scoped Storage** — จำกัดการเข้าถึงไฟล์ของแอป (Android 10+)
  (ดู "ขยายความศัพท์ทางเทคนิค")
- **SavedStateHandle** — เก็บ state ให้รอด config change/process death
- **Auto Backup** — สำรองข้อมูลแอปขึ้น Google Drive และกู้คืนอัตโนมัติเมื่อย้าย/ติดตั้งใหม่
  (Marshmallow 6.0) (ดู "ขยายความศัพท์ทางเทคนิค")
- **Project Volta** — ชุดกลไก/เครื่องมือประหยัดแบตที่มากับ Lollipop (5.0)
  (ดู "ขยายความศัพท์ทางเทคนิค")
- **JobScheduler / WorkManager** — API จัดคิวงานเบื้องหลังอย่างประหยัดพลังงาน
  (WorkManager แนะนำในปัจจุบัน)
- **Doze** — โหมดประหยัดแบตระดับ **ทั้งเครื่อง** เมื่อวางนิ่ง/จอดับนาน
- **Background execution limits** — จำกัด service ที่รันเบื้องหลังของแอป (Oreo 8.0)
  (ดู "ขยายความศัพท์ทางเทคนิค")
- **Adaptive Battery / Adaptive Brightness** — ใช้ ML คาดเดาการใช้งานเพื่อประหยัดแบต/
  ปรับความสว่างอัตโนมัติ (Pie 9.0) (ดู "ขยายความศัพท์ทางเทคนิค")
- **App Standby** — จำกัดงานเบื้องหลัง/เน็ตของ **แอปที่ไม่ได้ใช้ (รายแอป)** เพื่อประหยัด
  แบต (คู่กับ Doze) (ดู "ขยายความศัพท์ทางเทคนิค")

### ความปลอดภัย
- **SELinux** — กลไกควบคุมการเข้าถึงระดับ kernel (enforcing เต็มรูปยุค 5.x)
  (ดู "ขยายความศัพท์ทางเทคนิค")
- **Verified boot** — ตรวจความถูกต้องของระบบตอนบูต
- **FBE (File-Based Encryption)** — เข้ารหัสข้อมูลแบบ **รายไฟล์** แยกโซน DE/CE รองรับ
  Direct Boot (Nougat 7.0) (ดู "ขยายความศัพท์ทางเทคนิค")
- **FDE (Full-Disk Encryption)** — เข้ารหัส **ทั้งพาร์ทิชัน** ด้วยกุญแจเดียว (แบบเดิมก่อน FBE)
- **ASLR** — สุ่มตำแหน่งหน่วยความจำเพื่อกันการโจมตี
- **seccomp** — จำกัด syscall ที่โปรเซสเรียกได้ (ลดพื้นผิวการโจมตี)
- **Privilege escalation** — การยกระดับสิทธิ์ (เช่นจากผู้ใช้ธรรมดาเป็น root)
- **Stagefright** — ช่องโหว่ไลบรารีถอดรหัสสื่อ (กระทบ 2.2–5.1)
- **KRACK** — ช่องโหว่โปรโตคอล **WPA2** (Wi-Fi) ปี 2017 กระทบหลายแพลตฟอร์ม
  (ดู "ขยายความศัพท์ทางเทคนิค")
- **Advanced Protection** — โหมดความปลอดภัยขั้นสูงรวมศูนย์ (Android 16)

## ขยายความศัพท์ทางเทคนิค

หัวข้อนี้เจาะลึกศัพท์บางตัวจาก Glossary ที่ต้องการคำอธิบายเพิ่มเติม

### Stagefright (ช่องโหว่ปี 2015)

> เนื้อหาเชิงข้อเท็จจริง/การศึกษาและการป้องกันเท่านั้น **ไม่มีขั้นตอนหรือโค้ดสำหรับโจมตี**
> ช่องโหว่นี้ถูกแก้ไปนานแล้ว

**Stagefright คืออะไร**
- ชื่อชุดช่องโหว่ความปลอดภัยขนาดใหญ่ที่เปิดเผยกลางปี 2015 พบใน **`libstagefright`**
  — ไลบรารี **ถอดรหัส/ประมวลผลไฟล์มีเดีย** ของ Android

**ทำไมร้ายแรง (เชิงแนวคิด)**
- ไลบรารีนี้ **แกะ/อ่านไฟล์วิดีโอ-เสียงอัตโนมัติ** (เช่นตอนรับ MMS, เปิดเว็บ, พรีวิวไฟล์)
- ช่องโหว่เป็นแบบ **memory corruption** ตอนประมวลผลไฟล์มีเดียที่ถูกดัดแปลง เปิดทางสู่
  **remote code execution (รันโค้ดจากระยะไกล)**
- บางกรณี **แทบไม่ต้องให้ผู้ใช้ทำอะไรเลย** (เครื่องประมวลผล MMS ที่เข้ามาโดยอัตโนมัติ)
  จึงถูกมองว่า "เงียบ" และอันตราย

**ขอบเขตผลกระทบ**
- กระทบเป็นวงกว้างมาก (ยุคนั้นประเมินระดับ **หลายร้อยล้าน–ราวพันล้านเครื่อง**)
- ครอบคลุมเวอร์ชัน **Android 2.2 ถึง 5.1** (จึงถูกกล่าวถึงในหัวข้อ Lollipop)
- มี CVE ที่เกี่ยวข้องหลายรายการ (เช่นชุด CVE-2015-1538 เป็นต้น)

**ผลสืบเนื่องสำคัญ (คุณค่าเชิงประวัติ)**
- Google เริ่ม **แพตช์ความปลอดภัยรายเดือน (Android Security Bulletin)** อย่างเป็น
  ทางการหลังเหตุการณ์นี้
- **แยก/แซนด์บ็อกซ์ media server** และจำกัดสิทธิ์กระบวนการถอดรหัสสื่อ เพื่อจำกัดความ
  เสียหายแม้ถูกเจาะ
- ผู้ผลิตรายใหญ่ (Samsung, LG ฯลฯ) ทยอยประกาศแพตช์รายเดือนตามมา

**การป้องกัน (ผู้ใช้/นักพัฒนา)**
- อัปเดตระบบ/แพตช์ความปลอดภัยสม่ำเสมอ
- (ยุคนั้น) ปิดการดาวน์โหลด MMS อัตโนมัติ
- ติดตั้งแอป/เปิดไฟล์จากแหล่งที่เชื่อถือได้

### AOT (Ahead-Of-Time compilation)

**AOT คืออะไร**
- คอมไพล์ bytecode (`.dex`) เป็น **ภาษาเครื่อง (native)** **ล่วงหน้าตั้งแต่ตอนติดตั้งแอป**
  แล้วเก็บผลไว้ (ไฟล์ `.oat`/`.odex`) ตอนรัน **ไม่ต้องแปลอีก**

**ข้อดี / ข้อเสีย**
- **ข้อดี:** แอปเปิด/รัน **เร็วและลื่นตั้งแต่ครั้งแรก**, ลดภาระ CPU ขณะรัน → ประหยัดแบต,
  ไม่มีช่วง "อุ่นเครื่อง" แบบ JIT
- **ข้อเสีย:** ติดตั้ง/อัปเดต **ช้าลง** (ต้องคอมไพล์ก่อน) และ **กินพื้นที่จัดเก็บมากขึ้น**

**เทียบกับแนวทางอื่น**
- ตรงข้ามกับ **JIT** (แปลระหว่างรัน) และ **Interpret** (แปลทีละคำสั่งตอนรัน)

**ในบริบท Android**
- ART (ตั้งแต่ KitKat/Lollipop) ใช้ AOT เป็นหลักช่วงแรก ต่อมา **Nougat (7.0)** เปลี่ยน
  เป็น **JIT + AOT + profile-guided** ผสม เพื่อให้ติดตั้งเร็ว แล้วค่อย AOT เฉพาะส่วนที่ใช้
  จริงตอนเครื่องว่าง/ชาร์จ
- นอก Android: แนวคิดนี้ยังพบใน Kotlin/Native, GraalVM native image, Flutter (release)

### Project Volta (Lollipop 5.0)

**Project Volta คืออะไร**
- ชุดความพยายาม **ปรับปรุงการใช้พลังงาน/แบตเตอรี่** ในระบบและแอป (คล้ายที่ Project
  Butter เน้นความลื่น Volta เน้นแบต)

**สิ่งที่นำมา**
- **JobScheduler** — จัดกลุ่มงานเบื้องหลังให้ระบบเลือกเวลารันที่เหมาะ (รอชาร์จ/Wi-Fi/
  เครื่องว่าง) แทนที่แต่ละแอปจะปลุกเครื่องเองบ่อย ๆ
- **Battery Saver mode** — โหมดประหยัดแบต (ลดความถี่ CPU, จำกัดงานเบื้องหลัง, ลด
  แอนิเมชัน) เมื่อแบตใกล้หมด
- **Battery Historian** — เครื่องมือนักพัฒนาไว้วิเคราะห์ว่าอะไรกินแบต (จาก bug report)

**วิวัฒนาการสายประหยัดแบตต่อมา**
- **Doze + App Standby** (6.0) → **Background limits** (8.0) → **Adaptive Battery**
  (9.0) → **WorkManager** (ปัจจุบัน สืบทอดแนวคิดจาก JobScheduler)

### SELinux (Security-Enhanced Linux)

**SELinux คืออะไร**
- กลไกความปลอดภัยระดับ **kernel** ที่ควบคุมว่า "โปรเซสไหนเข้าถึงอะไรได้บ้าง" ตาม
  **นโยบาย (policy) กลาง**

**MAC vs DAC**
- Linux ปกติใช้ **DAC (Discretionary Access Control)** — สิทธิ์ขึ้นกับเจ้าของไฟล์/ผู้ใช้
  (root ทำอะไรก็ได้)
- SELinux เพิ่ม **MAC (Mandatory Access Control)** ทับอีกชั้น — นโยบายกำหนดล่วงหน้า
  ว่าแต่ละโปรเซส (domain) แตะทรัพยากร (type) ใดได้ **แม้เป็น root ก็ถูกจำกัด**
- ผล: ถ้าโปรเซสถูกเจาะ ก็ **ทำได้แค่เท่าที่นโยบายอนุญาต** (least privilege)

**2 โหมดหลัก**
- **Permissive** — ตรวจและ **แค่บันทึก log** เมื่อละเมิด แต่ยังปล่อยให้ทำได้ (ช่วงทดสอบ/
  เก็บข้อมูลปรับนโยบาย)
- **Enforcing** — **บล็อกจริง** ทุกการกระทำที่ผิดนโยบาย

**ไทม์ไลน์บน Android**
- **4.3 Jelly Bean:** เริ่มใส่แบบ **permissive** (แค่ log)
- **4.4 KitKat:** เริ่ม **enforcing บางส่วน** (เฉพาะบาง domain)
- **5.0 Lollipop:** **enforcing เต็มรูปแบบ** ทั้งระบบ

**ทำไมสำคัญ**
- ต่อให้มัลแวร์/ช่องโหว่เจาะเข้าโปรเซสหนึ่งได้ SELinux enforcing จะ **กันไม่ให้ลุกลาม**
  เกินกว่าที่นโยบายกำหนด — ช่วยลดผลกระทบของช่องโหว่แบบ Stagefright/root exploit

### App Standby & Doze (การประหยัดแบต Marshmallow 6.0)

**App Standby คืออะไร**
- กลไกที่ **จำกัดการทำงานเบื้องหลังของแอปที่ "ไม่ได้ใช้งานมาสักพัก" เป็นรายตัว**
- ถ้าแอป **ไม่ถูกเปิด/ไม่มีการแจ้งเตือน/ไม่ได้อยู่เบื้องหน้า** สักระยะ ระบบจะจัดเป็น idle แล้ว:
  - จำกัดการเข้าถึง **เน็ตเวิร์ก** (ปล่อยเชื่อมต่อเป็นช่วง ๆ)
  - เลื่อน/จำกัด **งาน sync และ job** เบื้องหลัง

**ต่างจาก Doze (จำง่าย)**
- **Doze** = มองระดับ **"ทั้งเครื่อง"** — วางเครื่องนิ่ง จอดับ ไม่ได้ชาร์จ นาน ๆ ระบบพัก
  งานเบื้องหลัง/เน็ต/การปลุกทั้งระบบเป็นช่วง ๆ
- **App Standby** = มองระดับ **"รายแอป"** — แอปไหนไม่ถูกใช้ก็โดนจำกัดเฉพาะตัว แม้เครื่อง
  กำลังใช้งานอยู่

**ข้อยกเว้น**
- แอปจะไม่ถูกจัดเป็น idle ถ้าผู้ใช้เปิดใช้, มีการแจ้งเตือนที่มองเห็น, หรือถูกยกเว้น
- ข้อความเร่งด่วนใช้ **high-priority FCM (push)** เพื่อส่งถึงแม้แอปอยู่ standby

**วิวัฒนาการต่อมา**
- **Oreo (8.0):** background execution limits เข้มขึ้น
- **Pie (9.0):** **App Standby Buckets** — จัดแอปเป็นกลุ่ม (active / working set /
  frequent / rare / restricted) แล้วให้สิทธิ์เบื้องหลังต่างกันตามความถี่การใช้

### Auto Backup (Marshmallow 6.0)

**Auto Backup คืออะไร**
- สำรองข้อมูลของแอปขึ้น **Google Drive** ของผู้ใช้ **อัตโนมัติ** และ **กู้คืนกลับให้เอง**
  เมื่อผู้ใช้ติดตั้งแอปนั้นใหม่ (เปลี่ยนเครื่อง/ล้างเครื่อง)

**ทำงานอย่างไร**
- สำรองสูงสุด ~25 MB ต่อแอป (ยุคนั้น) ตอนเครื่อง **ชาร์จ + ต่อ Wi-Fi + ไม่ได้ใช้งาน**
  (ประมาณวันละครั้ง)
- ข้อมูล **ไม่นับโควตา Drive** และผู้ใช้มองไม่เห็นเป็นไฟล์ตรง ๆ
- ตอนติดตั้งแอปใหม่ ระบบ **กู้ข้อมูลกลับให้อัตโนมัติ** → ได้ค่าตั้งค่า/ข้อมูลกลับโดยไม่ต้อง
  ตั้งใหม่

**นักพัฒนาควบคุมได้**
- เปิด/ปิดผ่าน `android:allowBackup` (ค่าเริ่มต้นเปิด)
- กำหนดกฎ include/exclude ว่าจะสำรองไฟล์ไหน ผ่าน backup rules
  (`fullBackupContent` / ยุคใหม่ `dataExtractionRules`)

**ความปลอดภัย (สำคัญ)**
- ควร **ยกเว้นข้อมูลอ่อนไหว** (โทเคน, กุญแจ, ข้อมูลส่วนตัว) ออกจากการสำรอง เพราะอาจ
  ถูกกู้ไปเครื่องอื่น
- ยุคใหม่มี **end-to-end encryption** ของ backup (ผูกกับ PIN/รหัสเครื่อง)
- โปรเจกต์จริงมักตั้ง `allowBackup=false` หรือกำหนด rules ให้รอบคอบ
  (แอป FoodOrder ตัวอย่างตั้ง `allowBackup=true` เพราะไม่มีข้อมูลลับ)

**ต่างจากของเดิม**
- ก่อนหน้านี้มี Backup API แต่ต้องให้นักพัฒนา implement เอง; Auto Backup ให้การสำรอง
  อัตโนมัติโดยแทบไม่ต้องเขียนโค้ด

### Bundled Notifications & Direct Reply (Nougat 7.0)

**Bundled Notifications (จัดกลุ่ม)**
- **รวมการแจ้งเตือนหลายอันจากแอปเดียวกันเป็น "กลุ่มเดียว"** ในแถบแจ้งเตือน แทนที่จะ
  กระจายเต็มไปหมด
- เช่น อีเมลหลายฉบับจาก Gmail รวมเป็นกลุ่ม → **แตะเพื่อกาง (expand)** ดูทีละอันได้
- ประโยชน์: แถบแจ้งเตือน **สะอาด/ไม่รก**, ปัดทิ้งทั้งกลุ่มได้
- นักพัฒนา: ใช้ `setGroup()` + สร้าง "summary notification" ของกลุ่ม

**Direct Reply (ตอบตรง)**
- **ตอบกลับข้อความได้ทันทีจากในแจ้งเตือน** โดยไม่ต้องเปิดแอป — มีช่องพิมพ์ (inline)
  โผล่ในตัวแจ้งเตือน
- เหมาะกับแอปแชต/ข้อความ
- นักพัฒนา: ใช้ `RemoteInput` ผูกกับ action ของแจ้งเตือนเพื่อรับข้อความที่ผู้ใช้พิมพ์

**ต่อยอดจาก / ไปทางไหน**
- ต่อยอดจาก **การแจ้งเตือนแบบขยาย + action buttons** (Jelly Bean)
- ต่อมาเสริมด้วย **notification channels** (Oreo 8.0) และ **Conversations/Bubbles**
  (Android 11)

### Vulkan (API กราฟิก, Nougat 7.0)

**Vulkan คืออะไร**
- **API กราฟิก (และคอมพิวต์) ระดับล่าง (low-level)** จากกลุ่ม **Khronos** มาเสริม/ต่อยอด
  จาก **OpenGL ES** ที่ Android ใช้มาแต่เดิม

**ต่างจาก OpenGL ES อย่างไร**
- **เข้าถึง GPU ระดับล่างกว่า** — คุมทรัพยากร/หน่วยความจำ/คิวงาน GPU ได้ละเอียด
- **overhead ไดรเวอร์ต่ำ** — ลดภาระ CPU ในการสั่งงาน GPU → เฟรมเรตดี/สม่ำเสมอขึ้น
- **มัลติเธรดดี** — กระจายการสร้างคำสั่งกราฟิกไปหลายคอร์ CPU ได้ (OpenGL ES ทำได้จำกัด)

**ข้อแลกเปลี่ยน**
- **เขียนยากกว่า/โค้ดยาวกว่า** เพราะต้องจัดการรายละเอียดเองที่ OpenGL เคยทำให้
- เหมาะกับ **เกม/แอปกราฟิกหนัก หรือเอนจิน** (Unity, Unreal) มากกว่างานทั่วไป

**บริบท/วิวัฒนาการ**
- Nougat รองรับ **Vulkan 1.0** ครั้งแรกในระบบ (บนเครื่องที่ฮาร์ดแวร์/ไดรเวอร์รองรับ)
- ปัจจุบัน Android ผลักดัน Vulkan เป็น API หลัก และมี **ANGLE** (แปลง OpenGL ES ให้รัน
  บน Vulkan)
- เทียบข้ามแพลตฟอร์ม: อยู่กลุ่มเดียวกับ **Metal (Apple)** และ **DirectX 12 (Microsoft)**

### File-Based Encryption (FBE) vs FDE (Nougat 7.0)

**FBE คืออะไร**
- วิธี **เข้ารหัสข้อมูลในเครื่องแบบ "รายไฟล์"** — แต่ละไฟล์เข้ารหัสด้วยกุญแจของตัวเอง
  แทนการเข้ารหัสทั้งพาร์ทิชันเป็นก้อนเดียว

**เทียบกับ FDE (Full-Disk Encryption แบบเดิม)**
- **FDE:** เข้ารหัส **ทั้งพาร์ทิชัน** ด้วยกุญแจเดียว ต้อง **ปลดล็อกด้วยรหัสก่อน** ระบบถึงเข้า
  ถึงข้อมูลได้ → ก่อนปลดล็อกครั้งแรกเครื่องแทบทำอะไรไม่ได้
- **FBE:** เข้ารหัสรายไฟล์และแยกกุญแจตามบริบท → ปลดล็อกข้อมูลเป็นระดับได้

**จุดเด่น: Direct Boot (แบ่ง 2 โซน)**
- **Device Encrypted (DE):** เข้าถึงได้ตั้งแต่ **หลังบูตก่อนผู้ใช้ปลดล็อก** (ข้อมูลไม่อ่อนไหว)
- **Credential Encrypted (CE):** เข้าถึงได้ **หลังผู้ใช้ปลดล็อกด้วย PIN/รหัส** เท่านั้น
- ผล: ฟีเจอร์สำคัญทำงานได้ก่อนปลดล็อก เช่น **นาฬิกาปลุกดัง, รับสาย, การช่วยเหลือการ
  เข้าถึง, ข้อความสำคัญ**

**ประโยชน์**
- ปลอดภัย (ข้อมูลส่วนตัวยังเข้ารหัสจนกว่าจะปลดล็อก) + บูตเร็ว/ใช้งานพื้นฐานได้ทันที
- รองรับหลายผู้ใช้ดีขึ้น (แต่ละคนมีกุญแจ CE ของตัวเอง)

**สำหรับนักพัฒนา**
- ถ้าต้องการให้ component ทำงานช่วง Direct Boot ให้ประกาศเป็น `directBootAware` และ
  เก็บข้อมูลที่จำเป็นไว้ในที่จัดเก็บแบบ DE

### Data Saver (Nougat 7.0)

**Data Saver คืออะไร**
- โหมดที่ **ผู้ใช้เปิดเอง** เพื่อ **ลดการใช้เน็ตมือถือ (เซลลูลาร์)** โดยเฉพาะการใช้ดาต้า
  **เบื้องหลัง** ของแอป

**ทำงานอย่างไร**
- **บล็อก/จำกัดการใช้เน็ตมือถือของแอปที่ทำงานเบื้องหลัง** เป็นหลัก
- แอปที่อยู่ **เบื้องหน้า** ยังใช้เน็ตได้ แต่ระบบส่งสัญญาณให้ **ลดการใช้ดาต้า** (เช่น โหลด
  รูปความละเอียดต่ำ, เลื่อน prefetch)
- โดยทั่วไปมีผลกับ **เน็ตมือถือ** ไม่ใช่ Wi-Fi

**ผู้ใช้ควบคุมได้**
- ตั้ง **allowlist (ยกเว้น)** ให้บางแอปใช้เน็ตเบื้องหลังได้ตามปกติ (เช่นแอปแชต)

**สำหรับนักพัฒนา**
- ตรวจสถานะผ่าน `ConnectivityManager.getRestrictBackgroundStatus()`:
  **ENABLED** (เปิดและแอปไม่ได้ยกเว้น → ควรลดดาต้า), **WHITELISTED** (เปิดแต่แอปได้
  ยกเว้น), **DISABLED** (ไม่ได้เปิด)

**ต่างจาก App Standby/Doze**
- **Data Saver** = จำกัด **ปริมาณเน็ต** (ประหยัดค่าเน็ต/โควตา) โดย **ผู้ใช้เปิดเอง**
- **App Standby/Doze** = จำกัดงานเบื้องหลัง **เพื่อประหยัดแบต** โดย **ระบบตัดสินเอง**

### Project Treble (Oreo 8.0)

**Project Treble คืออะไร**
- การปรับสถาปัตยกรรม Android ครั้งใหญ่ เพื่อแก้ปัญหา **อัปเดตช้า/ไม่ทั่วถึง** โดย **แยก
  ส่วนระบบ Android (framework) ออกจากส่วนของผู้ผลิตชิป/ฮาร์ดแวร์ (vendor)** ให้ชัดเจน

**ปัญหาเดิม (ก่อน Treble)**
- โค้ดระบบ Android กับไดรเวอร์ของผู้ผลิตชิป (เช่น Qualcomm) **ผูกกันแน่น**
- ออกเวอร์ชันใหม่ → ผู้ผลิตชิปต้องแก้ไดรเวอร์ → ผู้ผลิตมือถือต้องรวมเข้า ROM → กว่าจะถึง
  ผู้ใช้ **นานมากหรือไม่ได้อัปเดตเลย**

**Treble ทำอะไร**
- คั่น 2 ชั้นด้วย **Vendor Interface (VINTF)** ที่เป็นสัญญา/มาตรฐานตายตัว:
  **Android OS framework** (Google อัปเดต) ↔ **Vendor implementation** (ไดรเวอร์/HAL
  ของผู้ผลิตชิป)
- ใช้ **HAL แบบใหม่ (HIDL → ต่อมา AIDL)** เป็นอินเทอร์เฟซมาตรฐานระหว่างสองชั้น
- ผล: อัปเดต framework ได้ **โดยไม่ต้องรอผู้ผลิตชิปแก้ vendor ใหม่ทุกครั้ง**

**ประโยชน์**
- อัปเดต OS/แพตช์ความปลอดภัย **เร็วและทั่วถึงขึ้น**
- เปิดทางให้ **GSI (Generic System Image)** — ภาพระบบ Android มาตรฐานที่รันบนเครื่อง
  Treble ได้ (ช่วยการทดสอบ/นักพัฒนา ROM)

**ต่อยอด**
- เป็นรากฐานให้ **Project Mainline** (Android 10) ที่อัปเดตส่วนประกอบระบบผ่าน Play

### PiP — Picture-in-Picture (Oreo 8.0)

**PiP คืออะไร**
- เล่นวิดีโอต่อใน **หน้าต่างลอยเล็ก ๆ** ที่ค้างอยู่หน้าจอ **ขณะที่ผู้ใช้ไปใช้แอปอื่น**
- (Android TV มี PiP มาตั้งแต่ Nougat; Oreo 8.0 นำมาสู่ **โทรศัพท์**)

**ใช้ทำอะไร**
- ดูวิดีโอ, **วิดีโอคอล**, หรือ **นำทางแผนที่** ต่อได้ระหว่างทำงานอื่น
- ลากย้ายตำแหน่ง/แตะเพื่อขยายกลับ, ปัดเพื่อปิด

**สำหรับนักพัฒนา**
- เข้าโหมดด้วย `enterPictureInPictureMode()` + กำหนดอัตราส่วน/ปุ่มลัดผ่าน
  `PictureInPictureParams`

### Autofill Framework (Oreo 8.0)

**Autofill คืออะไร**
- ระบบ **เติมข้อมูลในฟอร์มอัตโนมัติระดับ OS** เช่น ชื่อผู้ใช้/รหัสผ่าน, ที่อยู่, บัตรเครดิต
- ทำงานผ่าน **Autofill service** (เช่น Google Password Manager หรือแอปจัดการรหัสผ่านอื่น)
  ที่ผู้ใช้เลือกเป็นค่าเริ่มต้น

**ประโยชน์**
- กรอกฟอร์มเร็ว/แม่นขึ้น และ **ส่งเสริมการใช้ password manager** (ลดการตั้งรหัสซ้ำ)

**สำหรับนักพัฒนา**
- ช่วยให้ autofill แม่นขึ้นด้วย **`android:autofillHints`** (บอกประเภทช่อง เช่น
  `username`, `password`) และ **`importantForAutofill`**
- ช่องข้อมูลอ่อนไหวควรตั้งค่าให้เหมาะเพื่อความปลอดภัย

### Background execution limits (Oreo 8.0)

**คืออะไร**
- ข้อจำกัดที่ **หยุด/ลด service ที่แอปรันเบื้องหลัง** เมื่อแอปไม่ได้อยู่เบื้องหน้า เพื่อ
  ประหยัดแบต/RAM และลดการปลุกเครื่อง

**เปลี่ยนอะไร**
- แอปที่อยู่เบื้องหลัง **สร้าง background service ค้างไว้ไม่ได้แบบเดิม** (ระบบจะหยุดให้)
- ทางแก้ที่ถูกต้อง: ใช้ **`JobScheduler`/`WorkManager`** สำหรับงานที่เลื่อนได้ หรือใช้
  **foreground service** (มีการแจ้งเตือนถาวร) สำหรับงานที่ผู้ใช้ต้องเห็น
- มีข้อจำกัด **implicit broadcast** ด้วย (แอปรับ broadcast ทั่วไปผ่าน manifest ได้น้อยลง)

**ทำไมสำคัญ**
- เป็นก้าวสำคัญของสาย "จำกัดงานเบื้องหลัง" ต่อจาก Doze/App Standby → ต่อยอดสู่
  Adaptive Battery (9.0) และข้อจำกัด foreground service ที่เข้มขึ้นในเวอร์ชันหลัง

### Adaptive icons (Oreo 8.0)

**คืออะไร**
- ไอคอนแอปที่แยกเป็น **2 ชั้น: foreground + background** แล้วให้ระบบ/ผู้ผลิต **ครอบด้วย
  หน้ากาก (mask) เป็นทรงต่าง ๆ** (วงกลม, สี่เหลี่ยมมน, squircle) ให้เข้าธีมเครื่อง

**ประโยชน์**
- ไอคอนดู **สม่ำเสมอทั้งเครื่อง** แม้แต่ละแอปออกแบบมาต่างกัน + รองรับ **เอฟเฟกต์
  เคลื่อนไหว** (parallax/pulse) ตอนแตะ/ในลิ้นชักแอป

**สำหรับนักพัฒนา**
- ประกาศเป็น `<adaptive-icon>` (ใน `res/mipmap-anydpi-v26/`) โดยมี `<background>` และ
  `<foreground>` แยกกัน
- โยงกับโปรเจกต์นี้: แอป FoodOrder ใช้ adaptive icon (ดู
  `res/mipmap-anydpi-v26/ic_launcher.xml`) พร้อม fallback แบบ layer-list สำหรับ
  Android ก่อน 8.0

### KRACK (ช่องโหว่ WPA2 ปี 2017)

> เนื้อหาเชิงข้อเท็จจริง/การศึกษาและการป้องกันเท่านั้น **ไม่มีขั้นตอนหรือโค้ดสำหรับโจมตี**
> ช่องโหว่นี้ถูกแก้ด้วยแพตช์แล้ว

**KRACK คืออะไร**
- ย่อจาก **Key Reinstallation Attack** — ช่องโหว่ที่พบใน **โปรโตคอล WPA2** (มาตรฐาน
  เข้ารหัส Wi-Fi) ตรงขั้นตอน **4-way handshake** (ตอนอุปกรณ์กับเราเตอร์ตกลงกุญแจ)

**ทำไมสำคัญ (เชิงแนวคิด)**
- เป็นช่องโหว่ **ระดับโปรโตคอล ไม่ใช่เฉพาะ Android** จึงกระทบอุปกรณ์ Wi-Fi แทบทุก
  แพลตฟอร์ม (Android, iOS, Windows, Linux, อุปกรณ์ IoT)
- โดยหลักการ ผู้โจมตีที่อยู่ในระยะ Wi-Fi อาจ **ดักฟัง/รบกวนทราฟฟิก** ที่ควรถูกเข้ารหัสได้
  ในบางเงื่อนไข — จึงเป็นความเสี่ยงต่อความลับของข้อมูลบนเครือข่ายไร้สาย

**ผลกระทบกับ Android**
- Android ยุคนั้น (รวม Oreo) อยู่ในกลุ่มที่ได้รับผลและต้องรับ **แพตช์ความปลอดภัย**
- Project Treble (8.0) ช่วยให้กระจายแพตช์ได้เร็วขึ้น

**การป้องกัน**
- **อัปเดตแพตช์ความปลอดภัย** ทั้งอุปกรณ์และเราเตอร์
- ใช้ **HTTPS/TLS** และ **VPN** เพื่อเข้ารหัสอีกชั้น (แม้ Wi-Fi จะถูกเจาะก็ยังปลอดภัยขึ้น)
- ใช้ **WPA3** ที่ออกแบบมาให้ทนต่อการโจมตีประเภทนี้มากขึ้น

### ฟีเจอร์เด่นของ Android 9 Pie

**Gesture navigation (นำทางด้วยท่าทาง)**
- ใช้ **ท่าปัด** แทนปุ่ม 3 ปุ่มเดิม (Back/Home/Recents) — Pie เริ่มด้วยแบบผสม (มีปุ่มยาว
  ตรงกลาง) แล้ว **Android 10** ทำเป็นแบบปัดเต็มรูป
- ประโยชน์: ได้พื้นที่จอมากขึ้น, สอดคล้องกับจอไร้ขอบ

**Adaptive Battery / Adaptive Brightness**
- **Adaptive Battery** — ใช้ **machine learning** คาดเดาว่าผู้ใช้จะใช้แอปไหนต่อ แล้ว
  **จำกัดแบตของแอปที่ไม่ค่อยใช้** (ต่อยอดจาก Doze/App Standby/Buckets)
- **Adaptive Brightness** — เรียนรู้พฤติกรรมการปรับความสว่างของผู้ใช้ตามสภาพแสง แล้ว
  ปรับให้อัตโนมัติตามความชอบ

**Digital Wellbeing**
- ชุดเครื่องมือดู **เวลาที่ใช้แต่ละแอป (dashboard)**, ตั้ง **App Timer** (จำกัดเวลา/วัน),
  **Wind Down / Bedtime** (โหมดขาวดำก่อนนอน), และ **Do Not Disturb** ที่ดีขึ้น
- เป้าหมาย: ช่วยให้ผู้ใช้ **สมดุลการใช้มือถือ**

**Display cutout / notch**
- **API มาตรฐานรองรับจอที่มีรอยบาก/เจาะกล้อง (notch/punch-hole)** ให้แอปวาง UI เลี่ยง
  รอยบากได้ถูกต้อง (ผ่าน `DisplayCutout` / WindowInsets)
- เกิดขึ้นเพราะยุคนั้นมือถือเริ่มทำ **จอเต็มไร้ขอบ** ที่ต้องเจาะที่วางกล้องหน้า

**App Actions / Slices**
- **App Actions** — ให้ระบบ **เสนอการกระทำของแอป** ในบริบทที่เกี่ยวข้อง (เช่นใน
  ผลค้นหา, Assistant) เพื่อเข้าถึงฟังก์ชันแอปได้เร็ว
- **Slices** — แสดง **เนื้อหา/UI บางส่วนของแอปแบบโต้ตอบได้** ในพื้นที่อื่น (เช่น Google
  Search) โดยไม่ต้องเปิดแอปเต็ม

### Scoped Storage (Android 10)

**Scoped Storage คืออะไร**
- โมเดลการเข้าถึงไฟล์ที่ **จำกัดให้แต่ละแอปเห็น/เข้าถึงได้เฉพาะพื้นที่ของตัวเอง** และสื่อ
  บางประเภทเท่านั้น แทนที่จะอ่าน/เขียนพื้นที่จัดเก็บ **ทั้งเครื่อง** ได้อย่างอิสระ

**เปลี่ยนจากเดิมอย่างไร**
- เดิม: ขอ permission `READ/WRITE_EXTERNAL_STORAGE` แล้วเข้าถึงไฟล์ทุกที่ได้ → เสี่ยง
  ความเป็นส่วนตัว/ไฟล์รก
- ใหม่: แอปมี **app-specific directory** ของตัวเอง (ไม่ต้องขอสิทธิ์), เข้าถึงสื่อร่วม
  (รูป/วิดีโอ/เสียง) ผ่าน **MediaStore**, และเปิด/บันทึกไฟล์อื่นผ่าน **Storage Access
  Framework (SAF) / Photo Picker**

**ผลกระทบ**
- **ดีต่อความเป็นส่วนตัว** แต่ **นักพัฒนาต้องปรับโค้ดจัดการไฟล์** (ช่วงเปลี่ยนผ่านวุ่นวาย)
- Android 11 บังคับใช้เข้มขึ้น; แอปจัดการไฟล์จริง ๆ ขอสิทธิ์พิเศษ
  `MANAGE_EXTERNAL_STORAGE` (ต้องผ่านการตรวจของ Play)

### Project Mainline (Android 10)

**Project Mainline คืออะไร**
- กลไกที่ทำให้ **อัปเดตส่วนประกอบระบบบางตัวได้ผ่าน Google Play** (เป็นโมดูลชื่อ APEX/
  APK) **โดยไม่ต้องรออัปเดต OS เต็มก้อนจากผู้ผลิต**

**ทำไมสำคัญ**
- โมดูลสำคัญ (เช่น media codecs, ART runtime ในเวอร์ชันหลัง, ส่วนความปลอดภัย) ได้รับ
  **แพตช์เร็วและทั่วถึง** ตรงจาก Google → ลดปัญหา fragmentation ของแพตช์
- ต่อยอดจาก **Project Treble** (ที่แยก framework ออกจาก vendor)

**ต่างจาก Treble (จำง่าย)**
- **Treble** = แยกสถาปัตยกรรมให้ **อัปเดต OS** ง่ายขึ้น (ฝั่งผู้ผลิต)
- **Mainline** = **ส่งอัปเดตโมดูลระบบตรงผ่าน Play** (ฝั่ง Google) โดยไม่ต้องรอ OTA เต็ม

## สรุปแนวโน้ม

- **2008–2013:** สร้างรากฐาน + ไล่ตามคู่แข่ง (ฟีเจอร์/ประสิทธิภาพ)
- **2014–2018:** ดีไซน์ (Material) + โมดูลาร์ (Treble) + ประสิทธิภาพ (ART/Vulkan)
- **2019–2023:** **ความเป็นส่วนตัวเป็นศูนย์กลาง** + อัปเดตเร็วขึ้น (Mainline)
- **2024–2026:** **จอใหญ่/พับได้ (adaptive-first)** + **AI-centric** + ความปลอดภัยขั้นสูง/กันขโมย
