Secure Coding ใน Android (ฉบับสมบูรณ์)

เจาะลึกความปลอดภัย "เชิงการเขียนโค้ด" บน Android — ช่องโหว่ที่เกิดจากการเขียน โค้ดผิด และวิธีเขียนให้ปลอดภัย ครอบคลุม injection, WebView, Intent/deep link, IPC, secret management, logging, anti-tamper, dependency — พร้อมโค้ด ผิด vs ถูก ทุกหัวข้อ, checklist, และแนวโน้ม

เอกสารนี้เน้นมุม "แฮกเกอร์โจมตียังไง / เขียนโค้ดกันยังไง" — ต่างจาก android-permissions-security.html ที่เน้นระบบสิทธิ์และการป้องกันพื้นฐาน อ่านคู่กัน จะครบเรื่องความปลอดภัย
หมายเหตุด้านจริยธรรม: เนื้อหาอธิบายช่องโหว่เพื่อ "ป้องกัน" (defensive) เท่านั้น — ไม่ใช่คู่มือโจมตี

1. Secure coding คืออะไร

Secure coding คือการเขียนโค้ดที่ "ไม่เปิดช่องให้ถูกโจมตี" — ต่างจากการตั้งค่าความ ปลอดภัย (permission/HTTPS) ตรงที่ช่องโหว่เหล่านี้เกิดจาก วิธีเขียนโค้ด เอง เช่น รับ input โดยไม่ตรวจ, เปิด WebView ผิด, ส่ง Intent แบบไม่ระวัง

หลักคิด 3 ข้อ: (1) อย่าเชื่อ input ใด ๆ (จากผู้ใช้/แอปอื่น/network) • (2) least privilege (ให้สิทธิ์/เปิดฟีเจอร์เท่าที่จำเป็น) • (3) defense in depth (ป้องกันหลายชั้น ไม่พึ่งชั้นเดียว)

2. โมเดลภัยคุกคาม (attack surface บน Android)

รู้ว่า "ทางเข้า" ของการโจมตีมาจากไหน จะเขียนโค้ดกันได้ถูกจุด:

ทางเข้า (attack surface)ภัยที่เกิดตัวอย่างภัยจริง
Input จากผู้ใช้ (ช่องกรอก)injection, XSS (ใน WebView)ช่องค้นหาต่อ SQL เอง → ผู้ใช้พิมพ์ '; DROP TABLE user; -- ทำให้ตารางผู้ใช้หาย
Intent/deep link จากแอปอื่นintent redirection, task hijacking, ข้อมูลปลอมแอปร้ายส่ง intent ให้แอปเรา forward ต่อไปยังหน้า "ตั้งค่าบัญชี" ที่ปกติเข้าจากภายนอกไม่ได้ → เปลี่ยนอีเมล/รหัสเหยื่อ
ContentProvider/Service ที่ exportแอปอื่นเข้าถึงข้อมูล/สั่งงานProvider เก็บโน้ตตั้ง exported=true ไม่ใส่ permission → แอปอื่น query ดึงโน้ตทั้งหมดของผู้ใช้ออกไป
WebView โหลด URL/JS ภายนอกรันโค้ดอันตราย, ขโมยข้อมูลWebView เปิด JS + addJavascriptInterface โหลดหน้าโฆษณาภายนอก → JS ในโฆษณาเรียก bridge อ่าน token/ไฟล์ในเครื่อง
ไฟล์/ข้อมูลที่เก็บในเครื่องอ่านได้ถ้าเครื่อง root / backup รั่วเก็บ token เป็น plain text ใน SharedPreferences → เครื่อง root หรือ Auto Backup ขึ้น cloud แล้วถูกดึงไปสวมสิทธิ์
Networkman-in-the-middle, ดักข้อมูลใช้ HTTP บน WiFi สาธารณะ → ผู้โจมตีดักอ่าน/แก้ข้อมูลระหว่างทาง (เช่นแก้ยอดเงิน/ราคา)
Dependency (library)ช่องโหว่/โค้ดอันตรายจากภายนอกใช้ library เวอร์ชันเก่าที่มีช่องโหว่ (เช่น log4j-style) หรือ typosquatting ชื่อคล้าย → โค้ดอันตรายฝังมากับแอป
APK ที่ถูกถอด/ดัดแปลงอ่าน secret, ปลอมแอป, bypass logichardcode API secret ในโค้ด → ผู้โจมตี decompile APK อ่าน secret ไปเรียก API แทน; หรือ patch เช็ค "จ่ายเงินแล้ว" ให้ผ่านฟรี
Clipboard / หน้าจอข้อมูลลับรั่วผ่าน clipboard/screenshotcopy OTP/เลขบัตรลง clipboard → แอปอื่นอ่าน clipboard ได้; หรือหน้าจอ OTP ถูก screen-record ด้วยมัลแวร์
ทุกภัยข้างบนมีวิธีป้องกันในหัวข้อถัด ๆ ไป (แต่ละหัวข้อมีโค้ด ❌ ผิด vs ✅ ถูก)

3. Input validation & Injection

3.1 SQL Injection

Room ใช้ parameterized query ให้อยู่แล้ว แต่ raw query ที่ต่อ string เอง ยังเสี่ยง:

// ❌ ผิด — ต่อ string ตรง ๆ → SQL injection
@RawQuery
fun search(query: SupportSQLiteQuery): List<User>
// เรียก: search(SimpleSQLiteQuery("SELECT * FROM user WHERE name = '$input'"))
// ถ้า input = "'; DROP TABLE user; --" → หายนะ
// ✅ ถูก — ใช้ parameter binding (Room escape ให้)
@Query("SELECT * FROM user WHERE name = :name")
fun search(name: String): List<User>

// ถ้าจำเป็นต้อง raw → ใส่ค่าเป็น bind args ไม่ใช่ต่อ string
SimpleSQLiteQuery("SELECT * FROM user WHERE name = ?", arrayOf(input))

3.2 Path Traversal

// ❌ ผิด — เอาชื่อไฟล์จาก input มาต่อ path ตรง ๆ
val file = File(baseDir, userInput)   // input = "../../databases/app.db" → หลุดออกนอก dir
// ✅ ถูก — ตรวจว่า path ที่ resolve แล้วยังอยู่ใน baseDir
val file = File(baseDir, userInput).canonicalFile
if (!file.path.startsWith(baseDir.canonicalPath)) throw SecurityException("path ไม่ถูกต้อง")

3.3 หลักการ validate input ทั่วไป

  • allowlist ดีกว่า denylist — ระบุ "อะไรที่อนุญาต" ดีกว่าไล่บล็อกทีละอย่าง
  • ตรวจ ชนิด/ความยาว/รูปแบบ (regex) ของ input ทุกทางเข้า
  • อย่าเชื่อข้อมูลจาก client — ตรวจซ้ำที่ server ด้วย (ถ้ามี backend)
  • encode/escape ก่อนนำไปแสดง (โดยเฉพาะใน WebView)

4. WebView Security

WebView เป็นจุดเสี่ยงสูงสุดจุดหนึ่ง — ถ้าโหลดเนื้อหาที่ควบคุมไม่ได้ + เปิด JS/interface ผิด อาจถูกรันโค้ดอันตราย/ขโมยข้อมูล

// ❌ ผิด — เปิดทุกอย่างแล้วโหลด URL ที่ไม่ควบคุม
webView.settings.javaScriptEnabled = true
webView.settings.allowFileAccess = true
webView.addJavascriptInterface(MyJsBridge(), "Android")   // เว็บเรียก native ได้!
webView.loadUrl(untrustedUrl)
// ✅ ถูก — เปิดเท่าที่จำเป็น + คุม URL
webView.settings.apply {
    javaScriptEnabled = false            // เปิดเฉพาะเมื่อจำเป็นจริง
    allowFileAccess = false              // กันอ่านไฟล์ในเครื่อง
    allowContentAccess = false
    javaScriptCanOpenWindowsAutomatically = false
}
// จำกัดให้โหลดได้เฉพาะ domain ของเรา
webView.webViewClient = object : WebViewClient() {
    override fun shouldOverrideUrlLoading(v: WebView, r: WebResourceRequest): Boolean {
        val host = r.url.host ?: return true
        return !host.endsWith("example.com")   // นอก domain = บล็อก
    }
}
addJavascriptInterface อันตรายมาก — ถ้าจำเป็นต้องใช้ ให้เปิดเฉพาะกับ เนื้อหาที่เราควบคุม 100%, ใช้ @JavascriptInterface เฉพาะเมธอดที่ตั้งใจ, และอย่าให้ เข้าถึงข้อมูลอ่อนไหว • หลีกเลี่ยงการโหลด untrusted URL ใน WebView ที่เปิด JS

4.1 ค่าดีฟอลต์ของ WebSettings (ถ้าไม่ตั้งอะไรเลย)

ค่าดีฟอลต์ค่อนข้างปลอดภัยในหลายเรื่อง แต่มีบางอันที่เปิดช่องได้ + บางอัน ต่างกันตามเวอร์ชัน:

settingค่าดีฟอลต์ปลอดภัย?
javaScriptEnabledfalse✅ (ต้องเปิดเอง)
addJavascriptInterfaceไม่มี (ต้องเรียกเอง)✅
allowFileAccesstrue (API ≤29) / false (API 30+)⚠️ ต่างตามเวอร์ชัน
allowContentAccesstrue⚠️ เข้าถึง content:// ได้
allowFileAccessFromFileURLsfalse✅
allowUniversalAccessFromFileURLsfalse✅
domStorageEnabledfalse✅
databaseEnabledfalse✅
mixedContentModeNEVER_ALLOW (API 21+)✅ บล็อก HTTP ในหน้า HTTPS
geolocationEnabledtrue⚠️ (แต่ยังต้องมี permission จริง)
จุดที่พลาดบ่อย — allowFileAccess ต่างตามเวอร์ชัน: API 29 (Android 10) ลงไปดีฟอลต์เป็น true (WebView อ่านไฟล์ file:// ในเครื่องได้) แต่ API 30+ เป็น false → ควรตั้ง false เองให้ชัดเพื่อพฤติกรรมเหมือนกันทุกเวอร์ชัน
สรุป: ไม่ตั้งอะไรเลย = ปลอดภัยพอสำหรับแสดง HTML ธรรมดา (JS ปิด, ไม่มี JS interface, mixed content บล็อก) • แต่ช่องโหว่ส่วนใหญ่เกิดจากที่นักพัฒนา เปิดเพิ่มเอง (javaScriptEnabled/addJavascriptInterface) • หลัก explicit ดีกว่า implicit — ตั้งค่า ความปลอดภัยชัดเจนเอง อย่าพึ่งดีฟอลต์ที่เปลี่ยนตามเวอร์ชัน

4.2 สิ่งที่ควรตั้ง "ทุกครั้ง" ที่ใช้ WebView

ไม่มี setting ไหนที่ "ต้องตั้งแบบตายตัว" — ขึ้นกับว่าโหลดอะไร แต่แบ่งเป็น 3 กลุ่มตาม ความจำเป็นได้ชัดเจน:

กลุ่ม 1 — ควรตั้งทุกครั้ง (กันดีฟอลต์ต่างเวอร์ชัน + explicit)

webView.settings.apply {
    allowFileAccess = false                    // ดีฟอลต์ต่างตามเวอร์ชัน → ตั้งเองให้ชัด
    allowContentAccess = false                 // ดีฟอลต์ true → ปิดถ้าไม่ใช้ content://
    allowFileAccessFromFileURLs = false
    allowUniversalAccessFromFileURLs = false   // กัน file:// อ่านข้าม origin
}

เหตุผล: explicit ดีกว่า implicit — ไม่ปล่อยให้พฤติกรรมขึ้นกับดีฟอลต์ที่เปลี่ยนตาม เวอร์ชัน (โดยเฉพาะ allowFileAccess) • ปิดการเข้าถึงไฟล์/content ที่ WebView ส่วนใหญ่ไม่ได้ใช้อยู่แล้ว

กลุ่ม 2 — ต้องมีเมื่อโหลด content ภายนอก (สำคัญสุดด้านความปลอดภัย)

// จำกัดให้โหลดได้เฉพาะ domain ของเรา — กันถูกพาไปหน้าอันตราย
webView.webViewClient = object : WebViewClient() {
    override fun shouldOverrideUrlLoading(v: WebView, r: WebResourceRequest): Boolean {
        val host = r.url.host ?: return true
        return !host.endsWith("example.com")   // นอก domain = บล็อก (return true = ไม่โหลด)
    }
}

เหตุผล: เป็นด่านกันการ redirect ไปหน้าอันตราย/ฟิชชิง — สำคัญกว่าการตั้ง flag เฉย ๆ เพราะควบคุม "โหลดอะไรได้บ้าง"

กลุ่ม 3 — ตั้งเฉพาะเมื่อจำเป็น (และต้องระวังเป็นพิเศษ)

settingเปิดเมื่อข้อควรระวัง
javaScriptEnabled = trueหน้าเว็บต้องใช้ JSเปิดเฉพาะกับ content ที่ควบคุมได้ + คู่กับกลุ่ม 2
domStorageEnabled = trueเว็บใช้ localStorageข้อมูลถูกเก็บในเครื่อง
addJavascriptInterface()ต้องให้ JS เรียก nativeอันตรายสุด — เฉพาะ content ที่เราคุม 100% + @JavascriptInterface

เทมเพลต WebView ที่ปลอดภัย (ใช้เป็นจุดตั้งต้น)

fun setupSecureWebView(webView: WebView, allowedHost: String) {
    webView.settings.apply {
        // กลุ่ม 1: ปิดการเข้าถึงไฟล์/content เสมอ
        allowFileAccess = false
        allowContentAccess = false
        allowFileAccessFromFileURLs = false
        allowUniversalAccessFromFileURLs = false
        // เปิด JS เฉพาะถ้าจำเป็น (กลุ่ม 3) — ตัวอย่างนี้เปิดเพราะสมมติว่าต้องใช้
        javaScriptEnabled = true
    }
    // กลุ่ม 2: จำกัด domain
    webView.webViewClient = object : WebViewClient() {
        override fun shouldOverrideUrlLoading(v: WebView, r: WebResourceRequest) =
            r.url.host?.endsWith(allowedHost) != true
    }
    // ไม่เรียก addJavascriptInterface เว้นแต่จำเป็นจริง
}
สรุปสั้น: ทุกครั้งให้ตั้ง กลุ่ม 1 (ปิด file/content access) + ถ้า โหลด URL ให้ทำ กลุ่ม 2 (จำกัด domain) • กลุ่ม 3 เปิดเท่าที่จำเป็นและระวัง addJavascriptInterface เป็นพิเศษ

5. Intent Security

5.1 Implicit intent รั่วข้อมูล → ใช้ explicit

// ❌ ผิด — implicit intent ส่งข้อมูลอ่อนไหว แอปอื่นอาจดักรับ
val intent = Intent("com.example.ACTION_PROCESS")
intent.putExtra("token", secretToken)
sendBroadcast(intent)   // ทุกแอปที่ลง filter นี้รับได้
// ✅ ถูก — explicit intent ระบุปลายทางชัด
val intent = Intent(this, ProcessService::class.java)
intent.putExtra("token", secretToken)
startService(intent)

5.2 Intent Redirection (อันตรายที่มือใหม่พลาด)

// ❌ ผิด — เอา Intent ที่รับมาจากภายนอก ไป startActivity ต่อ (redirection)
val forwarded = intent.getParcelableExtra<Intent>("next")
startActivity(forwarded)   // แอปร้ายส่ง intent ชี้ไป component ภายในที่ไม่ export → เข้าถึงได้
// ✅ ถูก — ตรวจ/จำกัดปลายทางก่อน หรือไม่ forward intent จากภายนอกเลย
val forwarded = intent.getParcelableExtra<Intent>("next")
if (forwarded?.component?.packageName == packageName &&
    forwarded.component?.className in allowedTargets) {
    startActivity(forwarded)
}

5.3 ตรวจข้อมูลที่รับจาก Intent เสมอ

// ✅ validate extra ทุกตัวก่อนใช้ (อาจเป็น null/ค่าปลอม)
val amount = intent.getIntExtra("amount", -1)
if (amount <= 0) { finish(); return }   // ค่าไม่ถูกต้อง = ปฏิเสธ

6. Deep link & App Links security

  • ตรวจ parameter ของ deep link เสมอ — myapp://order/{id} ค่า id อาจ เป็นอะไรก็ได้ → validate ก่อนใช้
  • App Links (verified) — ผูก domain กับแอปด้วย assetlinks.json เพื่อกัน แอปอื่นแอบอ้างเปิด link ของคุณ (link hijacking)
  • อย่าทำงานอ่อนไหวจาก deep link ตรง ๆ — เช่นห้ามโอนเงิน/ลบข้อมูลจากการเปิด link โดยไม่ยืนยันตัวตน
// ❌ ผิด — เชื่อ deep link แล้วทำงานอ่อนไหวเลย
val id = intent.data?.getQueryParameter("orderId")
deleteOrder(id!!)   // ใครส่ง link มาก็ลบได้
// ✅ ถูก — validate + ต้องผ่าน auth ก่อนทำงานอ่อนไหว
val id = intent.data?.getQueryParameter("orderId")
if (id.isNullOrBlank() || !id.matches(Regex("^[0-9]+$"))) return
if (!session.isLoggedIn) { navigateToLogin(); return }
showOrderConfirm(id)   // ให้ผู้ใช้ยืนยันก่อน ไม่ทำเลย

7. IPC / Broadcast / ContentProvider security

  • exported=false ถ้าไม่ต้องการให้แอปอื่นเรียก (component ทุกชนิด)
  • ถ้าต้อง export → กำหนด permission ป้องกัน + ตรวจผู้เรียก
  • Broadcast อ่อนไหว → ใช้ explicit หรือกำหนด permission; ภายในแอปใช้ LocalBroadcast/Flow
  • ContentProvider → ตั้ง android:grantUriPermissions/permission, ใช้ parameterized selection กัน injection
<!-- ContentProvider ให้เฉพาะแอปที่มี permission -->
<provider
    android:name=".MyProvider"
    android:authorities="com.example.provider"
    android:exported="true"
    android:readPermission="com.example.permission.READ_DATA" />
// ตรวจสิทธิ์ผู้เรียกใน bound service (IPC)
override fun onTransact(...) {
    if (checkCallingPermission("com.example.permission.USE")
        != PackageManager.PERMISSION_GRANTED) throw SecurityException()
}

8. PendingIntent security

PendingIntent คือ "การมอบสิทธิ์ให้แอปอื่นทำงานแทนเรา" — ถ้าตั้งค่าผิดแอปอื่นอาจแก้ไส้ในได้

// ❌ ผิด — mutable + implicit intent → แอปอื่นแก้ปลายทางได้
PendingIntent.getActivity(this, 0, Intent("SOME_ACTION"), PendingIntent.FLAG_MUTABLE)
// ✅ ถูก — IMMUTABLE + explicit intent (Android 12+ บังคับระบุ mutability)
PendingIntent.getActivity(
    this, 0,
    Intent(this, DetailActivity::class.java),
    PendingIntent.FLAG_IMMUTABLE or PendingIntent.FLAG_UPDATE_CURRENT
)
ใช้ FLAG_IMMUTABLE เสมอ เว้นแต่จำเป็นต้อง mutable จริง ๆ (เช่นใช้กับ inline reply/bubble) แล้วต้องใช้ explicit intent เท่านั้น

9. Secret & API key management

ความจริงที่ต้องยอมรับ: อะไรที่ฝังใน APK ถอดออกมาอ่านได้เสมอ (decompile) — obfuscation แค่ทำให้ยากขึ้น ไม่ใช่ปลอดภัย • secret ที่สำคัญจริงต้องอยู่ฝั่ง server
ระดับความลับเก็บที่ไหน
secret สำคัญมาก (payment key, admin)backend เท่านั้น — แอปเรียกผ่าน API
token ของผู้ใช้ (หลัง login)EncryptedSharedPreferences / Keystore
API key ที่จำกัดสิทธิ์ได้ (เช่น Maps)ฝังได้ แต่ต้อง restrict ด้วย package+SHA-1 ใน console
config ไม่ลับBuildConfig / resource
// ❌ ผิด — hardcode secret ในโค้ด
const val API_SECRET = "sk_live_abc123..."   // ถอด APK เจอทันที
// ✅ ถูก — secret อยู่ backend, แอปแลก token ชั่วคราวมาใช้
// หรือถ้าจำเป็นต้องมี key ในแอป → restrict + rotate ได้
// เก็บ token ผู้ใช้แบบเข้ารหัส:
securePrefs.edit().putString("access_token", token).apply()
อย่า commit secret ลง git — ใช้ local.properties/env vars + .gitignore; ถ้าเผลอ commit ไปแล้ว ให้ถือว่า secret นั้นรั่วและ rotate ทันที

10. การเก็บข้อมูล & Backup

  • ข้อมูลลับ → EncryptedSharedPreferences / SQLCipher (ไม่ใช่ plain text)
  • อย่าเก็บข้อมูลอ่อนไหวใน external storage (แอปอื่นอาจอ่านได้ในเวอร์ชันเก่า)
  • Auto Backup อาจ backup ข้อมูลลับขึ้น cloud → กำหนด exclude rules
<!-- Android 12+: res/xml/data_extraction_rules.xml -->
<data-extraction-rules>
    <cloud-backup>
        <exclude domain="sharedpref" path="secure_prefs.xml" />  <!-- ไม่ backup token -->
    </cloud-backup>
</data-extraction-rules>

<!-- ผูกใน AndroidManifest -->
<application android:dataExtractionRules="@xml/data_extraction_rules" ... />

11. Logging & debuggable ใน production

// ❌ ผิด — log ข้อมูลอ่อนไหว (อ่านได้ผ่าน Logcat / adb)
Log.d("Auth", "token = $accessToken, password = $password")
// ✅ ถูก — ไม่ log ข้อมูลลับ + ปิด log ใน release
if (BuildConfig.DEBUG) Log.d("Auth", "login success")   // ไม่มี token
// หรือใช้ Timber ที่ตัด log อัตโนมัติใน release
  • android:debuggable — ต้องเป็น false ใน release (build type release ตั้งให้อยู่แล้ว อย่า override เป็น true)
  • ปิด/ลด logging ใน production (ใช้ Timber + plant tree เฉพาะ debug)
  • เปิด minify/R8 ใน release (obfuscate + ลบโค้ดที่ไม่ใช้ + strip log ได้)
// build.gradle.kts
buildTypes {
    release {
        isMinifyEnabled = true          // R8: obfuscate + shrink
        isDebuggable = false
        proguardFiles(getDefaultProguardFile("proguard-android-optimize.txt"), "proguard-rules.pro")
    }
}

12. Anti-tampering / root detection

สำหรับแอปที่อ่อนไหว (การเงิน) ควรตรวจว่าแอป/เครื่องไม่ถูกดัดแปลง — แต่ ไม่มีอะไรกันได้ 100% เป็นการเพิ่มความยากเท่านั้น

  • Play Integrity API — ตรวจว่าแอปเป็นตัวจริงจาก Play + เครื่องน่าเชื่อถือ (แทน SafetyNet เดิม)
  • ตรวจ debug/emulator/root — เป็น signal เสริม (bypass ได้ ไม่ควรพึ่งอย่างเดียว)
  • ตรวจ signature ของแอป — กันการ repackage (ปลอมแอป)
// แนวคิด Play Integrity (เรียกผ่าน backend เพื่อ verify)
val integrityManager = IntegrityManagerFactory.create(context)
val token = integrityManager.requestIntegrityToken(
    IntegrityTokenRequest.builder().setNonce(nonce).build()
)
// ส่ง token ไป verify ที่ backend (อย่า verify ในแอป — bypass ได้)
การ verify ควรทำ ฝั่ง server เสมอ — ถ้า verify ในแอปอย่างเดียว ผู้โจมตี patch โค้ดข้ามได้

13. Dependency / Supply chain security

  • ใช้ library ที่น่าเชื่อถือ + ดูแลต่อเนื่อง — เช็คว่ามีคน maintain, ดาวน์โหลดเยอะ
  • ปักหมุดเวอร์ชัน (pin) — ไม่ใช้ +/range เพื่อกันดึงเวอร์ชันอันตรายมาเงียบ ๆ
  • ระวัง typosquatting — ชื่อ library คล้ายของจริง (เช่นสะกดผิด 1 ตัว)
  • สแกนช่องโหว่ — ใช้ dependency scanning (เช่น OWASP Dependency-Check, GitHub Dependabot)
  • ตรวจ permission ที่ library ขอ — library ไม่ควรขอสิทธิ์เกินหน้าที่
// ✅ ปักเวอร์ชันชัดเจน (ไม่ใช้ + หรือ latest)
implementation("com.squareup.retrofit2:retrofit:2.11.0")   // ไม่ใช่ 2.+

14. อื่น ๆ (clipboard / screenshot / keyboard)

  • Clipboard — อย่า copy ข้อมูลลับลง clipboard (แอปอื่นอ่านได้); Android 13+ auto-clear แต่ก็ควรเลี่ยง
  • Screenshot/screen recording — หน้าจอที่มีข้อมูลลับ (OTP, บัตร) ใช้ FLAG_SECURE
  • Keyboard cache — ช่องรหัสผ่านตั้ง inputType เป็น password (กันจำ/แนะนำคำ)
// ป้องกัน screenshot/บันทึกหน้าจอในหน้าที่มีข้อมูลลับ
window.setFlags(WindowManager.LayoutParams.FLAG_SECURE,
                WindowManager.LayoutParams.FLAG_SECURE)

16. แนวโน้มในอนาคต

  • Play Integrity แทน SafetyNet — เป็นมาตรฐานตรวจความน่าเชื่อถือ
  • Passkeys / passwordless — ลดความเสี่ยงจากรหัสผ่าน (Credential Manager)
  • R8/obfuscation + resource shrinking ฉลาดขึ้น
  • Supply chain security เข้มขึ้น — SBOM, dependency scanning เป็น mainstream
  • platform บังคับ secure defaults มากขึ้น — cleartext ปิด, exported บังคับระบุ, PendingIntent บังคับ mutability, scoped storage
  • สรุป: ทิศทางคือ "ปลอดภัยโดยดีฟอลต์ (secure by default)" + verify ฝั่ง server + privacy-first — เขียนโค้ดตามหลักในเอกสารนี้จะสอดคล้องกับทิศทางนี้

17. ศัพท์ทางเทคนิค (Glossary)

  • Secure coding — การเขียนโค้ดที่ไม่เปิดช่องให้ถูกโจมตี
  • Attack surface — จุดที่ผู้โจมตีเข้าถึง/โจมตีได้
  • Injection — แทรกคำสั่งอันตรายผ่าน input (SQL/command)
  • Path traversal — หลุดออกนอกโฟลเดอร์ที่ควรด้วย ../
  • Intent redirection — ถูกหลอกให้ forward intent ไป component ภายใน
  • Task hijacking — แอปร้ายแทรกตัวใน task ของแอปเรา
  • App Links — deep link ที่ verify domain (assetlinks.json)
  • PendingIntent / FLAG_IMMUTABLE — การมอบสิทธิ์ทำงานแทน / ห้ามแก้ไส้ใน
  • EncryptedSharedPreferences — เก็บ key-value แบบเข้ารหัส
  • R8 / ProGuard — obfuscate + shrink โค้ด (ไม่ใช่การเข้ารหัส)
  • Play Integrity API — ตรวจความน่าเชื่อถือของแอป/เครื่อง
  • Certificate pinning — ผูก cert ของ server กัน MITM
  • FLAG_SECURE — กัน screenshot/บันทึกหน้าจอ
  • Supply chain security — ความปลอดภัยของ dependency/library ที่ใช้
  • Defense in depth — ป้องกันหลายชั้น ไม่พึ่งชั้นเดียว
  • Least privilege — ให้สิทธิ์น้อยสุดเท่าที่จำเป็น
