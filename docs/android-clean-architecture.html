Clean Architecture ใน Android (ฉบับสมบูรณ์)

อธิบาย Clean Architecture (ของ Robert C. Martin) และการนำมาใช้บน Android แบบ ครบถ้วน — Dependency Rule, 4 ชั้น, การแมปลงโครง Android, โค้ดตัวอย่าง, ข้อดี/ข้อเสีย, การเปรียบเทียบกับ "สถาปัตยกรรมที่ Google แนะนำ", การเลือกใช้ และแนวโน้ม อ่านจบแล้วนำไปวาง โครงโปรเจกต์จริงได้

สรุปสั้นสุด: Clean Architecture คือการแบ่งโค้ดเป็นวงกลมซ้อนกัน โดย business logic (Entities/Use Cases) อยู่วงในสุด และไม่รู้จัก framework/UI/DB เลย • กฎเดียวที่สำคัญสุดคือ Dependency Rule: dependency ชี้เข้าด้านในเสมอ • ผลคือ logic ทดสอบง่าย และเปลี่ยน UI/DB/network ได้โดยไม่กระทบแกนธุรกิจ

1. Clean Architecture คืออะไร

Clean Architecture เป็นแนวคิดของ Robert C. Martin ("Uncle Bob") ที่เสนอวิธีจัดโครง โค้ดให้ business logic เป็นอิสระจาก framework, UI, database และปัจจัยภายนอก

เป้าหมายหลัก:

  • Independent of frameworks — logic ไม่ผูกกับ Android/Retrofit/Room
  • Testable — เทสต์ business logic ได้โดยไม่ต้องมี UI/DB/network
  • Independent of UI — เปลี่ยน UI (View → Compose) โดยไม่แตะ logic
  • Independent of database — เปลี่ยน Room → SQLDelight โดยไม่แตะ logic
Clean Architecture เป็น หลักการทั่วไป ใช้ได้ทุกแพลตฟอร์ม (backend/web/ mobile) — เอกสารนี้เน้นการนำมาปรับใช้บน Android

2. Dependency Rule (หัวใจของทั้งหมด)

กฎเดียวที่สำคัญที่สุด: "dependency (การพึ่งพา) ต้องชี้เข้าด้านในเสมอ"

┌────────────────────────────────────┐ │ Frameworks & Drivers (นอกสุด) │ UI, Room, Retrofit │ ┌──────────────────────────────┐ │ │ │ Interface Adapters │ │ ViewModel, Repository impl │ │ ┌──────────────────────┐ │ │ │ │ │ Use Cases │ │ │ business rules ของแอป │ │ │ ┌──────────────┐ │ │ │ │ │ │ │ Entities │ │ │ │ business models หลัก │ │ │ └──────────────┘ │ │ │ │ │ └──────────────────────┘ │ │ │ └──────────────────────────────┘ │ └────────────────────────────────────┘ dependency ชี้ ────► เข้าด้านใน
  • ชั้นในไม่รู้จักชั้นนอก — Entities/Use Cases ไม่ import อะไรจาก Android/UI/DB
  • ชั้นนอกรู้จักชั้นใน — UI/Repository เรียกใช้ Use Cases/Entities ได้
  • เมื่อชั้นในต้องคุยชั้นนอก → ใช้ interface (abstraction) ที่นิยามไว้ในชั้นใน แล้วชั้นนอกมา implement (Dependency Inversion)
ผิดกฎที่พบบ่อย: Use Case หรือ Entity import android.* หรือ Retrofit/Cursor — ถ้าเจอแบบนี้แปลว่า dependency ชี้ออกนอก ผิดหลัก Clean Architecture

3. สี่ชั้น (วงกลมซ้อนกัน)

ชั้น (วง)หน้าที่รู้จักอะไร
Entities (ในสุด)business models + กฎธุรกิจหลักที่ไม่เปลี่ยนตามแอปไม่รู้จักใครเลย (pure Kotlin)
Use Casesbusiness rules เฉพาะแอป (application logic)รู้จัก Entities
Interface Adaptersแปลงข้อมูลระหว่างชั้นใน↔นอก (ViewModel, Repository, Mapper)รู้จัก Use Cases + Entities
Frameworks & Drivers (นอกสุด)ของจริง: UI, DB, network, Android SDKรู้จักทุกชั้นใน

4. Entities (แกนธุรกิจ)

โมเดล + กฎธุรกิจหลักที่ เป็นจริงเสมอไม่ว่าแอปจะเป็นแบบไหน — เป็น pure Kotlin ไม่มี dependency กับ Android/framework ใด ๆ

// pure Kotlin — ไม่มี import android.* หรือ library ภายนอก
data class Cart(val items: List<CartItem>) {
    val total: BigDecimal
        get() = items.sumOf { it.price * it.quantity.toBigDecimal() }

    fun isEmpty(): Boolean = items.isEmpty()

    // กฎธุรกิจหลัก: สั่งได้เมื่อยอดขั้นต่ำ 100 บาท
    fun canCheckout(): Boolean = total >= BigDecimal(100)
}
Entities เปลี่ยนแปลงน้อยที่สุด — เป็นแก่นที่ทุกชั้นนอกพึ่งพา

5. Use Cases (application logic)

1 Use Case = 1 การกระทำทางธุรกิจของแอป (ชื่อเป็นกริยา) — ประสาน Entities + เรียกข้อมูล ผ่าน interface (repository) ที่นิยามไว้ในชั้นใน

// interface นิยามในชั้น domain (ชั้นใน) — ชั้นนอกมา implement
interface OrderRepository {
    suspend fun submit(cart: Cart): Result<OrderId>
}

// Use Case พึ่ง interface ไม่ใช่ตัวจริง → ไม่รู้ว่าเบื้องหลังเป็น Retrofit/Room
class PlaceOrderUseCase(private val repo: OrderRepository) {
    suspend operator fun invoke(cart: Cart): Result<OrderId> {
        if (!cart.canCheckout())                     // ใช้กฎจาก Entity
            return Result.failure(MinimumNotMetException())
        return repo.submit(cart)
    }
}
Use Case ก็เป็น pure Kotlin (ไม่มี Android) → เทสต์ด้วย JUnit ธรรมดาได้ทันที

6. Interface Adapters (ตัวแปลง)

แปลงข้อมูล/รูปแบบระหว่างชั้นใน (Entities/Use Cases) กับชั้นนอก (UI/DB/network) — ได้แก่ ViewModel, Repository implementation, Mapper

// ViewModel = adapter ระหว่าง UI กับ Use Case
class OrderViewModel(private val placeOrder: PlaceOrderUseCase) : ViewModel() {
    private val _state = MutableStateFlow(OrderUiState())
    val state = _state.asStateFlow()

    fun onCheckout(cart: Cart) = viewModelScope.launch {
        placeOrder(cart)
            .onSuccess { _state.update { s -> s.copy(done = true) } }
            .onFailure { e -> _state.update { s -> s.copy(error = e.message) } }
    }
}

// Mapper = แปลง DTO (จาก network) → Entity (โมเดลธุรกิจ)
fun OrderDto.toEntity(): Order = Order(id = OrderId(id), total = total.toBigDecimal())

7. Frameworks & Drivers (ชั้นนอกสุด)

ของจริงที่พึ่ง framework: การ implement repository ด้วย Retrofit/Room, Activity/Compose, Hilt module — ชั้นนี้ "เปลี่ยนได้" โดยไม่กระทบชั้นใน

// implement interface ที่นิยามในชั้น domain — อยู่ชั้นนอก รู้จัก Retrofit/Room
class OrderRepositoryImpl(
    private val api: OrderApi,     // Retrofit
    private val dao: OrderDao      // Room
) : OrderRepository {
    override suspend fun submit(cart: Cart): Result<OrderId> = try {
        val dto = api.submit(cart.toRequest())     // framework detail
        Result.success(dto.toEntity().id)
    } catch (e: Exception) { Result.failure(e) }
}
อยากเปลี่ยนจาก Retrofit เป็น Ktor? แก้แค่ชั้นนี้ — Use Case/Entity ไม่ต้องแตะ

8. แมปลงโครง Android

Clean Architecture 4 ชั้น แมปเข้ากับเครื่องมือ Android ได้ดังนี้:

Clean Architectureบน Androidตัวอย่าง
Entitiesdomain models (pure Kotlin)Cart, Order
Use CasesUseCase / InteractorPlaceOrderUseCase
Interface AdaptersViewModel, Repository (interface), MapperOrderViewModel, OrderRepository
Frameworks & DriversRetrofit/Room/Compose/Activity/HiltOrderRepositoryImpl, OrderApi

มักจัดเป็น 3 module ตามชั้น:

:domain ← Entities + Use Cases + repository interface (pure Kotlin, ไม่มี Android) :data ← Repository impl + DataSource (Retrofit/Room) (พึ่ง :domain) :app / :presentation ← ViewModel + UI (พึ่ง :domain, :data ผ่าน DI)
เคล็ดลับ: ทำ :domain เป็น pure Kotlin module (ไม่ใช่ Android library) จะบังคับโดยตัว compiler เองว่าห้าม import Android เข้าไป — เป็นการ enforce Dependency Rule แบบอัตโนมัติ

9. ตัวอย่างโค้ดเต็ม (ไล่ทุกชั้น flow "กดสั่งอาหาร")

// ══ :domain (ชั้นใน — pure Kotlin, ไม่มี Android) ══

// Entity + กฎธุรกิจ
data class Cart(val items: List<CartItem>) {
    val total: BigDecimal get() = items.sumOf { it.price * it.qty.toBigDecimal() }
    fun canCheckout() = total >= BigDecimal(100)
}

// interface (นิยามในชั้นใน — Dependency Inversion)
interface OrderRepository { suspend fun submit(cart: Cart): Result<OrderId> }

// Use Case
class PlaceOrderUseCase(private val repo: OrderRepository) {
    suspend operator fun invoke(cart: Cart): Result<OrderId> {
        if (!cart.canCheckout()) return Result.failure(MinimumNotMetException())
        return repo.submit(cart)
    }
}

// ══ :data (ชั้นนอก — รู้จัก Retrofit/Room) ══
class OrderRepositoryImpl(private val api: OrderApi) : OrderRepository {
    override suspend fun submit(cart: Cart): Result<OrderId> = try {
        Result.success(api.submit(cart.toRequest()).toEntity().id)
    } catch (e: Exception) { Result.failure(e) }
}

// ══ :app (ชั้นนอก — UI/ViewModel) ══
@HiltViewModel
class OrderViewModel @Inject constructor(
    private val placeOrder: PlaceOrderUseCase
) : ViewModel() {
    private val _state = MutableStateFlow(OrderUiState())
    val state = _state.asStateFlow()

    fun checkout(cart: Cart) = viewModelScope.launch {
        placeOrder(cart)
            .onSuccess { _state.update { it.copy(done = true) } }
            .onFailure { e -> _state.update { it.copy(error = e.message) } }
    }
}

// DI (ชั้นนอกสุด) — ผูก interface กับ impl
@Module @InstallIn(SingletonComponent::class)
object AppModule {
    @Provides fun repo(api: OrderApi): OrderRepository = OrderRepositoryImpl(api)
    @Provides fun useCase(r: OrderRepository) = PlaceOrderUseCase(r)
}
สังเกต: PlaceOrderUseCase และ Cart ไม่มี Android เลย → ย้ายไปใช้บน iOS (ผ่าน KMP) หรือเทสต์ด้วย JUnit ล้วนได้ทันที

9.1 ภาคปฏิบัติ: สร้างฟีเจอร์จริง step-by-step

ส่วนนี้เดินสร้างฟีเจอร์ "หน้าแสดงเมนูอาหาร (ดึงจาก API + cache ลง DB)" ตั้งแต่ศูนย์ ทีละไฟล์ พร้อมบอกว่าแต่ละไฟล์อยู่ชั้นไหนและทำไม — ก๊อปไปตั้งต้นโปรเจกต์จริงได้

ขั้น 0 — วางโครงโฟลเดอร์ก่อน

com.example.foodorder ├─ domain/ (ชั้นใน — pure Kotlin, ไม่มี Android) │ ├─ model/MenuItem.kt Entity │ ├─ repository/MenuRepository.kt interface │ └─ usecase/GetMenuUseCase.kt UseCase ├─ data/ (ชั้นนอก — รู้จัก Retrofit/Room) │ ├─ remote/MenuApi.kt Retrofit API │ ├─ remote/dto/MenuItemDto.kt DTO (โมเดลจาก network) │ ├─ local/MenuDao.kt Room DAO │ ├─ local/entity/MenuEntity.kt Room entity │ ├─ mapper/MenuMappers.kt DTO/Room ↔ domain Entity │ └─ repository/MenuRepositoryImpl.kt └─ presentation/ (ชั้นนอก — UI) ├─ MenuViewModel.kt ├─ MenuUiState.kt └─ MenuFragment.kt └─ di/DataModule.kt (Hilt)
ลำดับการเขียนที่แนะนำ: เขียนจาก ชั้นในออกนอก (domain → data → presentation) เพราะชั้นในไม่พึ่งใคร เขียนเสร็จก่อนแล้วชั้นนอกค่อยมาต่อ

ขั้น 1 — Entity (domain/model)

// domain/model/MenuItem.kt — โมเดลธุรกิจ pure Kotlin
data class MenuItem(
    val id: String,
    val name: String,
    val price: BigDecimal,
    val available: Boolean
) {
    // กฎธุรกิจ: แสดงราคาพร้อมหน่วย
    fun displayPrice(): String = "฿%.2f".format(price)
}

ขั้น 2 — Repository interface (domain/repository)

// domain/repository/MenuRepository.kt
// นิยาม "สัญญา" ว่าต้องดึงเมนูได้ — ยังไม่สนว่าเบื้องหลังเป็น network/db
interface MenuRepository {
    // คืน Flow เพื่อให้ UI อัปเดตอัตโนมัติเมื่อข้อมูลเปลี่ยน
    fun getMenu(): Flow<List<MenuItem>>
    suspend fun refresh()   // ดึงใหม่จาก network
}

ขั้น 3 — UseCase (domain/usecase)

// domain/usecase/GetMenuUseCase.kt
// business rule: แสดงเฉพาะเมนูที่ยังมีของ (available) เรียงตามชื่อ
class GetMenuUseCase(private val repo: MenuRepository) {
    operator fun invoke(): Flow<List<MenuItem>> =
        repo.getMenu().map { list ->
            list.filter { it.available }.sortedBy { it.name }
        }
}
ถึงตรงนี้ ชั้น domain เสร็จสมบูรณ์ — ไม่มี Android/Retrofit/Room เลย เทสต์ได้ทันที (ดูขั้น 8)

ขั้น 4 — Data sources (data/remote + data/local)

// data/remote/dto/MenuItemDto.kt — โมเดล "ดิบ" จาก JSON (ตรงกับ API)
data class MenuItemDto(
    val id: String,
    val name: String,
    val price: Double,        // API ส่งมาเป็น double
    val in_stock: Boolean     // ชื่อ field แบบ API (snake_case)
)

// data/remote/MenuApi.kt — Retrofit
interface MenuApi {
    @GET("menu") suspend fun fetchMenu(): List<MenuItemDto>
}

// data/local/entity/MenuEntity.kt — โมเดลสำหรับ Room
@Entity(tableName = "menu")
data class MenuEntity(
    @PrimaryKey val id: String,
    val name: String,
    val price: Double,
    val available: Boolean
)

// data/local/MenuDao.kt — Room DAO
@Dao
interface MenuDao {
    @Query("SELECT * FROM menu") fun observeAll(): Flow<List<MenuEntity>>
    @Upsert suspend fun upsertAll(items: List<MenuEntity>)
}

ขั้น 5 — Mapper 3 ชั้น (data/mapper) — ทำไมต้องมี

มี 3 โมเดลคนละชั้น: DTO (network), MenuEntity (Room), MenuItem (domain) — ต้องแปลงไปมา เพื่อ กันไม่ให้รายละเอียดของ network/db รั่วเข้าชั้น domain

// data/mapper/MenuMappers.kt
// DTO → domain Entity (แปลง double→BigDecimal, snake_case→ชื่อ domain)
fun MenuItemDto.toDomain() = MenuItem(
    id = id, name = name,
    price = price.toBigDecimal(),
    available = in_stock
)
// domain → Room entity (ตอนจะ cache)
fun MenuItem.toEntity() = MenuEntity(id, name, price.toDouble(), available)
// Room entity → domain (ตอนอ่านจาก DB)
fun MenuEntity.toDomain() = MenuItem(id, name, price.toBigDecimal(), available)
ทำไมไม่ใช้โมเดลเดียวทุกชั้น? เพราะถ้า domain ใช้ DTO ตรง ๆ → พอ API เปลี่ยน field ต้องแก้ทั้งแอป • การแยกโมเดล + mapper ทำให้ API/DB เปลี่ยนได้โดยแก้แค่ชั้น data

ขั้น 6 — Repository implementation (data/repository)

// data/repository/MenuRepositoryImpl.kt — SSOT: DB เป็นแหล่งความจริง
class MenuRepositoryImpl(
    private val api: MenuApi,
    private val dao: MenuDao
) : MenuRepository {

    // UI อ่านจาก DB เสมอ (single source of truth) → map เป็น domain model
    override fun getMenu(): Flow<List<MenuItem>> =
        dao.observeAll().map { entities -> entities.map { it.toDomain() } }

    // refresh: ดึง network → แปลง → เขียนลง DB (แล้ว Flow ข้างบนจะ emit เอง)
    override suspend fun refresh() {
        val fromNetwork = api.fetchMenu().map { it.toDomain() }
        dao.upsertAll(fromNetwork.map { it.toEntity() })
    }
}
รูปแบบ cache ที่นิยม: UI อ่านจาก DB (offline ได้) • refresh ดึง network มาเขียนทับ DB • Flow ทำให้ UI อัปเดตอัตโนมัติเมื่อ DB เปลี่ยน

ขั้น 7 — Presentation: UI State + ViewModel + error handling ข้ามชั้น

// presentation/MenuUiState.kt
data class MenuUiState(
    val items: List<MenuItem> = emptyList(),
    val isLoading: Boolean = false,
    val error: String? = null
)

// presentation/MenuViewModel.kt
@HiltViewModel
class MenuViewModel @Inject constructor(
    private val getMenu: GetMenuUseCase,
    private val repo: MenuRepository
) : ViewModel() {

    val uiState: StateFlow<MenuUiState> = getMenu()
        .map { MenuUiState(items = it) }
        .catch { emit(MenuUiState(error = it.toUiMessage())) }   // error → state
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), MenuUiState(isLoading = true))

    fun refresh() = viewModelScope.launch {
        try { repo.refresh() }
        catch (e: Exception) { /* แสดง snackbar ผ่าน event channel */ }
    }
}

// แปลง exception (ชั้น data) → ข้อความที่ผู้ใช้เข้าใจ (ชั้น UI)
fun Throwable.toUiMessage(): String = when (this) {
    is IOException -> "เชื่อมต่อเครือข่ายไม่ได้"
    else -> "เกิดข้อผิดพลาด กรุณาลองใหม่"
}
error handling ข้ามชั้น (จุดที่มือใหม่งง): exception เกิดที่ชั้น data (network) → ไหลขึ้นมาถูก catch ที่ ViewModel → แปลงเป็น ข้อความใน UI state → UI แสดง • ชั้น domain/data ไม่รู้จักข้อความภาษาไทย/UI เลย

ขั้น 8 — DI (di) ผูก interface กับ impl

// di/DataModule.kt
@Module @InstallIn(SingletonComponent::class)
object DataModule {
    @Provides @Singleton
    fun menuRepository(api: MenuApi, dao: MenuDao): MenuRepository =
        MenuRepositoryImpl(api, dao)          // ผูก interface → impl

    @Provides
    fun getMenuUseCase(repo: MenuRepository) = GetMenuUseCase(repo)
}

สังเกตว่าเทสต์ UseCase ไม่ต้องแตะ Android/Retrofit/Room เลย — นี่คือ ผลตอบแทนหลักของ Clean Architecture

สรุป flow ทั้งหมด (ที่เพิ่งสร้าง)

UI (MenuFragment) │ observe uiState MenuViewModel ── getMenu() ──► GetMenuUseCase ── กรอง/เรียง ──► MenuRepository │ (interface) MenuRepositoryImpl │ │ MenuDao(Room) MenuApi(Retrofit) ▲ SSOT │ └── refresh() เขียนทับ error: network ล้ม → Exception → catch ที่ ViewModel → toUiMessage() → error ใน state → UI แสดง

10. โครงสร้างแพ็กเกจ / โมดูล

แบบ multi-module (แนะนำสำหรับแอปใหญ่)

:domain (pure Kotlin library) ├─ model/ Entities ├─ repository/ interfaces └─ usecase/ Use Cases :data (Android library, พึ่ง :domain) ├─ remote/ Retrofit API + DTO ├─ local/ Room DAO + entity ├─ mapper/ DTO/Room ↔ Entity └─ repository/ RepositoryImpl :app (พึ่ง :domain, :data) ├─ ui/ Activity/Fragment/Compose ├─ viewmodel/ └─ di/ Hilt modules

แบบ single-module (แอปเล็ก-กลาง)

com.example.app ├─ domain/ (model, repository interface, usecase) ├─ data/ (repositoryImpl, remote, local, mapper) └─ ui/ (viewmodel, screens)
แยก :domain เป็น pure Kotlin module = compiler บังคับ Dependency Rule ให้เอง (import Android ไม่ได้) • แอปเล็กใช้แค่แพ็กเกจแยกก็พอ

11. ข้อดี / ข้อเสีย

  • ✅ business logic ทดสอบง่ายสุด — pure Kotlin เทสต์ด้วย JUnit ไม่ต้องมี Android
  • ✅ เปลี่ยน UI/DB/network ได้โดยไม่กระทบแกนธุรกิจ
  • ✅ แชร์ logic ข้ามแพลตฟอร์มได้ (KMP: :domain ใช้ทั้ง Android/iOS)
  • ✅ โครงชัด หลายทีมทำงานแยกชั้นได้
  • ✅ บังคับ separation ที่ดี ลด coupling
  • ❌ boilerplate เยอะมาก — interface + impl + mapper + usecase ต่อ 1 ฟีเจอร์
  • ❌ over-engineering สำหรับแอปเล็ก (ทุก action ต้องมี UseCase)
  • ❌ เรียนรู้ยาก มือใหม่งงเรื่อง Dependency Inversion/mapper หลายชั้น
  • ❌ เขียนโค้ดช้าลงตอนเริ่ม (แต่คุ้มระยะยาวถ้าแอปโต)
  • ❌ mapper ระหว่างชั้นเยอะ (DTO→Entity→UI model) อาจรู้สึกซ้ำซ้อน

ทั้งสองมีเป้าหมายเดียวกัน (แยกชั้น ทดสอบง่าย ขยายได้) แต่ต่างกันที่ระดับความเข้มงวดและ ขอบเขต

เห็นภาพชัดสุด: โค้ดฟีเจอร์เดียวกัน 2 แบบ

โจทย์: กดปุ่ม "สั่งอาหาร" โดยต้องมี ยอดขั้นต่ำ 100 บาท — มาดูว่าเขียน 2 แบบ ต่างกันตรงไหน

แบบ Google Guide (เบา) — ViewModel คุย Repository ตรง — 2 ไฟล์

// 1) Repository (data layer)
interface OrderRepository {
    suspend fun submit(items: List<CartItem>): Result<OrderId>
}

// 2) ViewModel — ใส่ logic "ยอดขั้นต่ำ" ไว้ตรงนี้เลย
class OrderViewModel(private val repo: OrderRepository) : ViewModel() {
    fun placeOrder(items: List<CartItem>) = viewModelScope.launch {
        val total = items.sumOf { it.price * it.qty.toBigDecimal() }
        if (total < BigDecimal(100)) {              // ← logic อยู่ใน ViewModel
            _state.update { it.copy(error = "ยอดขั้นต่ำ 100 บาท") }
            return@launch
        }
        repo.submit(items).onSuccess { /* ... */ }.onFailure { /* ... */ }
    }
}

แบบ Clean Architecture — แยก logic เป็น Entity + UseCase — 4 ไฟล์

// 1) Entity — กฎ "ยอดขั้นต่ำ" อยู่ในตัวโมเดล (pure Kotlin)
data class Cart(val items: List<CartItem>) {
    val total get() = items.sumOf { it.price * it.qty.toBigDecimal() }
    fun canCheckout() = total >= BigDecimal(100)      // ← logic อยู่ที่นี่
}

// 2) Repository interface (domain)
interface OrderRepository { suspend fun submit(cart: Cart): Result<OrderId> }

// 3) UseCase — 1 การกระทำทางธุรกิจ
class PlaceOrderUseCase(private val repo: OrderRepository) {
    suspend operator fun invoke(cart: Cart): Result<OrderId> {
        if (!cart.canCheckout()) return Result.failure(MinimumNotMetException())
        return repo.submit(cart)
    }
}

// 4) ViewModel — บางมาก แค่เรียก UseCase (ไม่มี logic)
class OrderViewModel(private val placeOrder: PlaceOrderUseCase) : ViewModel() {
    fun onPlaceOrder(cart: Cart) = viewModelScope.launch {
        placeOrder(cart).onSuccess { /* ... */ }.onFailure { /* ... */ }
    }
}
Google GuideClean Architecture
logic "ยอดขั้นต่ำ" อยู่ที่ไหนใน ViewModelใน Entity + UseCase
จำนวนไฟล์24
ViewModelมี logic ปนอยู่บางมาก แค่ต่อสาย

ต่างกันตอน "ใช้งานจริง" ยังไง — 3 สถานการณ์

สถานการณ์ 1 — logic เดียวกันถูกใช้ 2 ที่ (หน้า Cart + Checkout ด่วน)

  • Google Guide: ต้อง copy if (total < 100) ไปอีก ViewModel → เสี่ยงลืมแก้ที่เดียว logic ไม่ตรงกัน
  • Clean: เรียก PlaceOrderUseCase เดิมซ้ำได้ทันที → logic อยู่ที่เดียว

สถานการณ์ 2 — เขียน test กฎ "ยอดขั้นต่ำ"

  • Google Guide: ต้อง test ผ่าน ViewModel (mock Repository + จัดการ coroutine)
  • Clean: test cart.canCheckout() เป็น pure function → เร็ว ง่าย ไม่แตะ Android

สถานการณ์ 3 — แอปเล็ก logic แค่นี้ ไม่ได้ใช้ซ้ำ

  • Google Guide: จบใน 2 ไฟล์ อ่านง่าย
  • Clean: เขียน 4 ไฟล์เพื่อ logic บรรทัดเดียว → over-engineering
จุดตัดสินง่าย ๆ: ถาม "logic ธุรกิจนี้จะถูก ใช้ซ้ำ / ซับซ้อน / ต้องเทสต์ หนัก ไหม?" — ใช่ → Clean คุ้ม • ไม่ → Google Guide พอ

เลือกยังไง (กฎง่าย ๆ)

  • แอป เล็ก/กลาง → Google Guide (เบา พอแล้ว ไม่ต้องมี Use Case ทุกอัน)
  • แอป ใหญ่/ซับซ้อน/แชร์ข้าม iOS (KMP) → Clean Architecture (คุ้มกับความเข้ม)
  • ไม่แน่ใจ → เริ่ม Google Guide ก่อน แล้วค่อยเพิ่มความเข้มเมื่อโตขึ้น

15. แนวโน้มในอนาคต

  • KMP ดัน Clean Architecture ให้สำคัญขึ้น — การแชร์ :domain (pure Kotlin) ข้าม Android/iOS ทำให้การแยก business logic ออกจาก framework คุ้มค่าชัดเจน
  • Google Guide + Clean แบบผสม เป็นค่ากลางที่นิยม — ทีมส่วนใหญ่ไม่ทำ Clean เป๊ะ แต่หยิบ UseCase + domain module + dependency rule มาใช้
  • Compose + UDF เข้ากันดีกับ Clean — state-driven UI + Use Case ที่คืน state
  • เครื่องมือ modularization ดีขึ้น — ทำให้แยก :domain/:data ต้นทุนต่ำลง
  • สรุปทิศทาง: ไม่ใช่ "Clean vs Google Guide" แต่เป็น สเปกตรัม — เลือกความ เข้มตามขนาด/ความซับซ้อน/ความต้องการแชร์ข้ามแพลตฟอร์ม

16. ศัพท์ทางเทคนิค (Glossary)

  • Clean Architecture — แนวคิดจัดโครงให้ business logic เป็นอิสระจาก framework (Uncle Bob)
  • Dependency Rule — กฎว่า dependency ต้องชี้เข้าด้านในเสมอ
  • Dependency Inversion — ชั้นในนิยาม interface, ชั้นนอกมา implement (พลิกทิศพึ่งพา)
  • Entities — business models + กฎธุรกิจหลัก (วงในสุด, pure)
  • Use Case / Interactor — application logic 1 การกระทำ
  • Interface Adapters — ตัวแปลงข้อมูลระหว่างชั้น (ViewModel/Repository/Mapper)
  • Frameworks & Drivers — ของจริงชั้นนอกสุด (UI/DB/network/Android)
  • Mapper — ตัวแปลงระหว่างโมเดลแต่ละชั้น (DTO ↔ Entity ↔ UI model)
  • DTO (Data Transfer Object) — โมเดลข้อมูลดิบจาก network/db
  • pure Kotlin module — โมดูลที่ไม่พึ่ง Android SDK (บังคับ dependency rule ได้)
  • Google Guide (Recommended architecture) — แนวทางสถาปัตยกรรมทางการของ Android
