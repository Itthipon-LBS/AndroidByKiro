การจัดการ State และข้อมูลใน Android (ฉบับสมบูรณ์)

อธิบายการจัดการ state (สถานะ UI) และข้อมูลบน Android ครบทุกส่วน — ประเภท state, ที่เก็บ (ViewModel/SavedStateHandle), StateFlow/LiveData, event vs state, ระดับการรอด (config change/process death/ถาวร), DataStore/Room, ข้อมูลเครือข่าย, SSOT — พร้อมภาคปฏิบัติ สร้างจริง, ข้อดี/ข้อเสีย, การเลือกใช้ และแนวโน้ม อ่านจบแล้วนำไปใช้ได้ทันที

สรุปสั้นสุด: UI state เก็บใน ViewModel เปิดเป็น StateFlow (read-only) • state ที่ต้องรอด process death ใช้ SavedStateHandle • ข้อมูลถาวร ใช้ DataStore (คู่ค่า) หรือ Room (มีโครงสร้าง) • ยึดหลัก SSOT (แหล่งความจริงเดียว) + UDF (state ลง, event ขึ้น)

1. State และข้อมูลคืออะไร

State (สถานะ) คือ "ข้อมูลที่อธิบายว่า ณ ตอนนี้ UI ควรแสดงอะไร" — เช่น รายการสินค้า, กำลังโหลดอยู่ไหม, มี error ไหม • เมื่อ state เปลี่ยน UI ต้องอัปเดตตาม

แยก 2 คำที่มักสับสน:

  • State — ค่าปัจจุบันที่ "คงอยู่" และ UI สะท้อนตลอด (เช่น list, isLoading)
  • ข้อมูล (Data) — ตัวเนื้อข้อมูลจริง (จาก network/db) ที่ถูกแปลงมาเป็น state
หลักคิด: UI = f(state) — หน้าจอเป็นผลลัพธ์ของ state ล้วน ๆ ไม่ควรมี ข้อมูลซ่อนอยู่ใน view เอง

2. ประเภทของ state

ประเภทคือตัวอย่างเก็บที่
UI element stateสถานะของ view ชั่วคราวscroll position, ข้อความในช่องกรอกview/rememberSaveable
Screen (UI) stateสถานะทั้งหน้าจอlist, isLoading, errorViewModel (StateFlow)
App/persistent stateข้อมูลที่ต้องอยู่ถาวรตั้งค่าผู้ใช้, ข้อมูลที่ cacheDataStore/Room

3. State holders (ที่เก็บ state)

ViewModel — ที่เก็บ screen state หลัก

ถือ UI state ของหน้าจอ, รอด configuration change (หมุนจอ), มี viewModelScope

class MenuViewModel(private val repo: MenuRepository) : ViewModel() {
    private val _uiState = MutableStateFlow(MenuUiState())   // แก้ได้ (ภายใน)
    val uiState: StateFlow<MenuUiState> = _uiState.asStateFlow()  // read-only (ออกไป)
}

SavedStateHandle — state ที่ต้องรอด process death

class SearchViewModel(private val state: SavedStateHandle) : ViewModel() {
    // รอดทั้งหมุนจอ และตอนระบบ kill แอปคืน RAM
    val query: StateFlow<String> = state.getStateFlow("query", "")
    fun setQuery(q: String) { state["query"] = q }
}

Compose: remember / rememberSaveable

var text by remember { mutableStateOf("") }          // รอด recomposition
var text by rememberSaveable { mutableStateOf("") }  // รอด config change/process death

4. Observable state: StateFlow vs LiveData

เปิด state ให้ UI "สังเกต (observe)" แล้ววาดใหม่เมื่อเปลี่ยน — มี 2 ตัวหลัก:

ประเด็นStateFlowLiveData
มาจากKotlin Coroutines (Flow)Jetpack (เก่ากว่า)
มีค่าเริ่มต้นต้องมีเสมอไม่บังคับ (null ได้)
lifecycle-awareต้องใช้ repeatOnLifecycle เองในตัว
ใช้กับ ComposecollectAsStateWithLifecycle()observeAsState()
แนะนำปัจจุบัน✅ (มาตรฐานใหม่)ยังใช้ได้ (โปรเจกต์เก่า)

สังเกต StateFlow ใน View (ถูกต้อง)

viewLifecycleOwner.lifecycleScope.launch {
    viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
        viewModel.uiState.collect { state -> render(state) }  // หยุด/เริ่มตามการมองเห็น
    }
}

สังเกตใน Compose

val state by viewModel.uiState.collectAsStateWithLifecycle()
Text(state.title)   // recompose อัตโนมัติเมื่อ state เปลี่ยน

5. State vs Event (one-shot) — จุดพลาดบ่อย

ต้องแยก "state ที่คงอยู่" กับ "event ที่เกิดครั้งเดียว" (toast, navigate, snackbar)

  • State — สะท้อนตลอด (list, isLoading) → StateFlow/LiveData
  • One-shot event — เกิดครั้งเดียวแล้วจบ → ถ้าเก็บเป็น state จะ "เด้งซ้ำ" ตอนหมุนจอ
// ❌ ผิด: เก็บ navigate เป็น state → หมุนจอแล้ว navigate ซ้ำ
// ✅ ถูก: ใช้ Channel (consume ครั้งเดียว)
private val _events = Channel<UiEvent>()
val events = _events.receiveAsFlow()

fun onSubmit() = viewModelScope.launch {
    repo.submit()
    _events.send(UiEvent.NavigateToSuccess)   // ส่ง event ครั้งเดียว
}
สรุป: อะไรที่ "แสดงค้างบนจอ" = state • อะไรที่ "ทำครั้งเดียวแล้วจบ" (นำทาง/แจ้งเตือน) = event ผ่าน Channel/SharedFlow

6. ระดับการรอด (survival) — สำคัญที่สุด

ต้องรู้ว่า state แต่ละอันต้อง "รอด" สถานการณ์ไหนบ้าง แล้วเลือกที่เก็บให้ถูก:

สถานการณ์ViewModelSavedStateHandleDataStore/Room
หมุนจอ / config change✅ รอด✅ รอด✅ รอด
process death (ระบบ kill background)❌ หาย✅ รอด✅ รอด
ปิดแอปเอง / รีบูตเครื่อง❌ หาย❌ หาย✅ รอด (ถาวร)
process death มองไม่เห็นตอน dev — ต้องจงใจทดสอบ (Developer options → "Don't keep activities" หรือ kill จาก Android Studio) ไม่งั้นเจอบั๊กตอน production

9. SSOT + ทิศทางข้อมูล (UDF)

  • SSOT (Single Source of Truth): ข้อมูลแต่ละชนิดมี "แหล่งความจริงเดียว" — มัก เป็น Repository/DB คนอื่นแค่อ่าน
  • UDF (Unidirectional Data Flow): state ไหลลง (Repo→VM→UI), event ไหลขึ้น (UI→VM)
event (คลิก/พิมพ์) ▲ UI ──────────────────────────┘ ▲ observe state (StateFlow) │ ViewModel ◄── Repository ◄── DB / Network (SSOT)
ยึด SSOT + UDF แล้วบั๊ก "ข้อมูลไม่ตรงกันหลายที่" จะหายไปเกือบหมด

10. เก็บอะไรไว้ที่ไหน (Decision Guide)

ข้อมูลนี้ต้องอยู่ถาวร (ปิดแอป/รีบูตแล้วยังอยู่)? ├─ ใช่ + เป็นค่าเดี่ยว/ตั้งค่า → DataStore └─ ใช่ + มีโครงสร้าง/หลายรายการ → Room ต้องรอด process death (ระบบ kill ตอน background)? ├─ ใช่ + ข้อมูลเล็ก → SavedStateHandle └─ ใช่ + ข้อมูลใหญ่ → เก็บ id/คีย์ใน SavedStateHandle แล้วโหลดจาก repository แค่ต้องรอดหมุนจอ (config change)? └─ ใช่ → ViewModel (StateFlow) เป็นค่าชั่วคราวใน UI (Compose)? └─ remember (ไม่รอด) / rememberSaveable (รอด config+process death) เป็น "ทำครั้งเดียว" (navigate/toast)? └─ Channel / SharedFlow (ไม่ใช่ state)
ต้องการใช้
UI state ของหน้าจอViewModel + StateFlow
รอด process death (เล็ก)SavedStateHandle
ตั้งค่า/ค่าเดี่ยวถาวรDataStore
ข้อมูลมีโครงสร้าง/cacheRoom
ข้อมูลจาก serverRetrofit/Ktor → map → Repository
navigate/toast/snackbarChannel/SharedFlow (event)

11. ข้อดี / ข้อเสียของแต่ละตัว

ViewModel + StateFlow

  • ✅ รอด config change, มี scope จัดการ coroutine, เข้ากับ Compose/UDF
  • ❌ ไม่รอด process death (ต้องคู่กับ SavedStateHandle), StateFlow ต้อง repeatOnLifecycle เอง

SavedStateHandle

  • ✅ รอด process death, ผูกกับ ViewModel สะดวก
  • ❌ เก็บได้แต่ของเล็ก (Bundle) — ห้าม list/bitmap ใหญ่

DataStore

  • ✅ async ปลอดภัย (แทน SharedPreferences), Flow ในตัว, ถาวร
  • ❌ ไม่เหมาะข้อมูลมีโครงสร้าง/query ซับซ้อน

Room

  • ✅ query ได้, type-safe, Flow, เหมาะ cache/offline
  • ❌ setup มากกว่า, over-kill สำหรับค่าเดี่ยว ๆ

LiveData

  • ✅ lifecycle-aware ในตัว, ง่ายสำหรับมือใหม่/โปรเจกต์เก่า
  • ❌ เก่ากว่า, ไม่เข้ากับ coroutines/Compose เท่า StateFlow

12. ภาคปฏิบัติ: สร้างจริง step-by-step

โจทย์: หน้าจอ "ค้นหาเมนู" ที่ (1) เก็บคำค้นให้รอด process death, (2) โหลดผลจาก Repository, (3) จำ dark mode ถาวร, (4) navigate เมื่อกดรายการ — ครบทุกประเภท state

ขั้น 1 — UI State (immutable)

data class SearchUiState(
    val query: String = "",
    val results: List<MenuItem> = emptyList(),
    val isLoading: Boolean = false,
    val error: String? = null
)

// one-shot event แยกจาก state
sealed interface SearchEvent {
    data class OpenDetail(val id: String) : SearchEvent
    data class ShowError(val msg: String) : SearchEvent
}

ขั้น 2 — ViewModel: รวม SavedStateHandle + StateFlow + Channel

@HiltViewModel
class SearchViewModel @Inject constructor(
    private val repo: MenuRepository,
    private val savedState: SavedStateHandle
) : ViewModel() {

    // 1) query เก็บใน SavedStateHandle → รอด process death
    val query: StateFlow<String> = savedState.getStateFlow("query", "")

    // 2) results มาจาก query (debounce กันยิงถี่) แล้วโหลดจาก repo
    val uiState: StateFlow<SearchUiState> = query
        .debounce(300)
        .flatMapLatest { q ->
            if (q.isBlank()) flowOf(SearchUiState())
            else repo.search(q)
                .map { SearchUiState(query = q, results = it) }
                .onStart { emit(SearchUiState(query = q, isLoading = true)) }
                .catch { emit(SearchUiState(query = q, error = it.toUiMessage())) }
        }
        .stateIn(viewModelScope, SharingStarted.WhileSubscribed(5000), SearchUiState())

    // 3) event ครั้งเดียว (navigate)
    private val _events = Channel<SearchEvent>()
    val events = _events.receiveAsFlow()

    fun onQueryChange(q: String) { savedState["query"] = q }   // เก็บอัตโนมัติ
    fun onItemClick(id: String) = viewModelScope.launch {
        _events.send(SearchEvent.OpenDetail(id))
    }
}

ขั้น 3 — dark mode ถาวรด้วย DataStore (แยก Repository)

class SettingsRepository(private val dataStore: DataStore<Preferences>) {
    private val DARK = booleanPreferencesKey("dark_mode")
    val darkMode: Flow<Boolean> = dataStore.data.map { it[DARK] ?: false }
    suspend fun setDark(on: Boolean) { dataStore.edit { it[DARK] = on } }
}

ขั้น 4 — UI (Fragment): observe state + consume event

class SearchFragment : Fragment() {
    private val vm: SearchViewModel by viewModels()

    override fun onViewCreated(v: View, s: Bundle?) {
        // state → วาด UI
        viewLifecycleOwner.lifecycleScope.launch {
            viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
                launch { vm.uiState.collect { render(it) } }
                launch { vm.events.collect { handleEvent(it) } }   // event ครั้งเดียว
            }
        }
        // event → ส่งขึ้น ViewModel
        binding.searchInput.doAfterTextChanged { vm.onQueryChange(it.toString()) }
    }

    private fun handleEvent(e: SearchEvent) = when (e) {
        is SearchEvent.OpenDetail -> findNavController().navigate(/* to detail */)
        is SearchEvent.ShowError  -> showSnackbar(e.msg)
    }
}
ครบทุกประเภท: query = SavedStateHandle (รอด process death), results/ isLoading = StateFlow, navigate = Channel (event), dark mode = DataStore (ถาวร)

15. แนวโน้มในอนาคต

  • StateFlow + collectAsStateWithLifecycle เป็นมาตรฐาน — แทน LiveData เดิม
  • DataStore แทน SharedPreferences เต็มตัว — SharedPreferences ถือว่า legacy
  • UI state ก้อนเดียว (single state) + UDF/MVI นิยมขึ้นกับ Compose
  • Room + Flow เป็น cache/offline-first มาตรฐาน
  • KMP: StateFlow/coroutines/Room(KMP) แชร์ logic การจัดการ state ข้ามแพลตฟอร์มได้
  • สรุป: ทิศทางคือ state-driven + reactive (Flow) + immutable single state — เครื่องมือ เปลี่ยน (LiveData→StateFlow, SharedPreferences→DataStore) แต่หลักการ (SSOT/UDF/survival) คงเดิม

16. ศัพท์ทางเทคนิค (Glossary)

  • State — ข้อมูลที่อธิบายว่า UI ควรแสดงอะไรตอนนี้
  • UI State — ก้อน immutable ที่อธิบายทั้งหน้าจอ
  • State holder — ตัวถือ state (ViewModel)
  • StateFlow — Flow ที่มีค่าปัจจุบันเสมอ (จาก coroutines) ใช้เปิด state
  • LiveData — observable แบบ lifecycle-aware ของ Jetpack (เก่ากว่า)
  • SavedStateHandle — ที่เก็บ state ใน ViewModel ที่รอด process death
  • one-shot event — เหตุการณ์ที่เกิดครั้งเดียว (navigate/toast) → Channel/SharedFlow
  • Channel / SharedFlow — ช่องส่ง event แบบ consume ครั้งเดียว
  • DataStore — ที่เก็บ preference แบบ async (แทน SharedPreferences)
  • Room — ORM บน SQLite (ข้อมูลมีโครงสร้าง)
  • SSOT — Single Source of Truth (แหล่งความจริงเดียว)
  • UDF — Unidirectional Data Flow (state ลง, event ขึ้น)
  • process death — ระบบ kill process แอป (background) เพื่อคืน RAM
  • debounce — หน่วงรอให้หยุดพิมพ์ก่อนค่อยยิง (กัน request ถี่)
