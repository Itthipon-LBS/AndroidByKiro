Permissions & ความปลอดภัยใน Android (ฉบับสมบูรณ์)

อธิบายระบบสิทธิ์ (permissions) และความปลอดภัยบน Android ครบทุกส่วน — ประเภท permission, runtime permission flow, special permissions, Scoped Storage, การเก็บข้อมูล/ เครือข่ายที่ปลอดภัย, การป้องกัน component — พร้อมตารางเทียบตามเวอร์ชัน, ภาคปฏิบัติ, ข้อดี/ ข้อเสีย, การเลือกใช้ และแนวโน้ม อ่านจบแล้วนำไปใช้ได้ทันที

สรุปสั้นสุด: ขอ permission เท่าที่จำเป็น + ตอนใช้งานจริง (ผู้ใช้ปฏิเสธได้ ต้องเผื่อ) • ใช้ Activity Result API ขอ runtime permission • เก็บข้อมูลลับใน EncryptedSharedPreferences/Keystore ไม่ใช่ plain text • ใช้ HTTPS เสมอ • ตั้ง component เป็น exported=false ถ้าไม่ต้องการให้แอปอื่นเรียก

1. Permission คืออะไร

Permission (สิทธิ์) คือกลไกที่ Android ใช้ควบคุมว่าแอปเข้าถึง "ข้อมูล/ฟีเจอร์ที่ อ่อนไหว" ได้หรือไม่ — เช่น กล้อง, ตำแหน่ง, รายชื่อผู้ติดต่อ, ไมโครโฟน เพื่อปกป้องความเป็น ส่วนตัวและความปลอดภัยของผู้ใช้

ทุก permission ต้อง ประกาศใน AndroidManifest.xml ก่อน:

<uses-permission android:name="android.permission.CAMERA" />
<uses-permission android:name="android.permission.ACCESS_FINE_LOCATION" />
หลักการทอง: ขอเท่าที่จำเป็น (least privilege) + ขอตอนจะใช้จริง + อธิบายเหตุผลให้ผู้ใช้เข้าใจ

2. ประเภทของ permission

ประเภทคือต้องขอตอน runtime?ตัวอย่าง
Normalเสี่ยงต่ำ ระบบให้อัตโนมัติไม่ (แค่ประกาศใน manifest)INTERNET, VIBRATE, SET_ALARM
Dangerousเข้าถึงข้อมูลอ่อนไหว✅ ต้องขอตอนใช้CAMERA, LOCATION, CONTACTS, MICROPHONE
Signatureให้เฉพาะแอปที่เซ็นด้วย key เดียวกันอัตโนมัติ (ถ้า key ตรง)permission ระหว่างแอปของผู้พัฒนาเดียวกัน
Specialสิทธิ์พิเศษ ต้องพาไปหน้า Settingsผ่าน Settings (ไม่ใช่ dialog ปกติ)SYSTEM_ALERT_WINDOW, MANAGE_EXTERNAL_STORAGE
Dangerous คือกลุ่มที่ต้องเขียนโค้ดขอ runtime permission — เป็นหัวใจ ของหัวข้อ 3

3. Runtime permission flow (หัวใจ)

ตั้งแต่ Android 6 (API 23) permission กลุ่ม dangerous ต้องขอ ตอน runtime (ผู้ใช้ กดอนุญาต/ปฏิเสธ) ไม่ใช่ให้ตั้งแต่ติดตั้ง

1. เช็คว่ามีสิทธิ์แล้วยัง (checkSelfPermission) ├─ มีแล้ว → ทำงานเลย └─ ยังไม่มี ↓ 2. ควรอธิบายเหตุผลไหม (shouldShowRequestPermissionRationale) ├─ ควร → แสดงคำอธิบายก่อน แล้วค่อยขอ └─ ไม่ ↓ 3. ขอ permission (launcher.launch) ├─ อนุญาต → ทำงาน └─ ปฏิเสธ → แสดง fallback / อธิบาย / พาไป Settings

เขียนด้วย Activity Result API (วิธีปัจจุบัน)

// ลงทะเบียน launcher (ทำครั้งเดียว ตอนสร้าง Fragment/Activity)
private val cameraPermission = registerForActivityResult(
    ActivityResultContracts.RequestPermission()
) { granted: Boolean ->
    if (granted) openCamera()
    else showRationaleOrSettings()
}

fun onCameraClick() {
    when {
        // 1) มีสิทธิ์แล้ว
        ContextCompat.checkSelfPermission(this, Manifest.permission.CAMERA)
            == PackageManager.PERMISSION_GRANTED -> openCamera()

        // 2) เคยปฏิเสธ → อธิบายเหตุผลก่อน
        shouldShowRequestPermissionRationale(Manifest.permission.CAMERA) ->
            showRationaleDialog { cameraPermission.launch(Manifest.permission.CAMERA) }

        // 3) ขอครั้งแรก
        else -> cameraPermission.launch(Manifest.permission.CAMERA)
    }
}
ปฏิเสธถาวร (Android 11+): ถ้าผู้ใช้ปฏิเสธ 2 ครั้ง ระบบถือว่า "ไม่ถาม อีก" — ต้องพาผู้ใช้ไปเปิดเองใน Settings (เปิด dialog ขอไม่ขึ้นแล้ว)

4. Special permissions (ต้องไป Settings)

บาง permission ไม่ขอผ่าน dialog ปกติ แต่ต้องพาผู้ใช้ไปเปิดในหน้า Settings:

Permissionใช้ทำ
SYSTEM_ALERT_WINDOWวาด overlay บนแอปอื่น (floating bubble)
MANAGE_EXTERNAL_STORAGEเข้าถึงไฟล์ทั้งเครื่อง (ต้องมีเหตุผลชัด, Play เข้ม)
REQUEST_INSTALL_PACKAGESติดตั้ง APK
SCHEDULE_EXACT_ALARMตั้งปลุกเวลาเป๊ะ (Android 12+)
POST_NOTIFICATIONSส่ง notification (Android 13+ — เป็น runtime dialog)
// พาไปหน้า Settings ของ special permission
val intent = Intent(Settings.ACTION_MANAGE_OVERLAY_PERMISSION,
    Uri.parse("package:$packageName"))
startActivity(intent)

5. Permission ตำแหน่ง (กรณีพิเศษที่ซับซ้อนสุด)

  • ACCESS_COARSE_LOCATION — ตำแหน่งคร่าว ๆ (approximate) • ACCESS_FINE_LOCATION — ตำแหน่งแม่นยำ
  • Android 10+: แยก "ขณะใช้แอป" (WHEN_IN_USE) กับ "ตลอดเวลา" (ACCESS_BACKGROUND_LOCATION) — background ต้องขอแยกและมีเหตุผลชัด
  • Android 12+: ผู้ใช้เลือกให้ ตำแหน่งคร่าว ๆ แทนแม่นยำได้ (ต้องขอทั้งคู่ + เผื่อกรณีได้แค่ coarse)
// ขอทั้ง fine + coarse พร้อมกัน แล้วเช็คว่าได้อันไหน
private val locationPerms = registerForActivityResult(
    ActivityResultContracts.RequestMultiplePermissions()
) { result ->
    when {
        result[Manifest.permission.ACCESS_FINE_LOCATION] == true -> useFine()
        result[Manifest.permission.ACCESS_COARSE_LOCATION] == true -> useApprox()
        else -> showDenied()
    }
}
locationPerms.launch(arrayOf(
    Manifest.permission.ACCESS_FINE_LOCATION,
    Manifest.permission.ACCESS_COARSE_LOCATION
))
เลือกใช้ให้เหมาะ: ถ้าแค่ต้องการ "เมือง/ย่าน" ใช้ coarse พอ (privacy- friendly) • ขอ background location เฉพาะเมื่อจำเป็นจริง (Play ตรวจเข้ม)

6. Scoped Storage (การเข้าถึงไฟล์)

ตั้งแต่ Android 10 แอปเข้าถึงไฟล์แบบ "จำกัดขอบเขต" — เข้าถึงได้แค่โฟลเดอร์ของตัวเอง + media ที่สร้างเอง โดยไม่ต้องขอ permission storage

ต้องการวิธี (Scoped Storage)
ไฟล์ของแอปเองapp-specific dir (ไม่ต้องขอ permission)
เลือกไฟล์/รูปจากเครื่องPhoto Picker / Storage Access Framework (ไม่ต้องขอ permission)
อ่าน media ที่แอปอื่นสร้างREAD_MEDIA_IMAGES/VIDEO/AUDIO (Android 13+)
เข้าถึงไฟล์ทั้งเครื่องMANAGE_EXTERNAL_STORAGE (special, ต้องมีเหตุผล)
// Photo Picker (Android 13+) — เลือกรูปโดยไม่ต้องขอ permission เลย
val picker = registerForActivityResult(
    ActivityResultContracts.PickVisualMedia()
) { uri -> if (uri != null) showImage(uri) }

picker.launch(PickVisualMediaRequest(ActivityResultContracts.PickVisualMedia.ImageOnly))
แนวทางปัจจุบัน: ใช้ Photo Picker / Document Picker แทนการขอ storage permission — ปลอดภัยกว่าและไม่ต้องขอสิทธิ์

7. เก็บข้อมูลอย่างปลอดภัย

  • อย่าเก็บข้อมูลลับ (token/key/รหัสผ่าน) แบบ plain text ใน SharedPreferences/ไฟล์
  • EncryptedSharedPreferences — เก็บ key-value แบบเข้ารหัส (Jetpack Security)
  • Android Keystore — เก็บ cryptographic key ในฮาร์ดแวร์ (ถอดออกไม่ได้)
  • ระวัง Auto Backup — ข้อมูลอ่อนไหวอาจถูก backup ขึ้น cloud → ตั้ง exclude rules
// EncryptedSharedPreferences — เก็บ token แบบเข้ารหัส
val masterKey = MasterKey.Builder(context)
    .setKeyScheme(MasterKey.KeyScheme.AES256_GCM).build()

val securePrefs = EncryptedSharedPreferences.create(
    context, "secure_prefs", masterKey,
    EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
    EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
)
securePrefs.edit().putString("token", token).apply()   // เข้ารหัสอัตโนมัติ
อย่า hardcode API key/secret ในโค้ด (ถอด APK อ่านได้) — เก็บฝั่ง server หรือ ใช้กลไกที่ปลอดภัย; secret ที่ต้องมีในแอปให้จำกัดสิทธิ์ให้น้อยสุด

8. ความปลอดภัยด้านเครือข่าย

  • ใช้ HTTPS เสมอ — ตั้งแต่ Android 9 บล็อก HTTP (cleartext) โดยดีฟอลต์
  • Network Security Config — กำหนดนโยบาย TLS/cleartext ต่อ domain
  • Certificate pinning — ผูก certificate ของ server กันโดน man-in-the-middle
<!-- res/xml/network_security_config.xml -->
<network-security-config>
    <base-config cleartextTrafficPermitted="false" />  <!-- บล็อก HTTP -->
    <domain-config>
        <domain includeSubdomains="true">api.example.com</domain>
        <pin-set>
            <pin digest="SHA-256">base64hash...</pin>  <!-- cert pinning -->
        </pin-set>
    </domain-config>
</network-security-config>

9. การป้องกัน component

  • exported=false — ถ้า Activity/Service/Receiver ไม่ต้องการให้แอปอื่นเรียก ตั้งเป็น false (Android 12+ บังคับระบุ exported ชัดเจน)
  • ตรวจ Intent ที่รับเข้ามา — validate ข้อมูลจากภายนอก (untrusted input)
  • ป้องกัน SQL injection — ใช้ parameterized query (Room ทำให้อยู่แล้ว)
  • PendingIntent — ระบุ FLAG_IMMUTABLE (Android 12+ บังคับ)
  • ContentProvider — กำหนด permission ถ้า export
<service
    android:name=".MyService"
    android:exported="false" />  <!-- ไม่ให้แอปอื่นเรียก -->

10. ความปลอดภัยอื่น ๆ ที่ควรรู้

  • Biometric — ยืนยันตัวตนด้วยลายนิ้วมือ/ใบหน้า (BiometricPrompt)
  • App signing / Play App Signing — เซ็นแอปยืนยันตัวตนผู้พัฒนา
  • Code obfuscation (R8/ProGuard) — ย่อ/สับสนโค้ดกันถอด (ไม่ใช่การเข้ารหัส)
  • SafetyNet / Play Integrity API — ตรวจว่าแอป/เครื่องไม่ถูกดัดแปลง (root/emulator)
  • ไม่ log ข้อมูลอ่อนไหว — token/รหัสผ่านห้ามอยู่ใน Logcat
  • Clipboard/Screenshot — ป้องกันหน้าจอที่มีข้อมูลลับ (FLAG_SECURE)
เจาะลึกความปลอดภัยเชิงการเขียนโค้ด (injection, WebView, Intent/deep link, IPC, secret management, anti-tamper, dependency พร้อมโค้ด ผิด/ถูก): ดู docs/android-secure-coding.html

11. ตารางเทียบความแตกต่างตามเวอร์ชัน Android

ระบบ permission/ความปลอดภัยเข้มขึ้นแทบทุกเวอร์ชัน — จุดเปลี่ยนสำคัญ:

เวอร์ชันAPIสิ่งที่เปลี่ยนเรื่อง permission/security

Android 826permission ให้ทีละ "กลุ่ม" ชัดขึ้น; จำกัด background
Android 928บล็อก HTTP (cleartext) โดยดีฟอลต์; background เข้าถึงกล้อง/ไมค์/เซ็นเซอร์ไม่ได้

Android 15/1635+privacy เข้มขึ้นต่อเนื่อง; จำกัดสิทธิ์อ่อนไหวมากขึ้น; เน้น minimal permission
บทสรุปเชิงประวัติ: ทิศทางทุกเวอร์ชันคือ ให้สิทธิ์แคบลง + ผู้ใช้คุมได้ มากขึ้น + ขอเฉพาะตอนใช้ — โค้ดที่ขอเท่าที่จำเป็น + เผื่อกรณีถูกปฏิเสธ/ได้แค่ coarse จะ รอดทุกเวอร์ชัน

12. ข้อดี / ข้อเสีย ของระบบ permission Android

  • ✅ ปกป้องความเป็นส่วนตัวผู้ใช้ — ควบคุมได้ว่าให้สิทธิ์อะไร
  • ✅ ขอเฉพาะตอนใช้ → ผู้ใช้เข้าใจบริบท ตัดสินใจง่าย
  • ✅ one-time/auto-reset → ลดความเสี่ยงสิทธิ์ค้าง
  • ✅ Scoped Storage/Photo Picker → เข้าถึงไฟล์ได้โดยไม่ต้องขอสิทธิ์กว้าง
  • ❌ โค้ดขอ permission ซับซ้อน (เช็ค/rationale/ปฏิเสธถาวร/settings)
  • ❌ พฤติกรรมต่างกันมากตามเวอร์ชัน → ต้องเทสต์หลายเวอร์ชัน
  • ❌ ผู้ใช้ปฏิเสธได้ → ต้องออกแบบ fallback ทุกกรณี
  • ❌ บาง permission (background location/storage) Play ตรวจเข้ม อาจถูกปฏิเสธ

14. ภาคปฏิบัติ: ขอ permission กล้องแบบครบ flow

ขั้น 1 — ประกาศใน Manifest

<uses-permission android:name="android.permission.CAMERA" />

ขั้น 2 — ViewModel เก็บ state (optional แต่แนะนำ)

data class CameraUiState(
    val hasPermission: Boolean = false,
    val showRationale: Boolean = false,
    val permanentlyDenied: Boolean = false
)

ขั้น 3 — Fragment: ลงทะเบียน launcher + flow ครบ

class CameraFragment : Fragment() {

    // ลงทะเบียน launcher ครั้งเดียว
    private val requestPermission = registerForActivityResult(
        ActivityResultContracts.RequestPermission()
    ) { granted ->
        if (granted) {
            openCamera()
        } else if (!shouldShowRequestPermissionRationale(Manifest.permission.CAMERA)) {
            // ปฏิเสธถาวร (Android 11+) → พาไป Settings
            showGoToSettingsDialog()
        } else {
            showDeniedMessage()
        }
    }

    fun onTakePhotoClick() {
        when {
            ContextCompat.checkSelfPermission(requireContext(), Manifest.permission.CAMERA)
                == PackageManager.PERMISSION_GRANTED -> openCamera()

            shouldShowRequestPermissionRationale(Manifest.permission.CAMERA) ->
                // เคยปฏิเสธ 1 ครั้ง → อธิบายก่อนขอใหม่
                showRationaleDialog(
                    onOk = { requestPermission.launch(Manifest.permission.CAMERA) }
                )

            else -> requestPermission.launch(Manifest.permission.CAMERA)   // ขอครั้งแรก
        }
    }

    private fun showGoToSettingsDialog() {
        // พาไปหน้า Settings ของแอปให้ผู้ใช้เปิดเอง
        val intent = Intent(Settings.ACTION_APPLICATION_DETAILS_SETTINGS,
            Uri.parse("package:${requireContext().packageName}"))
        startActivity(intent)
    }
}
flow นี้ครอบคลุมครบ: มีสิทธิ์แล้ว / ขอครั้งแรก / เคยปฏิเสธ (rationale) / ปฏิเสธ ถาวร (ไป Settings) — เป็น template มาตรฐานที่ใช้ได้ทุกแอป

14.1 permission อื่น ๆ — ส่วนใหญ่ "เหมือนกัน แค่เปลี่ยนชื่อ"

ข่าวดี: permission กลุ่ม dangerous ที่เป็น "อันเดียว" เกือบทั้งหมดใช้โค้ด flow เดียวกัน กับกล้องด้านบน — แค่เปลี่ยน 2 อย่าง: (1) ชื่อ permission ที่ launch (2) การกระทำเมื่อได้สิทธิ์

// เปลี่ยนแค่ตรงนี้จาก template กล้อง requestPermission.launch(Manifest.permission.XXX) // ← เปลี่ยนชื่อ onGranted = { doSomething() } // ← เปลี่ยนการกระทำ
ต้องการpermission (ใส่แทน CAMERA)โค้ด flow
ไมโครโฟน (อัดเสียง)RECORD_AUDIOเหมือนกล้องเป๊ะ
อ่านผู้ติดต่อREAD_CONTACTSเหมือนกล้องเป๊ะ
เขียนผู้ติดต่อWRITE_CONTACTSเหมือนกล้องเป๊ะ
ปฏิทินREAD_CALENDAR / WRITE_CALENDARเหมือนกล้องเป๊ะ
โทรศัพท์CALL_PHONE / READ_PHONE_STATEเหมือนกล้องเป๊ะ
SMSSEND_SMS / READ_SMSเหมือนกล้องเป๊ะ
เซ็นเซอร์ร่างกายBODY_SENSORSเหมือนกล้องเป๊ะ
แจ้งเตือน (Android 13+)POST_NOTIFICATIONSเหมือนกล้อง (ดู 14.2)
สรุป: ถ้าเป็น permission dangerous อันเดียว → ก๊อป template กล้อง แล้ว เปลี่ยนชื่อ permission พอ ไม่ต้องเขียนใหม่

14.2 กรณีที่ต้องเขียน "ต่าง" จาก template

ก) หลาย permission พร้อมกัน → ใช้ RequestMultiplePermissions

// เช่น ตำแหน่ง (fine+coarse) หรือ SMS อ่าน+ส่งพร้อมกัน
private val multiPerms = registerForActivityResult(
    ActivityResultContracts.RequestMultiplePermissions()   // ← ต่าง: Multiple
) { result: Map<String, Boolean> ->                        // ← ต่าง: ได้ Map
    when {
        result[Manifest.permission.ACCESS_FINE_LOCATION] == true -> useFine()
        result[Manifest.permission.ACCESS_COARSE_LOCATION] == true -> useApprox()
        else -> showDenied()
    }
}
multiPerms.launch(arrayOf(
    Manifest.permission.ACCESS_FINE_LOCATION,
    Manifest.permission.ACCESS_COARSE_LOCATION
))

ข) Background location → ต้องขอ "2 สเต็ป"

// ต้องได้ WHEN_IN_USE (foreground) ก่อน แล้วค่อยขอ background แยกอีกที
// (ขอพร้อมกันไม่ได้ตั้งแต่ Android 11)
private val bgLocation = registerForActivityResult(
    ActivityResultContracts.RequestPermission()
) { granted -> if (granted) startTracking() }

fun requestBackgroundLocation() {
    // สเต็ป 1: ต้องมี foreground location ก่อน (ขอด้วย template ปกติ)
    // สเต็ป 2: แล้วค่อยขอ background
    bgLocation.launch(Manifest.permission.ACCESS_BACKGROUND_LOCATION)
}
background location ต้องมีเหตุผลชัดมาก + Play รีวิวเข้ม — ขอเฉพาะเมื่อจำเป็นจริง

ค) Special permission → ไม่ใช่ dialog แต่พาไป Settings

// SYSTEM_ALERT_WINDOW / MANAGE_EXTERNAL_STORAGE / SCHEDULE_EXACT_ALARM
// เช็คด้วยเมธอดเฉพาะ (ไม่ใช่ checkSelfPermission) แล้วพาไป Settings
fun requestOverlay() {
    if (!Settings.canDrawOverlays(this)) {              // ← ต่าง: เช็คเฉพาะทาง
        startActivity(Intent(
            Settings.ACTION_MANAGE_OVERLAY_PERMISSION,
            Uri.parse("package:$packageName")))         // ← ต่าง: เปิด Settings
    }
}
special permissionเช็คด้วยSettings intent
SYSTEM_ALERT_WINDOWSettings.canDrawOverlays()ACTION_MANAGE_OVERLAY_PERMISSION
MANAGE_EXTERNAL_STORAGEEnvironment.isExternalStorageManager()ACTION_MANAGE_ALL_FILES_ACCESS_PERMISSION
SCHEDULE_EXACT_ALARMalarmManager.canScheduleExactAlarms()ACTION_REQUEST_SCHEDULE_EXACT_ALARM
REQUEST_INSTALL_PACKAGESpackageManager.canRequestPackageInstalls()ACTION_MANAGE_UNKNOWN_APP_SOURCES

ง) ไฟล์/รูป → ไม่ต้องขอ permission เลย (ใช้ Picker)

// แทนการขอ READ_MEDIA_IMAGES → ใช้ Photo Picker (ไม่ต้อง permission)
val picker = registerForActivityResult(
    ActivityResultContracts.PickVisualMedia()
) { uri -> if (uri != null) showImage(uri) }
picker.launch(PickVisualMediaRequest(ActivityResultContracts.PickVisualMedia.ImageOnly))

จ) POST_NOTIFICATIONS (Android 13+) → เหมือน template แต่ต้องเช็คเวอร์ชัน

fun askNotificationPermission() {
    if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.TIRAMISU) {   // ← ต่าง: เช็ค API 33+
        requestPermission.launch(Manifest.permission.POST_NOTIFICATIONS)
    }
    // ต่ำกว่า 13 ไม่ต้องขอ — ได้อัตโนมัติ
}

สรุปตารางว่า "ต่าง" ตรงไหน

กลุ่มต่างจาก template ยังไง
dangerous อันเดียว (กล้อง/ไมค์/ผู้ติดต่อ...)ไม่ต่าง — เปลี่ยนชื่อ permission พอ
หลายอันพร้อมกัน (ตำแหน่ง/SMS)ใช้ RequestMultiplePermissions (ได้ Map)
background locationขอ 2 สเต็ป (foreground ก่อน)
special (overlay/storage/alarm)เช็คเมธอดเฉพาะ + พาไป Settings
ไฟล์/รูปใช้ Picker ไม่ต้องขอ permission
POST_NOTIFICATIONStemplate ปกติ + เช็ค API 33+

15. ข้อผิดพลาดที่พบบ่อย

ข้อผิดพลาดผล / วิธีแก้
ขอ permission ทั้งหมดตอนเปิดแอปผู้ใช้ปฏิเสธ/ลบแอป → ขอตอนใช้จริงทีละอัน
ไม่เผื่อกรณีถูกปฏิเสธแอปแครช/ค้าง → ต้องมี fallback ทุกครั้ง
ไม่จัดการ "ปฏิเสธถาวร"ขอซ้ำ dialog ไม่ขึ้น → พาไป Settings
เก็บ token แบบ plain textรั่วง่าย → EncryptedSharedPreferences/Keystore
ใช้ HTTPถูกบล็อก (Android 9+)/ไม่ปลอดภัย → HTTPS
ขอ background location ทั้งที่ไม่จำเป็นPlay ปฏิเสธ → ขอ WHEN_IN_USE พอ
hardcode API key ในโค้ดถอด APK อ่านได้ → เก็บฝั่ง server
ลืม POST_NOTIFICATIONS (Android 13+)notification ไม่ขึ้น → ขอ runtime permission
ไม่ระบุ exported (Android 12+)ติดตั้ง/build ไม่ผ่าน → ระบุ exported ชัดเจน

16. แนวโน้มในอนาคต

  • สิทธิ์ยิ่งแคบลง + ผู้ใช้คุมมากขึ้น — selected photos, approximate location, one-time เป็นทิศทางที่ต่อเนื่อง
  • Photo/Document Picker แทน storage permission — เข้าถึงไฟล์โดยไม่ต้องขอสิทธิ์กว้าง
  • Play Integrity + passkeys — ยืนยันแอป/ตัวตนที่ปลอดภัยขึ้น (passwordless)
  • auto-reset permission ขยายผล — แอปที่ไม่ได้ใช้จะถูกถอนสิทธิ์อัตโนมัติ
  • privacy dashboard/indicator โปร่งใสขึ้น — ผู้ใช้เห็นว่าแอปใช้กล้อง/ไมค์/ตำแหน่งเมื่อไร
  • สรุป: ออกแบบแอปแบบ privacy-first + least privilege ตั้งแต่ต้น จะรอด นโยบายที่เข้มขึ้นเรื่อย ๆ และผ่านรีวิวของ Play ง่าย

17. ศัพท์ทางเทคนิค (Glossary)

  • Permission — สิทธิ์เข้าถึงข้อมูล/ฟีเจอร์อ่อนไหว
  • Normal / Dangerous / Signature / Special — ระดับความเสี่ยงของ permission
  • Runtime permission — permission ที่ขอตอนใช้งาน (dangerous, ตั้งแต่ API 23)
  • Activity Result API — วิธีปัจจุบันในการขอ permission/รับผลลัพธ์
  • shouldShowRequestPermissionRationale — เช็คว่าควรอธิบายเหตุผลก่อนขอไหม
  • one-time permission — อนุญาตเฉพาะครั้งนี้ (Android 11+)
  • Scoped Storage — เข้าถึงไฟล์แบบจำกัดขอบเขต (Android 10+)
  • Photo Picker — เลือกรูปโดยไม่ต้องขอ storage permission
  • EncryptedSharedPreferences — เก็บ key-value แบบเข้ารหัส
  • Android Keystore — ที่เก็บ key เข้ารหัสในฮาร์ดแวร์
  • Network Security Config — นโยบายความปลอดภัยเครือข่ายต่อ domain
  • Certificate pinning — ผูก cert ของ server กัน MITM
  • exported — component เปิดให้แอปอื่นเรียกได้ไหม
  • BiometricPrompt — ยืนยันตัวตนด้วยชีวมิติ (นิ้ว/หน้า)
  • Play Integrity API — ตรวจความน่าเชื่อถือของแอป/เครื่อง
  • FLAG_SECURE — ป้องกัน screenshot/บันทึกหน้าจอที่มีข้อมูลลับ
