การเชื่อม Google Calendar จาก Android

เอกสารนี้อธิบายวิธีให้แอป Android เขียน/จัดการ event บน Google Calendar แบบครบทุกวิธี พร้อมข้อดี/ข้อเสีย สิ่งที่ต้องคำนึงก่อนใช้ โค้ดตัวอย่างที่นำไปรันได้จริง ความปลอดภัย การทดสอบ และแนวโน้มในอนาคต อ่านจบแล้วเลือกและลงมือทำได้ทันที

ภาพรวม: มี 3 วิธีหลัก

การพา event ไปที่ Google Calendar ทำได้ 3 ทาง เรียงจาก ง่าย → ยืดหยุ่น:

  • วิธี 1 Intent — เปิดแอปปฏิทินพร้อมข้อมูล ให้ผู้ใช้กดบันทึกเอง (ไม่ต้องล็อกอิน/ไม่ต้อง permission)
  • วิธี 2 CalendarContract (CalendarProvider) — เขียนลงปฏิทินในเครื่องโดยตรง (ต้องขอ permission ปฏิทิน)
  • วิธี 3 Google Calendar API — คุยกับ Google โดยตรงผ่าน OAuth (ยืดหยุ่นสูงสุด แต่ตั้งค่าเยอะสุด)
เลือกเร็ว ๆ: แค่ช่วยผู้ใช้สร้าง event → วิธี 1 • เขียนเข้าปฏิทินเครื่องอัตโนมัติ → วิธี 2 • จัดการ event เต็มรูปแบบ/ข้ามอุปกรณ์/มี backend → วิธี 3

วิธี 1 (Intent) — แก้ไข / ลบ

สิ่งที่ต้องใช้: eventId (Long) ของ event ที่จะแก้  •  ได้มาจาก: ตอนสร้างด้วยวิธี 2/3 (วิธี 1 ตอนสร้างมักไม่คืน id) หรือ query จาก CalendarContract

import android.content.ContentUris
import android.content.Intent
import android.provider.CalendarContract

// ── แก้ไข: เปิดหน้าแก้ event ให้ "ผู้ใช้กดบันทึกเอง" (ไม่ใช่แก้เงียบ) ──
fun openEditEvent(activity: Activity, eventId: Long) {
    // สร้าง URI ชี้ไปยัง event ที่ต้องการ: content://com.android.calendar/events/{id}
    val uri = ContentUris.withAppendedId(
        CalendarContract.Events.CONTENT_URI,  // base URI ของตาราง events
        eventId                                // id ที่เก็บไว้ตอนสร้าง
    )
    // ACTION_EDIT = ขอให้แอปปฏิทินเปิด "หน้าแก้ไข" ของ event นี้
    val intent = Intent(Intent.ACTION_EDIT).apply {
        data = uri
        putExtra(CalendarContract.Events.TITLE, "ชื่อใหม่ (ค่าเริ่มต้นในฟอร์ม)")
    }
    if (intent.resolveActivity(activity.packageManager) != null) {
        activity.startActivity(intent)  // ผู้ใช้จะเห็นหน้าแก้ไข แล้วกดบันทึกเอง
    }
}

// ── ลบ: ไม่มี Intent มาตรฐานสำหรับ "ลบ" โดยตรง ──
// ทำได้แค่ ACTION_VIEW เปิด event ให้ผู้ใช้ไปกดลบเองในแอปปฏิทิน
fun openViewEvent(activity: Activity, eventId: Long) {
    val uri = ContentUris.withAppendedId(CalendarContract.Events.CONTENT_URI, eventId)
    activity.startActivity(Intent(Intent.ACTION_VIEW).setData(uri))
    // → ถ้าต้องการ "ลบอัตโนมัติ" ให้ใช้วิธี 2 หรือ 3 แทน
}
วิธี 1 จึงเหมาะกับ "สร้าง/ให้ผู้ใช้แก้" เท่านั้น — ถ้าต้องลบอัตโนมัติต้องใช้วิธี 2/3

วิธี 2 (CalendarContract) — แก้ไข / ลบ (อัตโนมัติ)

สิ่งที่ต้องใช้: ContentResolver + eventId (Long) + permission WRITE_CALENDAR  •  ได้มาจาก: context.contentResolver, และ eventId ได้จาก uri.lastPathSegment.toLong() ตอน insert (ดูหัวข้อ 2.4)

import android.content.ContentResolver
import android.content.ContentUris
import android.content.ContentValues
import android.provider.CalendarContract

// ── แก้ไข event บนเครื่อง (เงียบ ไม่มี UI) ──
fun updateEvent(resolver: ContentResolver, eventId: Long): Int {
    // URI ชี้ไปยัง event ที่ต้องการแก้ (base URI + id)
    val uri = ContentUris.withAppendedId(CalendarContract.Events.CONTENT_URI, eventId)

    // ใส่เฉพาะฟิลด์ที่อยากเปลี่ยน (ฟิลด์อื่นคงเดิม)
    val values = ContentValues().apply {
        put(CalendarContract.Events.TITLE, "ประชุมทีม (เลื่อนเวลา)")
        put(CalendarContract.Events.DTSTART, System.currentTimeMillis() + 3600_000)
    }

    // update() คืนจำนวนแถวที่แก้สำเร็จ (ควรได้ 1) — ต้องมี WRITE_CALENDAR
    return resolver.update(uri, values, null, null)
}

// ── ลบ event บนเครื่อง ──
fun deleteEvent(resolver: ContentResolver, eventId: Long): Int {
    val uri = ContentUris.withAppendedId(CalendarContract.Events.CONTENT_URI, eventId)
    // delete() คืนจำนวนแถวที่ลบ (ควรได้ 1)
    return resolver.delete(uri, null, null)
}
ต้องได้รับ runtime permission WRITE_CALENDAR ก่อน (ดูหัวข้อ 2.2) มิฉะนั้นจะเกิด SecurityException

วิธี 3 (Calendar API) — แก้ไข / ลบ (อัตโนมัติ, คุยกับ Google ตรง)

สิ่งที่ต้องใช้: Calendar service (ที่ auth แล้ว) + calendarId (เช่น "primary") + eventId (String)  •  ได้มาจาก: buildCalendarService() (หัวข้อ 3.3), และ eventId ได้จาก created.id ตอนสร้าง (หัวข้อ 3.3)

import com.google.api.client.util.DateTime
import com.google.api.services.calendar.Calendar
import com.google.api.services.calendar.model.Event
import kotlinx.coroutines.Dispatchers
import kotlinx.coroutines.withContext

// ── แก้ไข: ต้อง get ของเดิมมาก่อน แล้วแก้ฟิลด์ แล้ว update กลับ ──
suspend fun updateEvent(
    service: Calendar,      // client ที่ผ่าน OAuth แล้ว (หัวข้อ 3.3)
    calendarId: String,     // "primary" = ปฏิทินหลักของผู้ใช้
    eventId: String         // id ที่เก็บไว้จาก created.id ตอนสร้าง
): Event = withContext(Dispatchers.IO) {   // API = network I/O → ต้องอยู่ IO thread

    // 1) ดึง event ปัจจุบันจาก Google (กันการเขียนทับฟิลด์อื่นโดยไม่ตั้งใจ)
    val event = service.events().get(calendarId, eventId).execute()

    // 2) แก้เฉพาะฟิลด์ที่ต้องการ
    event.summary = "ประชุมทีม (อัปเดต)"
    event.start.dateTime = DateTime(System.currentTimeMillis() + 3600_000)
    event.end.dateTime = DateTime(System.currentTimeMillis() + 7200_000)

    // 3) ส่งกลับไปอัปเดตบน Google (คืน Event ที่อัปเดตแล้ว)
    service.events().update(calendarId, eventId, event).execute()
}

// ── ลบ event ออกจาก Google โดยตรง ──
suspend fun deleteEvent(
    service: Calendar,
    calendarId: String,
    eventId: String
) = withContext(Dispatchers.IO) {
    // delete ไม่มีค่าคืน — สำเร็จ = ไม่ throw; ถ้า id ไม่มีจะได้ 404/410
    service.events().delete(calendarId, eventId).execute()
}
ทุกการเรียกเป็น network I/O → ต้องอยู่บน Dispatchers.IO เสมอ • ถ้า token หมดอายุต้อง handle การ re-auth
สรุป: ต้องการ แก้/ลบอัตโนมัติ → เลือก วิธี 2 (บนเครื่อง ง่ายกว่า) หรือ วิธี 3 (เต็มรูปแบบ ข้ามอุปกรณ์) • วิธี 1 ทำได้แค่พาผู้ใช้ไปแก้/ดูเอง และลบอัตโนมัติไม่ได้

การตั้งการเตือน (reminder) ของทั้ง 3 วิธี

ตั้งเตือนได้ ทั้ง 3 วิธี — ต่างกันแค่ที่วางโค้ด หลักการเหมือนกัน:

  • ไม่กำหนด reminder เอง → event ใช้ การเตือนเริ่มต้นของปฏิทิน (default reminder) ซึ่ง ผู้ใช้ตั้งเองได้ — อาจมีเตือน (เช่น default 30 นาที) หรือไม่มีเลย ถ้า default ปิดอยู่
  • กำหนดเอง → เตือนตามที่ตั้งแน่นอน (ควบคุมได้)
อยากให้เตือนแน่ ๆ ต้องกำหนดเอง — เพราะเราคุม default ของปฏิทินผู้ใช้ไม่ได้

วิธี 1 (Intent) — ตั้งเป็นค่าเริ่มต้นในฟอร์ม

val intent = Intent(Intent.ACTION_INSERT).apply {
    data = CalendarContract.Events.CONTENT_URI
    putExtra(CalendarContract.Events.TITLE, "ประชุมทีม")
    // ตั้งเตือนล่วงหน้า 30 นาที เป็น "ค่าเริ่มต้นในฟอร์ม"
    // → ผู้ใช้ยังปรับ/ลบได้ก่อนกดบันทึก (ควบคุมไม่ได้ 100%)
    putExtra(CalendarContract.Reminders.MINUTES, 30)
}

วิธี 2 (CalendarContract) — insert ลงตาราง Reminders

// 1) ตอน insert event ควรตั้ง HAS_ALARM = 1 ให้ระบบรู้ว่า event นี้มีเตือน
val values = ContentValues().apply {
    // ...ฟิลด์อื่น ๆ (DTSTART/DTEND/TITLE/CALENDAR_ID/EVENT_TIMEZONE)...
    put(CalendarContract.Events.HAS_ALARM, 1)   // สำคัญ: บอกว่ามีการเตือน
}
val uri = resolver.insert(CalendarContract.Events.CONTENT_URI, values)

// 2) แล้วเพิ่มรายการเตือนโยงกับ eventId
val eventId = uri!!.lastPathSegment!!.toLong()   // id จาก uri ที่ได้ตอน insert
val reminder = ContentValues().apply {
    put(CalendarContract.Reminders.EVENT_ID, eventId)
    put(CalendarContract.Reminders.MINUTES, 30)            // เตือนก่อน 30 นาที
    put(CalendarContract.Reminders.METHOD,
        CalendarContract.Reminders.METHOD_ALERT)             // เด้งแจ้งเตือนบนเครื่อง
}
resolver.insert(CalendarContract.Reminders.CONTENT_URI, reminder)
// ถ้าข้ามขั้นนี้ → event จะใช้ default reminder ของปฏิทินแทน
METHOD ที่ใช้ได้: METHOD_ALERT (เด้งเตือน), METHOD_EMAIL (อีเมล), METHOD_DEFAULT

วิธี 3 (Calendar API) — set property reminders ของ Event

import com.google.api.services.calendar.model.Event
import com.google.api.services.calendar.model.EventReminder

event.reminders = Event.Reminders()
    .setUseDefault(false)   // false = ไม่ใช้ default ของปฏิทิน, ใช้ที่เรากำหนด
    .setOverrides(listOf(
        EventReminder().setMethod("popup").setMinutes(30),  // เด้งเตือน 30 นาทีก่อน
        EventReminder().setMethod("email").setMinutes(60)   // อีเมลเตือน 60 นาทีก่อน
    ))
service.events().insert("primary", event).execute()

// ถ้าอยากใช้การเตือนเริ่มต้นของปฏิทินแทน:
// event.reminders = Event.Reminders().setUseDefault(true)

การป้องกัน event ซ้ำ

Calendar ไม่กันซ้ำให้อัตโนมัติ — ถ้าเรียกสร้าง 2 ครั้งด้วยข้อมูลเดียวกัน จะได้ 2 event คนละ id เพราะระบบมองเป็นคนละรายการ

เมื่อไรที่เกิดซ้ำ

  • ผู้ใช้กดปุ่มซ้ำ / กดรัว
  • retry ตอนเน็ตหลุด (ส่งสำเร็จแต่ response ไม่กลับ → โค้ด retry → สร้างซ้ำ)
  • หมุนจอ/สร้าง Activity ใหม่ แล้วเรียกสร้างซ้ำใน onCreate
  • sync หลายเครื่อง (วิธี 3) ที่ logic ซ้ำกัน

ก่อนอื่น: จะใช้ "อะไร" เป็นตัวเช็คว่าซ้ำ?

การกันซ้ำทั้งหมดขึ้นกับ "ตัวระบุ (key)" ที่ใช้เทียบ — เลือกให้ถูกสำคัญกว่าตัวโค้ด:

ตัวเช็คความแม่นใช้ตอนไหน
title + DTSTART (ชื่อ+เวลาเริ่ม)⚠️ ปานกลาง (heuristic)เช็คก่อน insert ครั้งแรก เมื่อไม่มี key อื่น
orderId ของเราเอง (custom key)✅ แม่นฝังไว้ตอนสร้าง แล้ว query/lookup ด้วย key นี้
event_id (id ที่ระบบสร้าง)✅ แม่นสุดเฉพาะหลังสร้างแล้ว (เช็คว่าของเดิมยังอยู่ไหม)
เรื่อง event_id ที่มักเข้าใจผิด: ใช้ event_id เช็คได้ก็ต่อเมื่อ รู้ id นั้นอยู่ก่อนแล้ว — แต่ event_id เกิด หลัง insert สำเร็จเท่านั้น จึงเอามา เช็ค "ก่อน insert ครั้งแรก" ไม่ได้ (ไก่กับไข่) • event_id เหมาะกับ "เช็คว่าของที่เคยสร้างยัง อยู่ไหม" ไม่ใช่ "กำลังจะสร้างของซ้ำหรือเปล่าตอนยังไม่เคยสร้าง"

แนวทาง 1 — Query เช็คก่อน insert (วิธี 2)

ตอน insert ครั้งแรกเรายัง ไม่มี event_id ให้เทียบ จึงต้องเช็คด้วยเนื้อหา event (title + DTSTART) แทน:

import android.content.ContentResolver
import android.provider.CalendarContract

// คืน true ถ้ามี event ชื่อเดียวกัน + เวลาเริ่มเดียวกันอยู่แล้ว
fun eventExists(resolver: ContentResolver, title: String, startMillis: Long): Boolean {
    // เลือกเงื่อนไข "ชื่อ = ? และเวลาเริ่ม = ?" (ปรับ field ให้เหมาะกับกรณีของคุณ)
    val selection = "${CalendarContract.Events.TITLE} = ? AND " +
                    "${CalendarContract.Events.DTSTART} = ?"
    val args = arrayOf(title, startMillis.toString())

    resolver.query(
        CalendarContract.Events.CONTENT_URI,
        arrayOf(CalendarContract.Events._ID),  // ขอแค่คอลัมน์ id พอ
        selection, args, null
    )?.use { cursor ->
        return cursor.count > 0   // มีอย่างน้อย 1 แถว = ซ้ำ
    }
    return false
}

// ใช้งาน: insert เฉพาะเมื่อยังไม่มี
if (!eventExists(resolver, "สั่งอาหาร #1234", startMillis)) {
    resolver.insert(CalendarContract.Events.CONTENT_URI, values)
}
ข้อจำกัดของการเช็ค title + DTSTART (เป็นแค่ heuristic/การเดา):
  • ชนผิด (false positive): 2 event ที่ตั้งใจให้ชื่อ+เวลาเดียวกันจริง ๆ จะถูกมองว่าซ้ำ
  • พลาด (false negative): ผู้ใช้แก้ชื่อ/เวลานิดเดียว ก็เช็คไม่เจอ → ซ้ำอยู่ดี
  • DTSTART ต้องตรงเป๊ะระดับ millisecond
  • มี race condition ได้ถ้ากดรัวเร็วมาก (เช็คพร้อมกันก่อนอีกอัน insert เสร็จ)
แม่นกว่า: ฝัง "คีย์ของเราเอง" (เช่น orderId) ลง event ตอนสร้าง แล้ว query ด้วยคีย์นั้นแทนการเดาจากชื่อ/เวลา — เก็บใน custom field เช่น Events._SYNC_ID หรือใช้แนวทาง 3 (เก็บ mapping ฝั่งแอป)

แนวทาง 2 — กำหนด event.id เอง แล้วดัก 409 (วิธี 3, กันได้เด็ดขาดสุด)

import com.google.api.client.googleapis.json.GoogleJsonResponseException
import com.google.api.services.calendar.Calendar
import com.google.api.services.calendar.model.Event

// สร้าง id แบบ deterministic จากข้อมูลของเราเอง (เช่น orderId)
// กติกา Google: ใช้ตัวอักษร base32hex → a-v และ 0-9 ยาว 5–1024 ตัว
fun buildEventId(orderId: String): String =
    "order" + orderId.lowercase().filter { it in "abcdefghijklmnopqrstuv0123456789" }

suspend fun createEventOnce(service: Calendar, event: Event, orderId: String) =
    withContext(Dispatchers.IO) {
        // กำหนด id เอง → id เดียวกันเสมอสำหรับ order นี้
        event.id = buildEventId(orderId)
        try {
            // ครั้งแรก = สร้างสำเร็จ
            service.events().insert("primary", event).execute()
        } catch (e: GoogleJsonResponseException) {
            if (e.statusCode == 409) {
                // 409 Conflict = มี event id นี้อยู่แล้ว → ไม่สร้างซ้ำ
                // เลือกได้: ข้ามไปเฉย ๆ หรือ update ทับด้วยข้อมูลใหม่
                service.events().update("primary", event.id, event).execute()
            } else throw e   // error อื่นโยนต่อ
        }
    }
วิธีนี้ให้ Google เป็นคนกันซ้ำ ด้วย id ที่เรากำหนด — กันได้แม้ retry/ หลายเครื่อง เพราะ id เดียวกันจะชนกันที่เซิร์ฟเวอร์เสมอ

แนวทาง 3 — เก็บ mapping id ไว้ฝั่งแอป แล้ว upsert (ครอบทุกวิธี)

// ตาราง Room ที่โยง "ข้อมูลต้นทางของเรา" ↔ "event id ที่สร้างไว้"
@Entity
data class CalendarLink(
    @PrimaryKey val orderId: String,   // คีย์ของข้อมูลเราเอง
    val eventId: String                // id ที่ Calendar คืนมาตอนสร้าง
)

suspend fun upsertEvent(service: Calendar, dao: CalendarLinkDao, orderId: String, event: Event) =
    withContext(Dispatchers.IO) {
        val existing = dao.findByOrderId(orderId)   // เคยสร้าง event ของ order นี้ไหม
        if (existing == null) {
            // ยังไม่เคย → สร้างใหม่ แล้วเก็บ mapping
            val created = service.events().insert("primary", event).execute()
            dao.insert(CalendarLink(orderId, created.id))
        } else {
            // เคยแล้ว → update ทับ (ไม่สร้างซ้ำ)
            service.events().update("primary", existing.eventId, event).execute()
        }
    }

การกันซ้ำในสถานการณ์จริง (หลายเครื่อง / หลายบัญชี / sync)

หัวข้อก่อนหน้าเป็นการกันซ้ำ "พื้นฐาน" ที่พอสำหรับเครื่องเดียว แต่ในโลกจริงมีหลายเครื่อง หลายบัญชี และ sync ที่ไม่ทันกัน — ส่วนนี้รวบทุกเคสและสถาปัตยกรรมที่ตอบโจทย์

2 หลักคิดที่ต้องจำ:
  1. ปฏิทิน Google อยู่บน cloud ไม่ใช่บนเครื่อง — เขียน event = เขียนลงปฏิทินของ "บัญชี" บน cloud แล้วอุปกรณ์ทุกเครื่องที่ล็อกอินบัญชีนั้น sync ลงมาเอง
  2. ตัวกันซ้ำต้องอยู่ที่ "จุดกลางจุดเดียว" — ถ้ากันซ้ำแบบต่างเครื่องต่างเช็คกันเอง จะพลาดเสมอ เพราะแต่ละเครื่องไม่รู้ว่าอีกเครื่องทำอะไรไปแล้ว

เคสต่าง ๆ และผลลัพธ์

เคส 1 — หลายเครื่อง บัญชี Google เดียวกัน (sync race)

เครื่อง A สร้าง event → เครื่อง B เปิดแอปก่อน sync ของ A จะมาถึง → B เช็คแล้ว "ไม่เจอ" → เขียนซ้ำ → พอ sync มาก็ได้ 2 อัน

timeline:
t1  เครื่อง A: สร้าง event ลงปฏิทินบัญชี G (ขึ้น cloud)
t2  เครื่อง B: จะสร้าง → query ปฏิทินก่อน แต่ยัง sync ของ A ไม่ถึง → ไม่เจอ → เขียนใหม่
t3  เครื่อง B: sync ของ A ลงมา → ปฏิทิน B มี 2 event  ← ซ้ำ
สาเหตุ: sync ไม่ใช่ real-time + การ "query เช็คก่อนเขียน" เป็นการ เช็คกับข้อมูลที่อาจล้าสมัย → มีช่องว่างให้เขียนซ้ำ

เคส 2 — หลายเครื่อง บัญชี Google คนละบัญชี

ปฏิทินผูกกับบัญชี — บัญชี A กับ B แยกกันสิ้นเชิง event.id ซ้ำได้ข้ามบัญชี และปฏิทินไม่ sync ข้ามบัญชี → กลไกที่พึ่ง Google กันไม่ได้

ต้องนิยามก่อนว่า "order เดียวลง 2 ปฏิทินคนละบัญชี" ถือว่าซ้ำไหม — ถ้าคนละคน/ คนละปฏิทินอาจไม่ใช่ซ้ำ • ถ้าต้องการ "order เดียว = event เดียวในโลก" → Google ช่วย ไม่ได้ ต้องมี backend กลาง

เคส 3 — สร้าง event ตอนเครื่องยังไม่ล็อกอิน Google

event จะไปอยู่ ปฏิทิน local ของเครื่อง • พอผู้ใช้ล็อกอินบัญชี A ภายหลัง event local ไม่ย้ายเข้า A + event ของ A ที่ sync ลงมา → เห็น 2 อัน = ซ้ำ

กลไก 409/query/Room กันเคสนี้ไม่ทัน เพราะ ณ ตอนสร้าง เครื่องยังไม่มีข้อมูล ของบัญชี A เลย

fun loadCalendars(resolver: ContentResolver): List<CalendarOption> {
    val proj = arrayOf(
        CalendarContract.Calendars._ID,
        CalendarContract.Calendars.ACCOUNT_NAME,               // เช่น a@gmail.com
        CalendarContract.Calendars.CALENDAR_DISPLAY_NAME
    )
    // กรองเฉพาะปฏิทินที่ "เขียนได้"
    val sel = "${CalendarContract.Calendars.CALENDAR_ACCESS_LEVEL} >= " +
              "${CalendarContract.Calendars.CAL_ACCESS_CONTRIBUTOR}"
    val out = mutableListOf<CalendarOption>()
    resolver.query(CalendarContract.Calendars.CONTENT_URI, proj, sel, null, null)
        ?.use { c -> while (c.moveToNext())
            out += CalendarOption(c.getLong(0), c.getString(1), c.getString(2)) }
    return out   // เอาไปโชว์ใน dialog ให้ผู้ใช้เลือก
}

สถาปัตยกรรมที่แนะนำ (แยกตามเป้าหมาย)

เป้าหมาย A — event เดียวไม่ซ้ำทุกเครื่อง + ล็อกอินแอปได้หลายแบบ

ใช้ วิธี 3 (Calendar API) เรียกจาก backend เป็น server-authoritative:

backend เรา (แหล่งความจริงกลาง)
  ├─ เก็บ refresh token ของบัญชี Google ที่ผู้ใช้ผูก (ผูกกับ appUserId)
  ├─ ตาราง event: UNIQUE (appUserId, orderId) → googleEventId
  └─ เป็นคนเรียก Google Calendar API เขียน event

client ทุกเครื่อง → เรียก API ของ backend เรา (ไม่เขียนปฏิทินเอง)
  • appUserId เป็นคีย์กันซ้ำ (ไม่ผูกกับวิธีล็อกอิน) — ล็อกอินแบบไหนก็ได้
  • UNIQUE (appUserId, orderId) ที่ DB → กัน race แม้ 2 เครื่องยิงพร้อมกัน
  • backend เขียนผ่าน refresh token → ไม่สนว่าเครื่องล็อกอิน Google หรือยัง
  • เสริม client-generated event.id → Google คืน 409 เป็นด่านสอง
server รู้ได้ไงว่าเขียนลงปฏิทินไหน: ไม่ได้ "ยิงไปที่เครื่อง" — server เขียนลงปฏิทินของ บัญชี บน cloud ผ่าน refresh token ที่ผูกกับ appUserId แล้ว Google sync ลงทุกเครื่องเอง (เหมือนส่งเข้า mailbox ไม่ใช่ส่งไปที่โทรศัพท์)

เป้าหมาย B — ต้องเห็นในปฏิทินบนเครื่อง แม้ไม่ล็อกอิน Google

ใช้ วิธี 2 (CalendarContract) ให้แอปดึง event จาก backend แล้วเขียนลงปฏิทิน local ของแต่ละเครื่อง:

backend (แหล่งข้อมูล event + ปลายทางปฏิทินที่เลือก ผูก appUserId)
        │  แอปดึงรายการตาม appUserId
        ▼

        ▼

  • กันซ้ำต้องพึ่ง backend (ไม่ใช่ sync ปฏิทิน) + mapping local ต่อเครื่องผูก (appUserId, orderId)
  • ยอมรับว่า event ถูกเขียน หนึ่งชุดต่อเครื่อง (ปฏิทิน local ไม่ sync ข้ามเครื่อง)
  • ถ้าเลือกลงปฏิทินที่เป็น Google account → จะ sync ข้ามเครื่องให้ (ได้ประโยชน์ทั้งคู่)

reconciliation — ตาข่ายกันพลาดชั้นสุดท้าย

ในระบบกระจาย การกัน "ก่อนเกิด" อาจพลาด จึงควรมีการเก็บกวาด "หลังเกิด":

  • ฝัง orderId ลงทุก event (เช่นใน description / extended property / _SYNC_ID)
  • เป็นระยะ/หลัง sync → query event ที่มี orderId เดียวกัน ถ้าเจอ >1 → เก็บตัวเก่าสุด ลบที่เหลือ

วิธีที่ 1 — Intent (ง่ายสุด)

ส่ง Intent ให้แอปปฏิทิน (Google Calendar หรือแอปปฏิทินใดก็ได้) เปิดหน้า "สร้าง event" พร้อมข้อมูลที่กรอกไว้ให้ล่วงหน้า แล้ว ผู้ใช้กดบันทึกเอง ไม่ต้องล็อกอิน ไม่ต้องขอ permission ไม่ต้องตั้งค่าอะไรเลย

1.1 สร้าง event (โค้ดเต็ม รันได้จริง)

import android.content.Intent
import android.provider.CalendarContract
import java.util.Calendar

fun openCreateEventInCalendar(activity: Activity) {
    // เวลาเริ่ม: พรุ่งนี้ 14:00 / เวลาจบ 15:00 (ตัวอย่าง)
    val begin = Calendar.getInstance().apply {
        add(Calendar.DAY_OF_YEAR, 1)
        set(Calendar.HOUR_OF_DAY, 14); set(Calendar.MINUTE, 0)
    }
    val end = (begin.clone() as Calendar).apply { add(Calendar.HOUR_OF_DAY, 1) }

    val intent = Intent(Intent.ACTION_INSERT).apply {
        data = CalendarContract.Events.CONTENT_URI
        putExtra(CalendarContract.Events.TITLE, "ประชุมทีม")
        putExtra(CalendarContract.Events.EVENT_LOCATION, "ห้องประชุม A")
        putExtra(CalendarContract.Events.DESCRIPTION, "วาระ: สรุปสปรินต์")
        putExtra(CalendarContract.EXTRA_EVENT_BEGIN_TIME, begin.timeInMillis)
        putExtra(CalendarContract.EXTRA_EVENT_END_TIME, end.timeInMillis)
        // putExtra(Intent.EXTRA_EMAIL, "a@x.com,b@y.com") // เชิญผู้เข้าร่วม
        // putExtra(CalendarContract.Events.ALL_DAY, true)   // ทั้งวัน
    }
    // ป้องกันกรณีไม่มีแอปปฏิทิน
    if (intent.resolveActivity(activity.packageManager) != null) {
        activity.startActivity(intent)
    } else {
        Toast.makeText(activity, "ไม่พบแอปปฏิทิน", Toast.LENGTH_SHORT).show()
    }
}
ผลลัพธ์: เปิดหน้าสร้าง event ในแอปปฏิทินพร้อมข้อมูลครบ ผู้ใช้แค่กด "บันทึก"

1.2 ข้อดี / ข้อเสีย

  • ✅ ไม่ต้องขอ permission, ไม่ต้อง OAuth, ไม่ต้อง config อะไรเลย
  • ✅ ปลอดภัยเรื่อง privacy — ผู้ใช้เห็นและควบคุมทุกอย่าง
  • ✅ ใช้ได้กับแอปปฏิทินทุกยี่ห้อ ไม่ผูกกับ Google อย่างเดียว
  • ❌ ไม่ใช่การเขียนอัตโนมัติ — ผู้ใช้ต้องกดยืนยันทุกครั้ง
  • ❌ ควบคุมรายละเอียด/ปฏิทินปลายทางไม่ได้ 100%
  • ❌ อ่าน/แก้/ลบ event ที่มีอยู่ไม่ได้
เหมาะเมื่อ: อยากช่วยผู้ใช้สร้าง event สะดวก ๆ โดยไม่แตะข้อมูลปฏิทินเอง

2.3 หา calendar_id ปลายทาง (เลือกปฏิทิน Google)

// คืน id ของปฏิทินหลักของบัญชี Google ที่ต้องการ (เช่น me@gmail.com)
fun findGoogleCalendarId(resolver: ContentResolver, accountEmail: String): Long? {
    val proj = arrayOf(CalendarContract.Calendars._ID)
    val sel = "${CalendarContract.Calendars.ACCOUNT_NAME} = ? AND " +
              "${CalendarContract.Calendars.ACCOUNT_TYPE} = ?"
    val args = arrayOf(accountEmail, "com.google")
    resolver.query(CalendarContract.Calendars.CONTENT_URI, proj, sel, args, null)
        ?.use { c -> if (c.moveToFirst()) return c.getLong(0) }
    return null
}

2.3.1 เลือกปฏิทินปลายทางครั้งแรก (โค้ดเต็ม)

เครื่องมีหลายปฏิทิน (หลายบัญชี + local) จึงควรให้ผู้ใช้เลือกปลายทางครั้งแรก แล้วจำไว้ — ทำ 4 ขั้น: (1) query ปฏิทินที่เขียนได้ → (2) โชว์ dialog ให้เลือก → (3) เก็บค่าที่เลือก → (4) ตอนจะเขียน event แปลงกลับเป็น CALENDAR_ID ของเครื่องนี้

ขั้น 1 — query ปฏิทินที่ "เขียนได้" ในเครื่อง

import android.content.ContentResolver
import android.provider.CalendarContract

// ข้อมูล 1 ปฏิทินที่จะเอาไปโชว์ให้ผู้ใช้เลือก
data class CalendarOption(
    val id: Long,            // CALENDAR_ID (เลขเฉพาะเครื่อง — ใช้ตอน insert)
    val accountName: String, // เช่น a@gmail.com (คงที่ข้ามเครื่อง → ใช้เก็บ)
    val displayName: String, // ชื่อที่โชว์ให้ผู้ใช้เห็น
    val isPrimary: Boolean    // เป็นปฏิทินหลักของบัญชีไหม (ไว้ตั้ง default)
)

fun loadWritableCalendars(resolver: ContentResolver): List<CalendarOption> {
    // คอลัมน์ที่ขอ
    val projection = arrayOf(
        CalendarContract.Calendars._ID,
        CalendarContract.Calendars.ACCOUNT_NAME,
        CalendarContract.Calendars.CALENDAR_DISPLAY_NAME,
        CalendarContract.Calendars.IS_PRIMARY,
        CalendarContract.Calendars.CALENDAR_ACCESS_LEVEL
    )
    // กรองเฉพาะปฏิทินที่มีสิทธิ์ "เขียน" (ตั้งแต่ระดับ CONTRIBUTOR ขึ้นไป)
    // เพื่อไม่ให้โชว์ปฏิทินอ่านอย่างเดียว (เช่น วันหยุด) ที่ insert ไม่ได้
    val selection = "${CalendarContract.Calendars.CALENDAR_ACCESS_LEVEL} >= ?"
    val args = arrayOf(CalendarContract.Calendars.CAL_ACCESS_CONTRIBUTOR.toString())

    val result = mutableListOf<CalendarOption>()
    resolver.query(
        CalendarContract.Calendars.CONTENT_URI, projection, selection, args, null
    )?.use { c ->
        // หา index ของแต่ละคอลัมน์ (กันตำแหน่งสลับ)
        val idIdx = c.getColumnIndexOrThrow(CalendarContract.Calendars._ID)
        val accIdx = c.getColumnIndexOrThrow(CalendarContract.Calendars.ACCOUNT_NAME)
        val nameIdx = c.getColumnIndexOrThrow(CalendarContract.Calendars.CALENDAR_DISPLAY_NAME)
        val primIdx = c.getColumnIndexOrThrow(CalendarContract.Calendars.IS_PRIMARY)

        while (c.moveToNext()) {
            result += CalendarOption(
                id = c.getLong(idIdx),
                accountName = c.getString(accIdx) ?: "",
                displayName = c.getString(nameIdx) ?: "",
                isPrimary = c.getInt(primIdx) == 1
            )
        }
    }
    return result
}

ขั้น 2 — โชว์ dialog ให้ผู้ใช้เลือก (พร้อมตั้ง default อัจฉริยะ)

import android.app.AlertDialog

fun showCalendarPicker(activity: Activity, appEmail: String?) {
    val calendars = loadWritableCalendars(activity.contentResolver)

    // ไม่มีปฏิทินให้เขียนเลย → แจ้งผู้ใช้ (อาจต้องสร้าง local calendar เอง)
    if (calendars.isEmpty()) { showNoCalendarError(); return }

    // เลือกตัวตั้งต้น (default) ให้ฉลาด:
    // 1) ปฏิทินที่ตรงกับอีเมลที่ล็อกอินแอป → 2) ปฏิทินหลัก (primary) → 3) อันแรก
    val defaultIndex = calendars.indexOfFirst { it.accountName == appEmail }
        .takeIf { it >= 0 }
        ?: calendars.indexOfFirst { it.isPrimary }.takeIf { it >= 0 }
        ?: 0

    // ถ้ามีปฏิทินเดียว ไม่ต้องถาม ใช้เลย
    if (calendars.size == 1) { saveSelectedCalendar(calendars[0]); return }

    // ข้อความแต่ละแถวในรายการเลือก
    val labels = calendars.map { "${it.displayName}\n${it.accountName}" }.toTypedArray()
    var chosen = defaultIndex

    AlertDialog.Builder(activity)
        .setTitle("เลือกปฏิทินสำหรับบันทึกนัดหมาย")
        .setSingleChoiceItems(labels, defaultIndex) { _, which -> chosen = which }
        .setPositiveButton("ตกลง") { _, _ ->
            saveSelectedCalendar(calendars[chosen])   // เก็บค่าที่เลือก
        }
        .setNegativeButton("ยกเลิก", null)
        .show()
}

ขั้น 3 — เก็บค่าที่เลือก (แนะนำเก็บ accountName)

// เก็บ "accountName" ไม่ใช่ CALENDAR_ID เพราะ id เป็นเลขเฉพาะเครื่อง
// (เครื่องอื่นจะได้ id คนละค่า) — ส่วน accountName คงที่ข้ามเครื่อง
// ในแอปจริงควรเก็บที่ backend ผูกกับ appUserId เพื่อให้ทุกเครื่องใช้ปลายทางเดียวกัน
fun saveSelectedCalendar(option: CalendarOption) {
    prefs.edit()
        .putString("calendar_account", option.accountName)
        .apply()
    // (ทางเลือก) backend.saveCalendarTarget(appUserId, option.accountName)
}

ขั้น 4 — ตอนจะเขียน event: แปลง accountName → CALENDAR_ID ของเครื่องนี้

// อ่าน accountName ที่เก็บไว้ แล้วหา CALENDAR_ID จริงบนเครื่องปัจจุบัน
// (ต้องหาใหม่ทุกเครื่อง เพราะ id ไม่เหมือนกัน)
fun resolveTargetCalendarId(resolver: ContentResolver): Long? {
    val account = prefs.getString("calendar_account", null) ?: return null
    return loadWritableCalendars(resolver)
        .firstOrNull { it.accountName == account }   // match ด้วย accountName
        ?.id                                          // ได้ CALENDAR_ID ไปใช้ insert
}

// ใช้งานจริง
val calendarId = resolveTargetCalendarId(resolver)
if (calendarId == null) {
    // ยังไม่เคยเลือก หรือปฏิทินที่เลือกหายไปจากเครื่อง → ให้เลือกใหม่
    showCalendarPicker(activity, appEmail)
} else {
    insertEvent(resolver, calendarId)   // เขียน event (หัวข้อ 2.4)
}
สรุป flow: query ปฏิทินที่เขียนได้ → ให้ผู้ใช้เลือก (ตั้ง default จาก อีเมลแอป/primary) → เก็บ accountName → ตอนเขียนค่อยแปลงเป็น CALENDAR_ID ของเครื่องนั้น • เก็บ accountName ไม่ใช่ id เพราะ id ต่างกันในแต่ละเครื่อง

2.3.2 เลือกปฏิทินอัตโนมัติ (ไม่ถามผู้ใช้)

ถ้าไม่อยากรบกวนให้ผู้ใช้เลือก สามารถเลือกปฏิทินให้อัตโนมัติตามลำดับความสำคัญ (heuristic) ได้ — เหมาะกับแอปที่อยากให้ "ใช้ได้เลย" แต่ควรมีทางให้เปลี่ยนภายหลังในหน้าตั้งค่า

ลำดับการเลือกอัตโนมัติ (priority)

1. ปฏิทินที่ accountName == อีเมลที่ล็อกอินแอป   (ตรงเจตนาผู้ใช้ที่สุด)
2. ปฏิทินหลัก (IS_PRIMARY = 1) ของบัญชี Google   (ปฏิทินหลักของเครื่อง)
3. ปฏิทิน Google ตัวแรกที่เขียนได้               (com.google)
4. ปฏิทิน local ตัวแรกที่เขียนได้                 (ถ้าไม่มี Google เลย)
5. ไม่มีเลย → สร้าง local calendar ของแอปเอง

โค้ดเลือกอัตโนมัติ

// เลือกปฏิทินปลายทางให้อัตโนมัติ คืน CALENDAR_ID (หรือ null ถ้าเลือกไม่ได้จริง ๆ)
fun autoPickCalendarId(resolver: ContentResolver, appEmail: String?): Long? {
    val calendars = loadWritableCalendars(resolver)   // จาก 2.3.1
    if (calendars.isEmpty()) return null            // ไม่มีปฏิทินเขียนได้เลย

    // ไล่ตามลำดับความสำคัญ — ตัวแรกที่เจอถือว่าเลือก
    val picked =
        // 1) ตรงกับอีเมลที่ล็อกอินแอป
        calendars.firstOrNull { it.accountName == appEmail }
        // 2) ปฏิทินหลักของบัญชี Google
        ?: calendars.firstOrNull { it.isPrimary }
        // 3) ปฏิทิน Google ตัวแรก (อีเมลมักลงท้าย @gmail / เป็น account google)
        ?: calendars.firstOrNull { it.accountName.contains("@") }
        // 4) อันแรกที่เขียนได้ (เช่น local)
        ?: calendars.first()

    // จำ accountName ไว้ (เหมือน 2.3.1) เพื่อให้ครั้งต่อไปใช้ตัวเดิม
    saveSelectedCalendar(picked)
    return picked.id
}

ถ้าไม่มีปฏิทินเขียนได้เลย → สร้าง local calendar ของแอปเอง

บางเครื่อง (เช่นไม่ได้ล็อกอิน Google และไม่มีปฏิทิน local) อาจไม่มีปฏิทินให้เขียน — สร้าง ปฏิทิน local ของแอปเองได้ผ่าน CalendarContract.Calendars:

import android.content.ContentUris
import android.net.Uri

private const val APP_CAL_NAME = "FoodOrder"
private const val APP_CAL_ACCOUNT = "FoodOrder Local"

// ต้องต่อ query parameter บอกว่าเป็น local account (ACCOUNT_TYPE_LOCAL)
private fun asSyncAdapter(uri: Uri, account: String): Uri =
    uri.buildUpon()
        .appendQueryParameter(CalendarContract.CALLER_IS_SYNCADAPTER, "true")
        .appendQueryParameter(CalendarContract.Calendars.ACCOUNT_NAME, account)
        .appendQueryParameter(CalendarContract.Calendars.ACCOUNT_TYPE,
            CalendarContract.ACCOUNT_TYPE_LOCAL)
        .build()

// สร้างปฏิทิน local ของแอป แล้วคืน CALENDAR_ID
fun createLocalCalendar(resolver: ContentResolver): Long? {
    val values = ContentValues().apply {
        put(CalendarContract.Calendars.ACCOUNT_NAME, APP_CAL_ACCOUNT)
        put(CalendarContract.Calendars.ACCOUNT_TYPE, CalendarContract.ACCOUNT_TYPE_LOCAL)
        put(CalendarContract.Calendars.NAME, APP_CAL_NAME)
        put(CalendarContract.Calendars.CALENDAR_DISPLAY_NAME, "ปฏิทิน FoodOrder")
        put(CalendarContract.Calendars.CALENDAR_COLOR, 0xFF00D1B2.toInt())
        // ให้แอป (owner) มีสิทธิ์เขียนเต็ม
        put(CalendarContract.Calendars.CALENDAR_ACCESS_LEVEL,
            CalendarContract.Calendars.CAL_ACCESS_OWNER)
        put(CalendarContract.Calendars.OWNER_ACCOUNT, APP_CAL_ACCOUNT)
        put(CalendarContract.Calendars.SYNC_EVENTS, 1)
        put(CalendarContract.Calendars.VISIBLE, 1)
    }
    // insert ต้องยิงผ่าน URI แบบ sync-adapter (ไม่งั้นสร้าง local calendar ไม่ได้)
    val uri = resolver.insert(
        asSyncAdapter(CalendarContract.Calendars.CONTENT_URI, APP_CAL_ACCOUNT), values
    )
    return uri?.let { ContentUris.parseId(it) }   // คืน id ที่เพิ่งสร้าง
}
การสร้าง local calendar ต้องมีสิทธิ์ WRITE_CALENDAR (และการยิงผ่าน URI แบบ sync-adapter) • ปฏิทินนี้อยู่เฉพาะในเครื่อง ไม่ sync ขึ้น cloud

รวมทั้งหมด: ได้ CALENDAR_ID แน่นอน (มีก็ใช้ ไม่มีก็สร้าง)

// เรียกใช้จุดเดียว — คืน CALENDAR_ID ที่พร้อมเขียน event เสมอ
fun ensureCalendarId(resolver: ContentResolver, appEmail: String?): Long? {
    // 1) เคยเลือก/เคยเก็บไว้แล้ว → ใช้ตัวเดิม (จาก 2.3.1)
    resolveTargetCalendarId(resolver)?.let { return it }
    // 2) ยังไม่มี → เลือกอัตโนมัติ
    autoPickCalendarId(resolver, appEmail)?.let { return it }
    // 3) ไม่มีปฏิทินเลย → สร้าง local calendar ของแอป
    return createLocalCalendar(resolver)
}

fun insertEvent(resolver: ContentResolver, calendarId: Long): Uri? {
    val start = Calendar.getInstance().apply { add(Calendar.HOUR_OF_DAY, 2) }
    val end = (start.clone() as Calendar).apply { add(Calendar.HOUR_OF_DAY, 1) }

    val values = ContentValues().apply {
        put(CalendarContract.Events.DTSTART, start.timeInMillis)
        put(CalendarContract.Events.DTEND, end.timeInMillis)
        put(CalendarContract.Events.TITLE, "ตรวจสุขภาพประจำปี")
        put(CalendarContract.Events.DESCRIPTION, "อดอาหารก่อน 8 ชม.")
        put(CalendarContract.Events.CALENDAR_ID, calendarId)
        put(CalendarContract.Events.EVENT_TIMEZONE, "Asia/Bangkok")
    }
    val uri = resolver.insert(CalendarContract.Events.CONTENT_URI, values)

    // (ตัวเลือก) เพิ่มการเตือนล่วงหน้า 30 นาที
    uri?.lastPathSegment?.toLong()?.let { eventId ->
        val reminder = ContentValues().apply {
            put(CalendarContract.Reminders.EVENT_ID, eventId)
            put(CalendarContract.Reminders.MINUTES, 30)
            put(CalendarContract.Reminders.METHOD, CalendarContract.Reminders.METHOD_ALERT)
        }
        resolver.insert(CalendarContract.Reminders.CONTENT_URI, reminder)
    }
    return uri
}

วิธีที่ 3 — Google Calendar API (ยืดหยุ่นสูงสุด)

เรียก REST API ของ Google Calendar โดยตรงผ่าน OAuth 2.0 — สร้าง/แก้/ลบ event, เชิญคน (ส่งอีเมล), ตั้ง recurring, สร้างลิงก์ Google Meet, เข้าถึงปฏิทินหลายอัน และทำงาน ข้ามอุปกรณ์/ฝั่ง server ได้เต็มที่

สำคัญเรื่องความปลอดภัย: ห้ามฝัง client secret ไว้ในแอป Android (ถอดรหัสได้ง่าย) — Android ใช้ OAuth client แบบ public client (ไม่มี secret) และ ยืนยันตัวตนด้วย package name + SHA-1 fingerprint ที่ลงทะเบียนไว้

3.0 "ล็อกอิน Google" ที่ว่า หมายถึงแบบไหน

คำว่า "ต้องล็อกอิน Google" ในวิธีนี้ ไม่ได้ หมายถึงให้ผู้ใช้พิมพ์อีเมล/รหัสผ่าน Google ลงในแอปของเรา แต่หมายถึง OAuth 2.0 — ผู้ใช้ "เลือกบัญชี Google แล้วกดยินยอม (consent)" ให้แอปเราเข้าถึงปฏิทินของเขา เป็น flow เดียวกับปุ่ม "Sign in with Google" ทั่วไป

flow ที่ผู้ใช้เห็น

  1. กดปุ่มในแอป → เด้งหน้าจอ เลือกบัญชี Google (บัญชีที่มีในเครื่องอยู่แล้ว)
  2. เด้งหน้าจอ ขอความยินยอม (consent screen) ว่า "แอป X ขอเข้าถึง Google Calendar ของคุณ" → ผู้ใช้กด อนุญาต
  3. แอปได้ access token (ขอบเขตจำกัดเฉพาะปฏิทิน) กลับมา → ใช้ token เรียก Calendar API
สิ่งที่ต้องเข้าใจให้ถูก:
  • ❌ ไม่ใช่ การให้ผู้ใช้กรอกอีเมล/รหัสผ่าน Google ในช่องกรอกในแอปเรา — แบบนั้นผิด นโยบายและอันตราย
  • ✅ รหัสผ่านถูกกรอกที่ หน้าจอของ Google เอง (หรือใช้บัญชีที่ล็อกอินในเครื่องอยู่ แล้ว) — แอปเรา ไม่เคยเห็นรหัสผ่าน
  • ✅ แอปได้แค่ token ที่มี scope จำกัด เฉพาะปฏิทิน ไม่ได้สิทธิ์อย่างอื่น และผู้ใช้ เพิกถอนได้ทุกเมื่อ

Authentication vs Authorization (2 ส่วนที่ใช้คนละตัว)

ส่วนคืออะไรใช้เครื่องมือ
Authentication (ระบุตัวตน)รู้ว่าเป็นบัญชีไหน / ใครล็อกอินCredential Manager (Sign in with Google)
Authorization (ขอสิทธิ์)ขออนุญาตเข้าถึงปฏิทิน (scope)Authorization API (AuthorizationClient)
ถ้าแค่ต้องการ "ยิงเข้าปฏิทิน" อาจข้ามส่วน authentication แล้วเรียก Authorization API เพื่อขอ scope ปฏิทิน + เลือกบัญชีได้เลย • ส่วน GoogleSignIn API เดิม กำลังถูกแทนที่ด้วย Credential Manager (ดูหัวข้อแนวโน้ม)
ต่างจากวิธี 1 และ 2: วิธี 1 (Intent) และวิธี 2 (CalendarContract) ไม่มีการล็อกอินในแอปเราเลย เพราะใช้บัญชี Google ที่ล็อกอินไว้ในเครื่อง (ระดับ OS) อยู่แล้ว — วิธี 2 แค่ขอ permission ปฏิทิน ของระบบเท่านั้น • มีเพียง วิธี 3 ที่ต้องให้ผู้ใช้ยินยอมผ่าน OAuth เพราะแอปคุยกับเซิร์ฟเวอร์ Google โดยตรง

3.2.1 ให้ผู้ใช้ Sign in + ขอสิทธิ์ปฏิทิน

ใช้ Credential Manager (แนวทางล็อกอินปัจจุบัน) เพื่อระบุตัวตน แล้วขอ authorization สำหรับ scope ปฏิทินผ่าน AuthorizationClient:

import com.google.android.gms.auth.api.identity.AuthorizationRequest
import com.google.android.gms.auth.api.identity.Identity
import com.google.api.services.calendar.CalendarScopes

fun requestCalendarAuthorization(activity: Activity, onGranted: (account: Account) -> Unit) {
    val request = AuthorizationRequest.builder()
        .setRequestedScopes(listOf(Scope(CalendarScopes.CALENDAR)))
        .build()

    Identity.getAuthorizationClient(activity)
        .authorize(request)
        .addOnSuccessListener { result ->
            if (result.hasResolution()) {
                // ต้องให้ผู้ใช้ยินยอม → เปิดหน้าจอ consent
                val pi = result.pendingIntent!!
                activity.startIntentSenderForResult(
                    pi.intentSender, RC_AUTH, null, 0, 0, 0, null)
            } else {
                // ได้สิทธิ์แล้ว — ใช้บัญชีนี้เรียก API ได้
                onGranted(result.toGoogleSignInAccount()!!.account!!)
            }
        }
        .addOnFailureListener { e -> Log.e("Auth", "failed", e) }
}
ใน onActivityResult(RC_AUTH) ให้เรียก authorizationClient.getAuthorizationResultFromIntent(data) เพื่อรับผลหลังผู้ใช้ยินยอม

fun buildCalendarService(context: Context, account: Account): Calendar {
    val credential = GoogleAccountCredential.usingOAuth2(
        context, listOf(CalendarScopes.CALENDAR)
    ).apply { selectedAccount = account }

    return Calendar.Builder(
        NetHttpTransport(),
        GsonFactory.getDefaultInstance(),
        credential
    ).setApplicationName("FoodOrder").build()
}

suspend fun createEvent(service: Calendar): String = withContext(Dispatchers.IO) {
    val event = Event().apply {
        summary = "สั่งอาหาร #1234"
        location = "ร้าน FoodOrder"

            .setTimeZone("Asia/Bangkok")

            .setDateTime(DateTime(System.currentTimeMillis() + 7200_000))
            .setTimeZone("Asia/Bangkok")

  • ❌ ตั้งค่าเยอะสุด: Cloud Console + OAuth consent + SHA-1
  • ❌ ผู้ใช้ต้องล็อกอิน Google + ยินยอม scope

สิ่งที่ต้องคำนึงถึงก่อนใช้

  • ความเป็นส่วนตัว (privacy): ปฏิทินเป็นข้อมูลอ่อนไหว — ขอสิทธิ์เท่าที่จำเป็น และอธิบายเหตุผลให้ผู้ใช้ชัดเจน
  • Time zone: ระบุ timezone ให้ถูกเสมอ (เช่น Asia/Bangkok) มิฉะนั้น เวลาเพี้ยนข้ามโซน
  • ต้องมีเน็ตไหม: วิธี 3 ต้องออนไลน์; วิธี 2 เขียนลงเครื่องก่อนแล้ว sync ทีหลังได้
  • OAuth verification: scope calendar เป็น sensitive/restricted — แอป production ที่ให้คนทั่วไปใช้อาจต้องผ่านการรีวิวของ Google ก่อน (มีเวลารอ)
  • SHA-1 ต่าง environment: debug กับ release คนละค่า — ต้องลงทะเบียนทั้งคู่ (รวม Play App Signing) ไม่งั้น sign-in พังเฉพาะบน production
  • Quota & rate limit: Calendar API มีโควตาต่อโปรเจกต์/ต่อผู้ใช้ — ออกแบบให้ batch/cache ไม่ยิงถี่เกิน
  • ประสบการณ์ผู้ใช้: วิธี 1 ผู้ใช้ยืนยันเอง (ไว้ใจได้) ส่วนวิธี 2/3 เขียนเงียบ ๆ ควรมี feedback ว่าเพิ่ม event สำเร็จ
  • รองรับแอปปฏิทินหลากหลาย (วิธี 1): เช็ค resolveActivity เผื่อไม่มี แอปปฏิทิน

ความปลอดภัย

  • ห้ามฝัง client secret ในแอป — Android OAuth client เป็น public client (ไม่มี secret) ยืนยันด้วย package name + SHA-1
  • อย่า log access/refresh token และอย่าเก็บ token แบบ plain text — ใช้ที่จัดเก็บ ปลอดภัย (EncryptedSharedPreferences/Keystore) หรือให้ library จัดการ
  • ขอ scope น้อยที่สุด: ถ้าแค่เพิ่ม event ใช้ calendar.events แทน calendar เต็ม
  • ตรวจ input: ข้อมูลที่ผู้ใช้/ระบบภายนอกป้อน ควร validate ก่อนสร้าง event
  • ฝั่ง server: ถ้าเก็บ refresh token ไว้ที่ backend ต้องเข้ารหัสและจำกัดสิทธิ์เข้าถึง

แนวโน้มในอนาคต

  • Credential Manager เป็นมาตรฐานล็อกอิน — Google ผลักดันแทน GoogleSignIn API เดิม (ตัวเก่าเริ่ม deprecated) แอปใหม่ควรเริ่มด้วย Credential Manager
  • OAuth เข้มขึ้นเรื่องความเป็นส่วนตัว — scope อ่อนไหวต้องผ่าน verification, แนวโน้มบังคับขอสิทธิ์แบบละเอียด (granular) และ least-privilege
  • ฝั่ง server + refresh token ยังเป็นแนวทางหลัก สำหรับแอปที่ต้องซิงก์ต่อเนื่อง/ หลายอุปกรณ์
  • Intent-based ยังอยู่ยาว — เป็นวิธีที่ privacy-friendly และไม่ต้อง maintenance เหมาะกับกรณีทั่วไปตลอดไป
  • สรุป: ถ้าเริ่มโปรเจกต์ใหม่วันนี้ → ใช้ Credential Manager + Calendar API สำหรับงานจริงจัง และ Intent สำหรับงานเบา ๆ; หลีกเลี่ยงการพึ่ง GoogleSignIn API เดิม

ศัพท์ทางเทคนิค (Glossary)

  • OAuth 2.0 — มาตรฐานให้แอปขอสิทธิ์เข้าถึงข้อมูลผู้ใช้โดยไม่ต้องรู้รหัสผ่าน
  • Scope — ขอบเขตสิทธิ์ที่ขอ (เช่น .../auth/calendar)
  • Access token / Refresh token — โทเคนเข้าถึงระยะสั้น / โทเคนต่ออายุระยะยาว
  • Public client — OAuth client ที่ไม่มี secret (แอปมือถือ) ยืนยันด้วย package+SHA-1
  • SHA-1 fingerprint — ลายนิ้วมือของ signing key ที่ใช้ยืนยันตัวตนแอป
  • Credential Manager — API ล็อกอินรวมยุคใหม่ของ Android (แทน GoogleSignIn เดิม)
  • CalendarContract — ContentProvider ของระบบสำหรับเข้าถึงปฏิทินบนเครื่อง
  • calendar_id — id ของปฏิทินปลายทางบนเครื่อง
  • RRULE — กติกากำหนด event ประจำ (recurring) เช่น FREQ=WEEKLY
  • OAuth consent screen — หน้าจอขอความยินยอมจากผู้ใช้ + ที่ตั้งค่า scope/verification
  • sendUpdates — พารามิเตอร์บอกให้ส่งอีเมลแจ้งผู้เข้าร่วมเมื่อสร้าง/แก้ event
