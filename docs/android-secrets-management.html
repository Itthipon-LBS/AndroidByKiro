การเก็บ Key & Secret ใน Android (ฉบับสมบูรณ์)

เจาะลึกว่า key/secret แต่ละชนิด (API token, Google API key, Facebook key, token ผู้ใช้ ฯลฯ) ควรเก็บที่ไหน ไม่ควรเก็บที่ไหน พร้อมเหตุผล, ข้อดี/ข้อเสียแต่ละที่, การจำกัดสิทธิ์ key, การจัดการเมื่อ key รั่ว, checklist และแนวโน้ม — อ่านจบแล้วตัดสินใจได้ ถูกต้องทุกกรณี

กฎเหล็กข้อเดียวที่ต้องจำ: อะไรที่อยู่ในแอป (APK) ถือว่าเปิดเผยได้ เสมอ — decompile อ่านได้, obfuscation แค่หน่วงเวลา • secret ที่ รั่วแล้วเสียหายหนัก (payment/admin/private key) ต้องอยู่ backend เท่านั้น ห้ามอยู่ในแอป

⚡ ตอบเร็ว: ของแบบนี้ เก็บตรงไหน (ฟันธง)

ถ้าอ่านแค่ส่วนเดียว อ่านตรงนี้ — ดูว่า "ของที่คุณมี" ตรงกับแถวไหน แล้วไปทำตามวิธีในข้อถัดไป

🔧 วิธีเก็บจริง (โค้ดก๊อปไปใช้ได้)

วิธี A — Token ผู้ใช้ → EncryptedSharedPreferences

ใช้เมื่อ: เก็บ access/refresh token, ข้อมูลลับที่ผูกกับผู้ใช้คนนั้น

// 1) dependency (build.gradle.kts)
implementation("androidx.security:security-crypto:1.1.0-alpha06")

// 2) สร้างที่เก็บเข้ารหัส (ทำครั้งเดียว เก็บ instance ไว้ใช้)
class SecureStorage(context: Context) {
    private val masterKey = MasterKey.Builder(context)
        .setKeyScheme(MasterKey.KeyScheme.AES256_GCM).build()

    private val prefs = EncryptedSharedPreferences.create(
        context, "secure_store", masterKey,
        EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
        EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
    )

    // 3) ใช้งานเหมือน SharedPreferences ปกติ (เข้ารหัสให้อัตโนมัติ)
    fun saveToken(token: String) = prefs.edit().putString("access_token", token).apply()
    fun getToken(): String? = prefs.getString("access_token", null)
    fun clear() = prefs.edit().clear().apply()   // เรียกตอน logout
}
token ควร อายุสั้น + refresh ได้ + เคลียร์ตอน logout เสมอ

วิธี B — ค่าที่ฝังในแอปได้ → local.properties → BuildConfig

ใช้เมื่อ: Maps key (ต้อง restrict ด้วย), Facebook App ID, Stripe pk_, base URL — ค่าที่ยอมเปิดเผยได้ แต่ไม่อยาก hardcode/commit git

// 1) local.properties (ไฟล์นี้อยู่ใน .gitignore อยู่แล้ว — ไม่ขึ้น git)
MAPS_API_KEY=AIzaSy...your_restricted_key...
BASE_URL=https://api.example.com

// 2) build.gradle.kts — อ่านค่ามาใส่ BuildConfig
import java.util.Properties
val localProps = Properties().apply {
    val f = rootProject.file("local.properties")
    if (f.exists()) f.inputStream().use { load(it) }
}
android {
    buildFeatures { buildConfig = true }
    defaultConfig {
        buildConfigField("String", "MAPS_API_KEY",
            "\"${localProps.getProperty("MAPS_API_KEY") ?: ""}\"")
        buildConfigField("String", "BASE_URL",
            "\"${localProps.getProperty("BASE_URL") ?: ""}\"")
    }
}

// 3) ใช้ในโค้ด
val key = BuildConfig.MAPS_API_KEY
BuildConfig ถอดอ่านได้จาก APK — วิธีนี้แค่กัน commit git + แยกค่าต่อ environment • ใช้เฉพาะค่าที่ยอมเปิดเผย/restrict ได้ ห้ามใส่ secret จริง

วิธี C — restrict key (คู่กับวิธี B สำหรับ Maps ฯลฯ)

ทำใน Google Cloud Console (ไม่ใช่ในโค้ด) — ทำให้ key รั่วไปก็ใช้จากแอปอื่นไม่ได้:

  1. Cloud Console → APIs & Services → Credentials → เลือก API key
  2. Application restrictions → เลือก Android apps → ใส่ package name + SHA-1 ของแอป (ทั้ง debug และ release/Play App Signing)
  3. API restrictions → จำกัดให้ใช้ได้เฉพาะ API ที่ต้องการ (เช่น Maps SDK for Android)
# หา SHA-1 ไปใส่ใน console
./gradlew signingReport

วิธี D — secret สำคัญ → Backend proxy (ไม่เข้าแอปเลย)

ใช้เมื่อ: Stripe sk_, Facebook App Secret, API secret — ของที่รั่วแล้วเสียหายหนัก

แอป ──(ส่งข้อมูลคำสั่งซื้อ + token ผู้ใช้)──► Backend เรา │ (Backend ถือ Stripe secret) ▼ Stripe API แอปไม่เคยเห็น secret เลย — Backend เป็นคนเรียกให้
// ฝั่งแอป: เรียก backend เราเอง (ไม่มี secret ในแอป)
interface PaymentApi {
    @POST("checkout")
    suspend fun checkout(@Body order: OrderRequest): CheckoutResponse
    // backend รับ order → ใช้ Stripe secret (ที่เก็บฝั่ง server) เรียก Stripe → คืนผล
}
ถ้ายังไม่มี backend แต่จำเป็นต้องใช้ third-party ที่มี secret → อย่าใส่ secret ในแอป ให้ทำ backend เล็ก ๆ (เช่น Cloud Function) เป็น proxy แทน

วิธี E — key เข้ารหัสข้อมูลในเครื่อง → Android Keystore

ใช้เมื่อ: ต้องเข้ารหัสข้อมูลเองด้วย key ที่ปลอดภัยสุด (key ถอดออกจากเครื่องไม่ได้)

// สร้าง/ดึง key จาก Keystore (ตัว key ไม่เคยหลุดออกมาเป็นค่าในโค้ด)
fun getOrCreateKey(): SecretKey {
    val ks = KeyStore.getInstance("AndroidKeyStore").apply { load(null) }
    (ks.getEntry("my_key", null) as? KeyStore.SecretKeyEntry)?.let { return it.secretKey }

    val gen = KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
    gen.init(KeyGenParameterSpec.Builder("my_key",
        KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT)
        .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
        .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
        .build())
    return gen.generateKey()
}
ส่วนใหญ่ ไม่ต้องแตะ Keystore ตรง ๆ — ใช้ EncryptedSharedPreferences (วิธี A) ก็พอ เพราะมันใช้ Keystore ให้อยู่แล้วเบื้องหลัง • ใช้ตรง ๆ เมื่อต้องเข้ารหัสไฟล์/ข้อมูลเองแบบ custom
สรุปวิธีเลือก: token ผู้ใช้ → A • key ที่ฝังได้ → B (+C restrict ถ้าเป็น Maps) • secret สำคัญ → D (backend) • เข้ารหัสข้อมูลเอง → E

1. Key / Secret คืออะไร

Secret คือข้อมูลลับที่ถ้ารั่วจะเกิดความเสียหาย — เช่น API key, token, รหัสผ่าน, private key, credential ต่าง ๆ • การเก็บผิดที่ = ประตูให้ผู้โจมตี

ตัวอย่างที่เจอบ่อยในแอป Android:

  • API token/key ของ backend เราเอง — เรียก API ของเรา
  • Third-party key — Google Maps API key, Firebase, Facebook App Secret, Stripe key
  • Token ของผู้ใช้ — access token / refresh token หลัง login
  • Encryption key — key เข้ารหัสข้อมูลในเครื่อง
  • Signing key — key เซ็นแอป (คนละเรื่อง อยู่นอกแอป)

2. ความจริงข้อแรก: APK ถอดได้เสมอ

APK ที่ติดตั้งบนเครื่องผู้ใช้ ถูก decompile กลับมาอ่านได้ ด้วยเครื่องมือฟรี (jadx, apktool) — ทุกอย่างที่ฝังในโค้ด/resource/BuildConfig อ่านได้หมด

สิ่งที่หลายคนเข้าใจผิด:
  • ❌ "ใส่ใน BuildConfig แล้วปลอดภัย" — ผิด อ่านได้
  • ❌ "obfuscate (R8/ProGuard) แล้วปลอดภัย" — ผิด แค่ยากขึ้น ไม่ใช่ปลอดภัย
  • ❌ "ซ่อนใน native code (C++/.so)" — ยากขึ้นแต่ยังถอดได้ (reverse engineer)
  • ❌ "เข้ารหัสไว้ในแอป" — key ที่ใช้ถอดก็อยู่ในแอป → ถอดได้อยู่ดี
ข้อสรุป: ถ้า secret รั่วแล้ว "เสียหายหนัก" → อย่าเอาเข้าแอปเลย เก็บ backend • ถ้าจำเป็นต้องมีในแอป → เลือก key ที่ จำกัดสิทธิ์ได้ และ เพิกถอน/หมุนได้

3. จำแนกประเภท secret ก่อนตัดสินใจ

ก่อนเลือกที่เก็บ ถามว่า "รั่วแล้วเสียหายแค่ไหน" + "จำกัดสิทธิ์ได้ไหม":

ระดับตัวอย่างเก็บที่ไหน
ลับสูงสุด (รั่ว = หายนะ)payment secret key, admin key, DB credential, private keybackend เท่านั้น
token ของผู้ใช้ (ผูกกับคนเดียว)access/refresh tokenEncryptedSharedPreferences / Keystore
key ที่จำกัดสิทธิ์ได้Google Maps API key, Firebase configฝังในแอปได้ + restrict ใน console
ไม่ลับbase URL, feature flag, public configBuildConfig / resource ได้เลย

4. ที่เก็บทั้งหมด (ตารางเทียบ)

ที่เก็บปลอดภัยแค่ไหนเหมาะกับ
hardcode ในโค้ด (const/String)แย่สุดไม่ควรใช้กับ secret เลย
strings.xml / resourceแย่เฉพาะค่าไม่ลับ
BuildConfig (จาก gradle)แย่ (ถอดได้)ค่าไม่ลับ / key ที่ restrict แล้ว
SharedPreferences (ธรรมดา)แย่ (plain text)ค่าไม่ลับ
EncryptedSharedPreferencesดีtoken ผู้ใช้, ข้อมูลลับในเครื่อง
Android Keystoreดีสุด (ในเครื่อง)encryption key (key ถอดออกไม่ได้)
native code (.so)หน่วงเวลา ไม่ใช่ปลอดภัยเพิ่มความยาก (ไม่พึ่งอย่างเดียว)
Backend serverปลอดภัยสุดsecret สำคัญทุกชนิด
แปลง "ระดับ secret" (ข้อ 3) + "ที่เก็บ" (ข้อ 4) เข้าด้วยกัน = ตัดสินใจได้: ลับสูง→ backend, token ผู้ใช้→Encrypted/Keystore, key restrict ได้→BuildConfig+restrict, ไม่ลับ→resource

5. ที่ห้ามเก็บ secret เด็ดขาด

// ❌ hardcode ในโค้ด — ถอด APK เจอทันที
const val STRIPE_SECRET = "sk_live_51H..."

// ❌ ใน strings.xml — อยู่ใน resources.arsc ถอดง่ายยิ่งกว่า
<string name="api_secret">sk_live_51H...</string>

// ❌ commit ลง git — อยู่ใน history ตลอดไป (แม้ลบทีหลัง)
ห้าม: hardcode, strings.xml, comment, log, commit git, ฝากใน client-side ใด ๆ สำหรับ secret สำคัญ • git history อันตรายเป็นพิเศษ — ลบไฟล์ทีหลังก็ยังอยู่ใน commit เก่า ต้องถือว่ารั่วและ rotate ทันที

6. Android Keystore (ที่เก็บ key ปลอดภัยสุดในเครื่อง)

Android Keystore เก็บ cryptographic key ไว้ในฮาร์ดแวร์ (TEE/StrongBox) — key ถูกดึงออกจากเครื่องไม่ได้ แม้เครื่อง root ก็ได้แค่ "ใช้" ไม่ได้ "อ่านค่า key"

// สร้าง key ใน Keystore (ไม่มีตัว key หลุดออกมาในโค้ดเลย)
val keyGen = KeyGenerator.getInstance(KeyProperties.KEY_ALGORITHM_AES, "AndroidKeyStore")
keyGen.init(
    KeyGenParameterSpec.Builder("my_key",
        KeyProperties.PURPOSE_ENCRYPT or KeyProperties.PURPOSE_DECRYPT)
        .setBlockModes(KeyProperties.BLOCK_MODE_GCM)
        .setEncryptionPaddings(KeyProperties.ENCRYPTION_PADDING_NONE)
        .setUserAuthenticationRequired(false)   // ตั้ง true = ต้องปลดล็อก/biometric ก่อนใช้
        .build()
)
val key = keyGen.generateKey()   // ใช้เข้ารหัส/ถอดรหัสข้อมูล — key อยู่ใน Keystore
ใช้ Keystore เมื่อ: ต้องเข้ารหัสข้อมูลในเครื่องด้วย key ที่ปลอดภัย • มักใช้ "เบื้องหลัง" ของ EncryptedSharedPreferences (ซึ่งใช้ Keystore สร้าง master key ให้)

7. EncryptedSharedPreferences / DataStore

ที่เก็บ key-value แบบเข้ารหัส — เหมาะกับ token ของผู้ใช้ และข้อมูลลับที่ต้องเก็บใน เครื่อง (master key ถูกเก็บใน Keystore ให้อัตโนมัติ)

val masterKey = MasterKey.Builder(context)
    .setKeyScheme(MasterKey.KeyScheme.AES256_GCM).build()

val prefs = EncryptedSharedPreferences.create(
    context, "secure_store", masterKey,
    EncryptedSharedPreferences.PrefKeyEncryptionScheme.AES256_SIV,
    EncryptedSharedPreferences.PrefValueEncryptionScheme.AES256_GCM
)
prefs.edit().putString("access_token", token).apply()   // เข้ารหัสอัตโนมัติ
val token = prefs.getString("access_token", null)
ข้อจำกัด: ป้องกัน "การอ่านไฟล์ตรง ๆ" ได้ดี แต่ถ้าแอปทำงานอยู่และถูก hook (เครื่อง root + tool ขั้นสูง) ก็ยังอ่าน token ตอน runtime ได้ — จึงควรใช้ token ที่ อายุ สั้น + เพิกถอนได้ ประกอบด้วย

8. Backend proxy (สำหรับ secret สำคัญ)

วิธีที่ปลอดภัยที่สุดสำหรับ secret สำคัญ: ไม่เอา secret เข้าแอปเลย — ให้แอปเรียก backend ของเรา แล้ว backend เป็นคนถือ secret + เรียก third-party API แทน

❌ แบบไม่ปลอดภัย: แอป (มี Stripe secret) ──► Stripe API ← secret อยู่ในแอป = รั่ว ✅ แบบปลอดภัย (backend proxy): แอป ──► backend เรา (ถือ Stripe secret) ──► Stripe API (แอปส่งแค่ข้อมูลคำสั่งซื้อ ไม่เคยเห็น secret)
  • secret สำคัญ (payment/admin/private key) อยู่ที่ backend — แอปไม่เคยเห็น
  • backend ตรวจสิทธิ์ผู้ใช้ (token) ก่อนเรียก third-party ให้
  • ถ้า secret ต้อง rotate → เปลี่ยนที่ backend ที่เดียว ไม่ต้องอัปเดตแอป

9. Token ของผู้ใช้ (access / refresh token)

  • เก็บใน EncryptedSharedPreferences (หรือ Keystore-backed)
  • access token อายุสั้น (นาที-ชม.) + refresh token ต่ออายุ
  • ถ้าเป็นไปได้ ให้ backend ถือ refresh token แอปถือแค่ access token สั้น ๆ
  • ล้าง token ตอน logout • เพิกถอนได้ฝั่ง server
  • ห้าม log token / ห้ามใส่ใน URL (อยู่ใน history/log server)
// เก็บ token แบบเข้ารหัส + ล้างตอน logout
fun saveToken(token: String) = securePrefs.edit().putString("token", token).apply()
fun logout() = securePrefs.edit().remove("token").apply()

11. จำกัดสิทธิ์ key (restriction) — สำคัญเมื่อต้องฝังในแอป

ถ้าจำเป็นต้องมี key ในแอป (เช่น Maps) การ restrict ทำให้ "รั่วไปก็ใช้ที่อื่นไม่ได้"

  • Application restriction — ผูก key กับ package name + SHA-1 ของแอป → แอปอื่น เอา key ไปใช้ไม่ได้ (Google Cloud Console)
  • API restriction — จำกัดว่า key นี้เรียกได้เฉพาะ API ไหน (เช่น Maps SDK เท่านั้น)
  • Quota/rate limit — จำกัดปริมาณ กันใช้เกิน
สำคัญ: การ restrict ไม่ได้ทำให้ key "ลับ" แต่ทำให้ "ใช้ที่อื่นไม่ได้" — เหมาะกับ key ประเภท public ที่ต้องอยู่ในแอป • สำหรับ secret จริง ๆ ยังต้องอยู่ backend

12. BuildConfig / gradle / git (จัดการ key ที่ต้องฝัง)

วิธี "ที่ถูก" ในการใส่ key ที่ยอมให้อยู่ในแอป (เช่น Maps ที่ restrict แล้ว) — ไม่ hardcode และ ไม่ commit ลง git

// local.properties (อยู่ใน .gitignore — ไม่ขึ้น git)
MAPS_API_KEY=AIza...restricted...

// build.gradle.kts — อ่านจาก local.properties ไป BuildConfig
val mapsKey = gradleLocalProperties(rootDir).getProperty("MAPS_API_KEY") ?: ""
android {
    defaultConfig {
        buildConfigField("String", "MAPS_API_KEY", "\"$mapsKey\"")
    }
}
// ใช้: BuildConfig.MAPS_API_KEY
ย้ำ: BuildConfig ถอดอ่านได้จาก APK — วิธีนี้แค่กัน "commit ลง git" + จัดการ key ต่อ environment (dev/prod) ไม่ได้ทำให้ key ลับ • ใช้เฉพาะกับ key ที่ restrict/ public ได้ ห้ามใช้กับ secret จริง
git: ใส่ local.properties, *.keystore, .env ใน .gitignore • ถ้าเผลอ commit secret แล้ว = ถือว่ารั่ว → rotate ทันที (ลบจาก history อย่างเดียวไม่พอ เพราะอาจถูก clone ไปแล้ว)

13. ข้อดี / ข้อเสีย แต่ละที่เก็บ

Backend (สำหรับ secret สำคัญ)

  • ✅ ปลอดภัยสุด — secret ไม่เคยอยู่ในแอป, rotate ง่าย, เพิกถอนได้
  • ❌ ต้องมี backend + เพิ่ม network round-trip, ออกแบบ API เพิ่ม

Android Keystore

  • ✅ key ถอดออกจากเครื่องไม่ได้ (ฮาร์ดแวร์), ผูก biometric ได้
  • ❌ ใช้กับ "key เข้ารหัส" ไม่ใช่เก็บ API key ภายนอกโดยตรง, API ซับซ้อนกว่า

EncryptedSharedPreferences

  • ✅ ใช้ง่าย, เข้ารหัสอัตโนมัติ, เหมาะ token ผู้ใช้
  • ❌ ยังถูก hook ตอน runtime บนเครื่อง root ได้ → คู่กับ token อายุสั้น

BuildConfig / restrict key

  • ✅ จัดการ key ต่อ environment ได้, ไม่ commit git, restrict กันใช้ที่อื่น
  • ❌ ถอด APK อ่านได้ → เฉพาะ key ที่ยอมเปิดเผย/restrict เท่านั้น

14. ถ้า key รั่วต้องทำยังไง

  1. Rotate ทันที — สร้าง key ใหม่ + ยกเลิก key เก่า (ที่ third-party console/backend)
  2. ตรวจการใช้งานผิดปกติ — ดู log/usage ว่าถูกใช้ในทางที่ผิดไหม
  3. ถ้ารั่วใน git — ถือว่ารั่วถาวร (อาจถูก clone) → rotate เสมอ ไม่ใช่แค่ลบ commit
  4. หา root cause — ทำไมถึงรั่ว (hardcode? commit? log?) แล้วแก้ต้นเหตุ
  5. เพิ่มการป้องกัน — restrict, ย้ายไป backend, ใช้ secret scanner กันซ้ำ
ป้องกันล่วงหน้า: ใช้ secret scanning (git-secrets, GitHub secret scanning, gitleaks) ใน CI เพื่อจับ secret ก่อน commit/merge

16. แนวโน้มในอนาคต

  • Backend-for-frontend (BFF) เป็นมาตรฐาน — แอปไม่ถือ secret เลย ทุกอย่างผ่าน backend
  • short-lived token + refresh ปกติทุกที่ — ลดความเสียหายเมื่อ token รั่ว
  • Passkeys / Credential Manager — ลดการพึ่งรหัสผ่าน/secret ฝั่ง client
  • Play Integrity + App Attestation — ยืนยันว่า request มาจากแอปจริง (ลดการปลอมเรียก API)
  • secret scanning เป็น default ใน CI — GitHub/GitLab จับ secret อัตโนมัติ
  • สรุป: ทิศทางชัดเจนคือ "ย้าย secret ออกจาก client ให้มากที่สุด" + token อายุสั้น + ยืนยันตัวแอป — ออกแบบตามนี้ตั้งแต่ต้นจะปลอดภัยระยะยาว

17. ศัพท์ทางเทคนิค (Glossary)

  • Secret — ข้อมูลลับที่รั่วแล้วเสียหาย (key/token/credential)
  • API key — กุญแจเรียกใช้ API (บางตัว public บางตัว secret)
  • publishable/public key — key ที่ออกแบบให้เปิดเผยได้ (เช่น Stripe pk_)
  • secret key — key ลับ (เช่น Stripe sk_) ต้องอยู่ backend
  • access token / refresh token — โทเคนเข้าถึงสั้น / ต่ออายุ
  • Android Keystore — ที่เก็บ cryptographic key ในฮาร์ดแวร์ (ถอดออกไม่ได้)
  • EncryptedSharedPreferences — เก็บ key-value แบบเข้ารหัส
  • BuildConfig — ค่าที่ gradle ฝังลง APK (ถอดอ่านได้)
  • restriction — จำกัดว่า key ใช้ได้จาก package/SHA-1/API ไหน
  • backend proxy / BFF — ให้ server ถือ secret + เรียก third-party แทนแอป
  • rotate — เปลี่ยน key ใหม่ + ยกเลิกอันเก่า
  • secret scanning — เครื่องมือจับ secret ที่หลุดใน code/git
  • public client (OAuth) — client ที่ไม่มี secret (แอปมือถือ)
  • Play Integrity / App Attestation — ยืนยันว่า request มาจากแอปจริง
