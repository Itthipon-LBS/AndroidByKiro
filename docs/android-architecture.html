สถาปัตยกรรมที่แนะนำ (Android App Architecture)

สรุปแนวทางการวางสถาปัตยกรรมแอป Android ตามที่ Google แนะนำ (Guide to app architecture) แบบครบถ้วน — การแบ่งชั้น, UI/Domain/Data layer, Unidirectional Data Flow, รูปแบบ MVVM/MVI/MVP/MVC, DI, การแยกโมดูล, ข้อดี/ข้อเสีย, การเลือกใช้, ข้อผิดพลาดที่พบบ่อย และแนวโน้ม อ่านจบแล้วนำไปวางโครงโปรเจกต์จริงได้

สรุปสั้นสุด: แบ่งแอปเป็น UI layer → (Domain layer) → Data layer โดย data ไหลทางเดียว (UDF): event ขึ้นบน, state ลงล่าง • ใช้ MVVM/MVI ในชั้น UI • Repository เป็นแหล่งความจริงเดียว • เป้าหมายคือ แยกความรับผิดชอบ, ทดสอบง่าย, ขยายได้

1. ทำไมต้องมีสถาปัตยกรรม

แอปเล็ก ๆ เขียนรวมกันใน Activity เดียวก็ทำงานได้ แต่พอโตขึ้นจะเจอปัญหา: แก้จุดเดียว กระทบทั้งไฟล์, เทสต์ไม่ได้เพราะ logic ผูกกับ UI, หลายคนทำงานชนกัน, บั๊ก lifecycle

สถาปัตยกรรมที่ดีช่วยให้:

  • แยกความรับผิดชอบ — UI ทำแค่แสดงผล, logic อยู่ที่อื่น
  • ทดสอบง่าย — logic ที่ไม่ผูก UI เทสต์ด้วย unit test ได้
  • ขยาย/แก้ง่าย — เพิ่มฟีเจอร์โดยไม่พังของเดิม
  • ทนต่อ lifecycle — state รอดหมุนจอ/process death
เอกสารนี้อิงแนวทาง "Guide to app architecture" ของ Google ซึ่งเป็น มาตรฐานที่ทีมส่วนใหญ่ใช้

2. หลักการพื้นฐาน

  • Separation of concerns — แต่ละส่วนทำหน้าที่เดียว อย่ายัด logic ลง Activity/Fragment
  • Drive UI from data models — UI สะท้อนจาก state/ข้อมูล ไม่ใช่เก็บ state ไว้ใน view
  • Single source of truth (SSOT) — ข้อมูลแต่ละชนิดมี "แหล่งความจริงเดียว" ที่แก้ได้ (มักเป็น Repository/DB) คนอื่นแค่อ่าน
  • Unidirectional Data Flow (UDF) — state ไหลลง, event ไหลขึ้น (หัวข้อ 7)
  • ทุกชั้นควรอยู่ได้ด้วยตัวเอง (loosely coupled) — พึ่ง abstraction (interface) ไม่ใช่ตัวจริง

3. การแบ่งชั้น (Layers)

สถาปัตยกรรมมาตรฐานแบ่งเป็น 2 ชั้นบังคับ + 1 ชั้นตัวเลือก:

┌─────────────────────────────────────┐ │ UI Layer │ ← แสดงผล + รับ interaction │ (UI elements + State holders/VM) │ └───────────────┬─────────────────────┘ │ (state ↓ / event ↑) ┌───────────────▼─────────────────────┐ │ Domain Layer (optional) │ ← business logic ที่ใช้ซ้ำ (Use Cases) └───────────────┬─────────────────────┘ │ ┌───────────────▼─────────────────────┐ │ Data Layer │ ← แหล่งข้อมูล (Repository + DataSource) │ (Repositories + Data Sources) │ └──────────────────────────────────────┘
ชั้นหน้าที่องค์ประกอบหลัก
UIแสดง state บนจอ + ส่ง event ของผู้ใช้Activity/Fragment/Composable, ViewModel
Domain (optional)รวม business logic ที่ซับซ้อน/ใช้ซ้ำหลายที่Use Case / Interactor
Dataจัดการข้อมูล (network/db) + เป็น SSOTRepository, DataSource (Retrofit/Room)
กฎการพึ่งพา (dependency rule): ชั้นบนรู้จักชั้นล่างได้ แต่ชั้นล่าง ห้ามรู้จักชั้นบน — Data layer ต้องไม่รู้จัก UI/ViewModel

4. UI Layer

หน้าที่: แปลงข้อมูลจากชั้นล่างเป็น UI state แล้วแสดงผล + รับ interaction ส่งต่อ

  • UI elements — Activity/Fragment/Compose ที่วาดหน้าจอ ไม่ควรมี business logic
  • State holder (ViewModel) — ถือ UI state, จัดการ logic ของหน้าจอ, เรียก Repository/UseCase
  • UI State — ควรเป็น immutable data class ก้อนเดียวที่อธิบายหน้าจอทั้งหน้า
// UI state = ก้อนข้อมูล immutable ที่อธิบายทั้งหน้าจอ
data class OrderUiState(
    val items: List<CartItem> = emptyList(),
    val total: BigDecimal = BigDecimal.ZERO,
    val isLoading: Boolean = false,
    val error: String? = null
)

class OrderViewModel(private val repo: OrderRepository) : ViewModel() {
    private val _uiState = MutableStateFlow(OrderUiState())
    val uiState: StateFlow<OrderUiState> = _uiState.asStateFlow()   // read-only ออกไป

    fun loadCart() {
        viewModelScope.launch {
            _uiState.update { it.copy(isLoading = true) }
            try {
                val items = repo.getCart()
                _uiState.update { it.copy(items = items, total = items.sumTotal(), isLoading = false) }
            } catch (e: Exception) {
                _uiState.update { it.copy(error = e.message, isLoading = false) }
            }
        }
    }
}
UI แค่ observe uiState แล้ววาด — ไม่เก็บ state เอง (SSOT ของหน้าจออยู่ที่ ViewModel)

5. Domain Layer (ตัวเลือก)

ชั้นกลางที่รวม business logic ที่ซับซ้อนหรือใช้ซ้ำหลาย ViewModel ห่อเป็น Use Case (บางทีเรียก Interactor) — ใช้เมื่อจำเป็น ไม่ต้องมีทุกโปรเจกต์

// Use Case = 1 การกระทำทางธุรกิจ 1 คลาส (ชื่อเป็นกริยา)
class PlaceOrderUseCase(
    private val orderRepo: OrderRepository,
    private val paymentRepo: PaymentRepository
) {
    // operator invoke → เรียกได้เหมือนฟังก์ชัน: placeOrder(cart)
    suspend operator fun invoke(cart: Cart): Result<OrderId> {
        if (cart.isEmpty()) return Result.failure(EmptyCartException())
        val payment = paymentRepo.charge(cart.total)
        return orderRepo.submit(cart, payment)
    }
}
เมื่อไรควรมี Domain layer: logic เดียวกันถูกใช้ในหลาย ViewModel, หรือ ViewModel เริ่มใหญ่/ซับซ้อนเกินไป • โปรเจกต์เล็กข้ามได้ (ViewModel คุย Repository ตรง ๆ)

6. Data Layer

หน้าที่: เป็น แหล่งความจริง (SSOT) ของข้อมูลแอป จัดการ network/db และซ่อนรายละเอียด ไว้หลัง Repository

  • Repository — จุดเข้าถึงข้อมูลชนิดหนึ่ง (เช่น OrderRepository) รวมข้อมูลจากหลาย source, ตัดสินใจว่าจะเอาจาก cache หรือ network, expose เป็น model ที่ชั้นบนใช้
  • Data Source — ตัวจริงที่คุย network (Retrofit/Ktor) หรือ local (Room/DataStore)
// interface ให้ชั้นบนพึ่ง (ไม่พึ่งตัวจริง → เทสต์/สลับ implementation ได้)
interface OrderRepository {
    suspend fun getCart(): List<CartItem>
    suspend fun submit(cart: Cart, payment: Payment): Result<OrderId>
}

class OrderRepositoryImpl(
    private val remote: OrderApi,       // Retrofit
    private val local: OrderDao         // Room
) : OrderRepository {
    override suspend fun getCart(): List<CartItem> {
        return local.getCart().ifEmpty {
            remote.fetchCart().also { local.saveCart(it) }   // cache-then-network
        }
    }
    // ...
}
SSOT: ให้ Repository/DB เป็นเจ้าของข้อมูล — UI อ่านผ่าน Repository เท่านั้น อย่าให้หลายที่แก้ข้อมูลชนิดเดียวกันตรง ๆ

7. Unidirectional Data Flow (UDF)

ข้อมูลไหล ทางเดียว: state ลงล่าง (ViewModel → UI) และ event ขึ้นบน (UI → ViewModel) — ทำให้ตามรอย state ง่ายและกันบั๊ก state ไม่ตรงกัน

state (StateFlow) ViewModel ───────────────► UI (แสดงผล) ▲ │ └──────────────────────────┘ event (คลิก/พิมพ์) เรียก fun บน ViewModel
  • UI ไม่แก้ state เอง — ส่ง event ให้ ViewModel, ViewModel แก้ state, UI สะท้อนตามใหม่
  • state เป็น immutable → สร้างก้อนใหม่ด้วย copy() ทุกครั้งที่เปลี่ยน

8. รูปแบบชั้น UI: MVVM / MVI / MVP / MVC

รูปแบบแนวคิดสถานะปัจจุบัน
MVC (Model-View-Controller)ดั้งเดิม — Controller/Activity คุมทั้ง view+logicเก่า, logic กระจุกใน Activity
MVP (Model-View-Presenter)Presenter ถือ logic, View เป็น interfaceดีขึ้น แต่ Presenter ผูกกับ View lifecycle
MVVM (Model-View-ViewModel)ViewModel ถือ state, View observeแนะนำ/นิยมสุด (Jetpack ViewModel)
MVI (Model-View-Intent)state ก้อนเดียว + event เป็น intent (UDF เข้ม)นิยมขึ้นเรื่อย ๆ โดยเฉพาะกับ Compose

MVVM vs MVI (ที่ใช้จริงทุกวันนี้)

  • MVVM — ViewModel expose state หลายตัว/หนึ่งก้อนก็ได้ ยืดหยุ่น เข้าใจง่าย
  • MVI — บังคับ state ก้อนเดียว (single immutable state) + event ผ่าน sealed class → คาดเดาง่าย เหมาะจอที่ state ซับซ้อน แต่ boilerplate มากกว่า
// MVI: event เป็น sealed class ก้อนเดียว
sealed interface OrderIntent {
    data object LoadCart : OrderIntent
    data class RemoveItem(val id: String) : OrderIntent
    data object PlaceOrder : OrderIntent
}
fun onIntent(intent: OrderIntent) = when (intent) {
    OrderIntent.LoadCart      -> loadCart()
    is OrderIntent.RemoveItem -> removeItem(intent.id)
    OrderIntent.PlaceOrder    -> placeOrder()
}
ทั้ง MVVM และ MVI ใช้ ViewModel เหมือนกัน — MVI คือ MVVM ที่จัดระเบียบ state/event ให้เข้มขึ้น เลือกตามความซับซ้อนของหน้าจอ

9. Dependency Injection (DI)

แทนที่จะให้คลาสสร้าง dependency เอง (ผูกกันแน่น เทสต์ยาก) ให้ ฉีดเข้ามาจากภายนอก → สลับ implementation/ใส่ fake ตอนเทสต์ได้

// Hilt (ทางการ) — ประกาศว่าจะฉีดอะไรให้ interface ไหน
@Module @InstallIn(SingletonComponent::class)
object DataModule {
    @Provides @Singleton
    fun provideOrderRepository(api: OrderApi, dao: OrderDao): OrderRepository =
        OrderRepositoryImpl(api, dao)
}

@HiltViewModel
class OrderViewModel @Inject constructor(
    private val repo: OrderRepository   // ถูกฉีดให้อัตโนมัติ
) : ViewModel()
  • Hilt / Dagger — DI ทางการ (compile-time, ปลอดภัย, นิยมสุด)
  • Koin — DI แบบ Kotlin DSL (runtime, เรียนง่ายกว่า)
  • โปรเจกต์เล็ก: ฉีดผ่าน constructor เองแบบ manual DI ก็ได้

10. Modularization (แยกโมดูล)

เมื่อแอปโต แยกโค้ดเป็นหลาย Gradle module เพื่อ build เร็วขึ้น + แยกทีม + บังคับขอบเขต

:app ← ประกอบทุกอย่างเข้าด้วยกัน :feature:order ← ฟีเจอร์สั่งอาหาร (UI + VM) :feature:cart :core:data ← Repository, DataSource :core:domain ← Use Cases :core:ui ← component UI ที่ใช้ร่วม :core:common ← util, model กลาง
  • by layer — แยกตามชั้น (data/domain/ui)
  • by feature — แยกตามฟีเจอร์ (order/cart/profile) — นิยมเมื่อทีมใหญ่
  • ผสมกัน (feature + core) เป็นแนวทางที่พบบ่อยสุดในแอปใหญ่
โปรเจกต์เล็ก-กลาง module เดียว (:app) ก็พอ — modularization มีต้นทุน setup ทำเมื่อ build ช้า/ทีมโตจริง ๆ

11. ตัวอย่างโค้ดเต็ม (ต่อกันครบทุกชั้น)

ตัวอย่าง flow "โหลดตะกร้า → กดสั่ง" ไล่จาก UI → ViewModel → (UseCase) → Repository:

// ── Data Layer ──
interface OrderRepository {
    suspend fun getCart(): List<CartItem>
    suspend fun submit(cart: Cart): Result<OrderId>
}

// ── Domain Layer (optional) ──
class PlaceOrderUseCase(private val repo: OrderRepository) {
    suspend operator fun invoke(cart: Cart): Result<OrderId> {
        if (cart.isEmpty()) return Result.failure(EmptyCartException())
        return repo.submit(cart)
    }
}

// ── UI Layer: ViewModel ──
@HiltViewModel
class OrderViewModel @Inject constructor(
    private val repo: OrderRepository,
    private val placeOrder: PlaceOrderUseCase
) : ViewModel() {
    private val _uiState = MutableStateFlow(OrderUiState())
    val uiState = _uiState.asStateFlow()

    fun loadCart() = viewModelScope.launch {
        _uiState.update { it.copy(isLoading = true) }
        val items = repo.getCart()
        _uiState.update { it.copy(items = items, isLoading = false) }
    }

    fun onPlaceOrder() = viewModelScope.launch {
        placeOrder(Cart(_uiState.value.items))
            .onSuccess { _uiState.update { s -> s.copy(placed = true) } }
            .onFailure { e -> _uiState.update { s -> s.copy(error = e.message) } }
    }
}

// ── UI Layer: Fragment (observe state, ส่ง event) ──
class OrderFragment : Fragment() {
    private val vm: OrderViewModel by viewModels()

    override fun onViewCreated(view: View, s: Bundle?) {
        viewLifecycleOwner.lifecycleScope.launch {
            viewLifecycleOwner.repeatOnLifecycle(Lifecycle.State.STARTED) {
                vm.uiState.collect { render(it) }        // state ↓
            }
        }
        binding.placeBtn.setOnClickListener { vm.onPlaceOrder() }   // event ↑
    }
}
สังเกต: UI ไม่มี business logic เลย — แค่ observe state + ส่ง event • logic อยู่ที่ ViewModel/UseCase • ข้อมูลอยู่ที่ Repository

12. ข้อดี / ข้อเสีย

  • ✅ ทดสอบง่าย — ViewModel/UseCase/Repository เทสต์ด้วย unit test โดยไม่ต้องมี UI
  • ✅ แก้/ขยายง่าย — เพิ่มฟีเจอร์โดยไม่กระทบส่วนอื่น
  • ✅ ทนต่อ lifecycle — state อยู่ใน ViewModel รอดหมุนจอ
  • ✅ หลายคนทำงานพร้อมกันได้ — แยกชั้น/โมดูลชัด
  • ✅ สลับ implementation ได้ (เช่นเปลี่ยน network library) เพราะพึ่ง interface
  • ❌ boilerplate เยอะขึ้น — โปรเจกต์เล็กอาจรู้สึกเกินจำเป็น
  • ❌ เรียนรู้เยอะ (ViewModel, Flow, DI, Repository) สำหรับมือใหม่
  • ❌ over-engineering ได้ง่าย — ใส่ทุก layer/UseCase ทั้งที่ไม่จำเป็น
  • ❌ ไฟล์เยอะขึ้น (interface + impl + module)
คุ้มค่าเมื่อแอปมีแนวโน้มโต/มีทีม — โปรเจกต์เล็กมาก ๆ ปรับให้เบาลงได้ (ข้าม Domain, manual DI, module เดียว)

14. ข้อผิดพลาดที่พบบ่อย

ข้อผิดพลาดผล / วิธีแก้
ยัด business logic ลง Activity/Fragmentเทสต์ยาก, ผูก lifecycle → ย้ายไป ViewModel/UseCase
เก็บ Context/View ใน ViewModelmemory leak → ส่งผ่าน parameter/ใช้ AndroidViewModel เท่าที่จำเป็น
UI แก้ state เอง (ไม่ผ่าน ViewModel)state ไม่ตรงกัน → ยึด UDF (event ขึ้น, state ลง)
Data layer รู้จัก UI/ViewModelผิด dependency rule → ชั้นล่างห้ามรู้จักชั้นบน
ViewModel พึ่ง implementation ตรง ๆเทสต์/สลับยาก → พึ่ง interface + DI
expose MutableStateFlow ออกจาก ViewModelข้างนอกแก้ได้ → expose เป็น StateFlow (asStateFlow)
over-engineering (ทุก layer ในแอปเล็ก)ช้า/งานเยอะเกิน → เริ่มเบา เพิ่มเมื่อจำเป็น

15. แนวโน้มในอนาคต

  • Compose + MVI/UDF เป็นค่าเริ่มต้น — Compose เข้ากับโมเดล state-driven/UDF โดยตรง ทำให้ MVI ได้รับความนิยมขึ้น
  • Domain layer + Use Case เป็นมาตรฐานในแอปใหญ่ — โดยเฉพาะ multi-module
  • Kotlin Multiplatform (KMP) — แชร์ Data/Domain layer ข้าม Android/iOS ได้ → สถาปัตยกรรมแบบแยกชั้นยิ่งสำคัญ (UI แยก, logic ใช้ร่วม)
  • Hilt เป็น DI มาตรฐาน — Google ผลักดันต่อเนื่อง
  • เครื่องมือช่วยมากขึ้น — template/แนวทางทางการทำให้วางโครงเร็วขึ้น แต่หลักการ (แยกชั้น, SSOT, UDF) ยังเหมือนเดิม
  • สรุป: ทิศทางคือ "แยกชั้นให้ชัดเพื่อแชร์/ทดสอบ/ขยาย" — เทคโนโลยีเปลี่ยน (View→Compose, MVVM→MVI) แต่หลักการพื้นฐานคงเดิม

16. ศัพท์ทางเทคนิค (Glossary)

  • Separation of concerns — แยกความรับผิดชอบ แต่ละส่วนทำหน้าที่เดียว
  • SSOT (Single Source of Truth) — แหล่งความจริงเดียวของข้อมูลแต่ละชนิด
  • UDF (Unidirectional Data Flow) — ข้อมูลไหลทางเดียว: state ลง, event ขึ้น
  • UI State — ก้อนข้อมูล immutable ที่อธิบายทั้งหน้าจอ
  • State holder — ตัวถือ state (มักเป็น ViewModel)
  • Repository — จุดเข้าถึงข้อมูลชนิดหนึ่ง ซ่อนรายละเอียด source
  • Data Source — ตัวจริงที่คุย network/db (Retrofit/Room)
  • Use Case / Interactor — 1 การกระทำทางธุรกิจใน Domain layer
  • MVVM / MVI / MVP / MVC — รูปแบบจัดโครงชั้น UI
  • DI (Dependency Injection) — ฉีด dependency จากภายนอก (Hilt/Dagger/Koin)
  • Dependency rule — ชั้นล่างห้ามรู้จักชั้นบน
  • Modularization — แยกโค้ดเป็นหลาย Gradle module
